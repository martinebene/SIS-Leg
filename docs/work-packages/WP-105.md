# WP-105 - Bootstrap público seguro desde releases pre-WP-101A

## Estado documental

`APROBADO`

## Objetivo

Crear un bootstrap **transicional, mínimo, auditable y fail-closed** que permita pasar desde una release histórica compatible con WP-029 a una release pública moderna, sin activar esa release ni modificar `current`, `target-release`, servicios, Nginx, wrappers, sudoers, configuración institucional o `.desktop`.

El bootstrap existe sólo para superar el salto de formato/capacidad entre la release histórica y el mecanismo público moderno. Una vez preparada una release moderna, las operaciones normales deben volver a usar exclusivamente las herramientas versionadas ya existentes (`actualizador_publico.py`, `herramienta_despliegue.py`, `instalador_host.py`, `operaciones_host.py`).

## Dependencias

- WP-100 `INTEGRADO`: canal público de releases y evidencia verificable.
- WP-101 `INTEGRADO`: mecanismo versionado de operación/instalación del host.
- WP-104 `INTEGRADO`: selección de release desplegable cuando `main` avanza documentalmente.

## Problema demostrado

El host productivo está sano y estable en SIS-Leg, pero la release activa/target `a702d71da8c0f2d66b8ccb0231543d15bcdb1e48` es anterior al mecanismo versionado moderno.

Esa release:

- no contiene `deploy/actualizador_publico.py`;
- no contiene `deploy/instalador_host.py` ni `deploy/operaciones_host.py`;
- sí contiene `deploy/herramienta_despliegue.py` y el subcomando `preparar`;
- pero su validador de `release.json` acepta únicamente las cuatro SPA antiguas (`moderacion`, `recinto`, `simulador`, `tecnico`) y por lo tanto rechaza una release moderna que incluye también `zocalo`.

Consecuencia: la herramienta residente no puede preparar de forma canónica una release moderna y no debe relajarse ni editarse manualmente en producción.

**Este WP es sólo de desarrollo y no autoriza ninguna mutación del host productivo.**

## Alcance

### 1. Artefacto bootstrap autónomo

Implementar un único ejecutable Python versionado, preferentemente `deploy/bootstrap_publico.py`, que:

- use sólo biblioteca estándar de Python 3.14;
- no importe módulos desde la release activa histórica;
- pueda ejecutarse como archivo suelto;
- no requiera `git`, `gh`, PAT, token, cookie ni autenticación GitHub;
- acepte identidades exactas de una release pública;
- falle cerrado ante cualquier desacuerdo de identidad.

### 2. Transporte público y validación

Debe obtener por HTTPS público y validar, como mínimo:

- publicación exacta `sis-leg-<SHA>` y `target_commitish`;
- exactamente los tres assets canónicos;
- metadatos de publicación;
- intento histórico exacto de CI y job `Empaquetado · release productiva`;
- commit y tree SHA;
- paquete y sidecar;
- SHA-256 del paquete;
- `release.json` y su inventario;
- ausencia de rutas absolutas, traversal, entradas especiales o miembros fuera de la allowlist productiva.

No confiar sólo en fecha, orden de releases, nombres mutables ni prefijos de SHA.

### 3. Delegación a la herramienta moderna

El bootstrap no debe reimplementar la preparación completa.

Después de verificar íntegramente el paquete, debe materializar en un temporal privado únicamente los módulos modernos mínimos necesarios para ejecutar la preparación canónica, verificando sus bytes contra el inventario de `release.json`.

Como mínimo evaluar `deploy/herramienta_despliegue.py`, `deploy/configuracion_local.py` y cualquier dependencia adicional real.

Luego debe ejecutar la **herramienta moderna extraída y verificada de la propia release objetivo** para hacer `preparar` sobre el paquete ya validado.

No ejecutar ningún byte extraído antes de validar paquete, manifest e inventario.

### 4. Efectos permitidos del futuro uso productivo

El bootstrap debe estar diseñado para que, cuando exista una asignación productiva específica, los únicos efectos persistentes sean los propios de preparar una release nueva bajo `/opt/sis-leg/releases/<SHA>` y los temporales/descargas controlados necesarios.

Debe garantizar que no modifica:

- `/opt/sis-leg/current`;
- `/opt/sis-leg/target-release`;
- configuración institucional existente;
- systemd o Nginx;
- `/usr/local/bin`;
- wrappers de `/home/concejo/.local/bin`;
- sudoers/PolicyKit;
- `.desktop`;
- Legacy;
- logs históricos.

No debe activar ni reiniciar servicios.

### 5. Idempotencia y fallas

- Release ya preparada con marcador compatible: informar idempotencia sin reescribirla.
- Directorio parcial/incompatible: abortar y exigir inspección; no borrar ni reparar silenciosamente.
- Falla de descarga/validación: no promover artefactos parciales.
- Falla durante `preparar`: preservar la semántica diagnóstica de la herramienta moderna y nunca tocar `current`/`target-release`.
- No implementar limpieza destructiva automática.

### 6. Diagnóstico/readiness

Debe existir una forma de validar conectividad, release objetivo y compatibilidad del bootstrap sin preparar ni escribir en `/opt/sis-leg`, apta para un gate productivo read-only previo.

### 7. Procedimiento posterior para WP-101B

Documentar un flujo inequívoco:

1. obtener el bootstrap desde una URL inmutable del commit/release aprobado;
2. verificar su SHA-256 exacto antes de ejecutarlo;
3. ejecutar primero diagnóstico/readiness;
4. sólo con HUMAN_GATE productivo separado, preparar la release moderna;
5. detenerse después de preparar;
6. ejecutar luego `instalador_host.py plan` desde la release moderna en otro gate;
7. no instalar wrappers, corregir privilegios/helper ni conmutar en el mismo turno de bootstrap.

El hash exacto que utilizará producción se fija después del merge y publicación.

## Casos de prueba obligatorios

1. release válida completa → valida y delega en la herramienta moderna;
2. SHA/tag/target divergentes → fail-closed;
3. draft/prerelease o assets inesperados → fail-closed;
4. CI/job/tree/metadatos inconsistentes → fail-closed;
5. checksum incorrecto → fail-closed antes de ejecutar código extraído;
6. `release.json` inválido, traversal, symlink/hardlink/entrada especial o inventario inconsistente → fail-closed;
7. módulos de despliegue extraídos con hash distinto del inventario → no ejecutar;
8. la validación histórica de cuatro SPA no se usa para validar el manifest moderno;
9. contrato vigente de cinco SPA + manual aceptado correctamente;
10. preparación no modifica `current`, `target-release`, servicios, Nginx, wrappers ni configuración;
11. directorio parcial existente → aborta sin borrar;
12. release ya preparada compatible → idempotencia;
13. ausencia de Authorization/Cookie/token;
14. temporales limpiados ante falla de transporte/validación;
15. ninguna regresión en el canal público normal.
