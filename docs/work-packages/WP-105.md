# WP-105 — Bootstrap público seguro desde releases pre-WP-101A

## Estado y autoridad

Work Package de desarrollo previo a continuar WP-101B sobre producción.

**No autoriza ninguna mutación del host productivo.** Su resultado debe quedar versionado, probado, revisado e integrado antes de volver a producción.

## Problema demostrado

El host productivo está sano y estable en SIS-Leg, pero la release activa/target `a702d71da8c0f2d66b8ccb0231543d15bcdb1e48` es anterior a WP-101A.

Esa release:

- no contiene `deploy/actualizador_publico.py`;
- no contiene `deploy/instalador_host.py` ni `deploy/operaciones_host.py`;
- sí contiene `deploy/herramienta_despliegue.py` y el subcomando `preparar`;
- pero su validador de `release.json` acepta únicamente las cuatro SPA antiguas (`moderacion`, `recinto`, `simulador`, `tecnico`) y por lo tanto no puede preparar una release moderna que incluye también `zocalo`.

Consecuencia: no existe hoy una ruta canónica para obtener y preparar en ese host una release moderna sin introducir manualmente código nuevo o relajar la validación histórica.

## Objetivo

Crear un bootstrap **transicional, mínimo, auditable y fail-closed** que permita pasar desde una release histórica compatible con WP-029 a una release pública moderna, sin activar esa release ni modificar `current`, `target-release`, servicios, Nginx, wrappers, sudoers, configuración institucional o `.desktop`.

El bootstrap existe sólo para superar el salto de formato/capacidad entre la release histórica y el mecanismo público moderno. Una vez preparada una release moderna, las operaciones normales deben volver a usar exclusivamente las herramientas versionadas ya existentes (`actualizador_publico.py`, `herramienta_despliegue.py`, `instalador_host.py`, `operaciones_host.py`).

## Semántica requerida

### 1. Artefacto bootstrap autónomo

Implementar un único ejecutable Python versionado, preferentemente:

`deploy/bootstrap_publico.py`

Debe:

- usar sólo biblioteca estándar de Python 3.14;
- no importar módulos desde la release activa histórica;
- ser ejecutable como archivo suelto;
- no requerir `git`, `gh`, PAT, token, cookie ni autenticación GitHub;
- aceptar exclusivamente identidades exactas de una release pública: SHA completo, tag/URL o repositorio canónico y, cuando corresponda, SHA-256 esperado;
- fallar cerrado ante cualquier desacuerdo de identidad.

### 2. Transporte público y validación

Debe obtener por HTTPS público y validar, como mínimo:

- publicación exacta `sis-leg-<SHA>`;
- `target_commitish` exacto;
- exactamente los tres assets canónicos de la release;
- metadatos de publicación;
- intento histórico exacto de CI y job `Empaquetado · release productiva`;
- commit y tree SHA;
- paquete y sidecar;
- SHA-256 del paquete;
- `release.json` y su inventario;
- ausencia de rutas absolutas, traversal, entradas especiales o miembros fuera de la allowlist productiva.

No se permite confiar sólo en fecha, nombre de archivo, `latest.tar.gz`, orden de publicación o prefijos de SHA.

### 3. Delegación a la herramienta moderna

El bootstrap no debe reimplementar la preparación completa de una release.

Después de verificar íntegramente el paquete, debe materializar en un temporal privado únicamente los módulos modernos mínimos necesarios para ejecutar la preparación canónica, verificando sus bytes contra el inventario de `release.json`.

Como mínimo evaluar:

- `deploy/herramienta_despliegue.py`;
- `deploy/configuracion_local.py`;
- cualquier dependencia adicional real que el módulo moderno requiera.

Luego debe ejecutar la **herramienta moderna extraída y verificada de la propia release objetivo** para hacer `preparar` sobre el paquete ya validado.

No debe ejecutar ningún byte extraído antes de haber validado paquete, manifest e inventario.

### 4. Efectos permitidos

En modo de preparación autorizado, los únicos efectos persistentes permitidos son los propios de preparar una release nueva bajo `/opt/sis-leg/releases/<SHA>` y los temporales/descargas controlados necesarios para ello.

Debe garantizar explícitamente que NO modifica:

- `/opt/sis-leg/current`;
- `/opt/sis-leg/target-release`;
- configuración institucional existente;
- systemd;
- Nginx;
- `/usr/local/bin`;
- wrappers de `/home/concejo/.local/bin`;
- sudoers/PolicyKit;
- `.desktop`;
- Legacy;
- logs históricos.

No debe activar ni reiniciar ningún servicio.

### 5. Idempotencia y fallas

- Si la release ya está preparada y el marcador es compatible, debe informar idempotencia sin reescribirla.
- Si existe un directorio parcial/incompatible, debe abortar y exigir inspección; no borrar ni reparar silenciosamente.
- Una falla de descarga/validación debe dejar sin promoción artefactos parciales.
- Una falla durante `preparar` debe preservar la semántica diagnóstica de la herramienta moderna y nunca tocar `current`/`target-release`.
- No implementar limpieza destructiva automática.

### 6. Modo de diagnóstico/plan

Debe existir una forma de validar conectividad, release objetivo y compatibilidad del bootstrap sin preparar ni escribir en `/opt/sis-leg`, utilizable en pruebas y en un gate productivo read-only previo.

### 7. Integración con WP-101B

La documentación de producción debe dejar un procedimiento inequívoco:

1. obtener el bootstrap desde una URL inmutable del commit/release aprobado;
2. verificar su SHA-256 exacto antes de ejecutarlo;
3. ejecutar primero su modo de diagnóstico/readiness;
4. sólo tras HUMAN_GATE productivo separado, preparar la release moderna;
5. detenerse después de preparar;
6. ejecutar luego `instalador_host.py plan` desde la release moderna en otro gate;
7. no instalar wrappers, no corregir sudoers/helper y no conmutar en el mismo turno de bootstrap.

El hash exacto del bootstrap que deberá usar producción se fija después del merge y publicación, nunca antes.

## Casos de prueba obligatorios

Agregar pruebas deterministas, sin red real ni filesystem productivo, que cubran al menos:

1. release válida completa → valida y delega en la herramienta moderna;
2. SHA/tag/target divergentes → fail-closed;
3. draft/prerelease o assets inesperados → fail-closed;
4. CI/job/tree/metadatos inconsistentes → fail-closed;
5. checksum incorrecto → fail-closed antes de ejecutar código extraído;
6. `release.json` inválido, traversal, symlink/hardlink/entrada especial o inventario inconsistente → fail-closed;
7. módulos de despliegue extraídos con hash distinto del inventario → no ejecutar;
8. release histórica con cuatro SPA no se usa para validar el manifest moderno;
9. bootstrap moderno acepta correctamente el contrato vigente de cinco SPA + manual;
10. preparación no modifica `current`, `target-release`, servicios, Nginx, wrappers ni configuración;
11. directorio parcial existente → aborta sin borrar;
12. release ya preparada compatible → idempotencia;
13. ausencia de cabeceras Authorization/Cookie/token;
14. temporales limpiados ante falla de transporte/validación;
15. ninguna regresión en el canal público normal ya usado por `actualizador_publico.py`.

## Fuera de alcance

- cualquier acceso o mutación de producción;
- instalar wrappers;
- modificar sudoers;
- modificar `/usr/local/bin/teclados-menu`;
- `.desktop`;
- cambiar servicios, Nginx o bridges;
- activar una release;
- cambiar `target-release`;
- corregir el hardening de privilegios/Legacy helper, que tendrá gate propio posterior;
- modificar la política de tres assets del canal público salvo que sea estrictamente necesario y aprobado por ORCHESTRATOR.

## Gates de integración

Antes del merge:

- CI candidata completa verde;
- revisión independiente 0 BLOQUEANTES / 0 IMPORTANTES;
- auditoría sustantiva ORCHESTRATOR `APROBADO_PARA_MERGE`;
- pruebas explícitas de todos los casos obligatorios;
- ningún acceso a producción.

Después del merge:

- CI post-merge verde sobre SHA exacto;
- publicación pública válida de la release funcional;
- recién entonces HUMAN_GATE para diseñar la preparación productiva con el bootstrap ya publicado.
