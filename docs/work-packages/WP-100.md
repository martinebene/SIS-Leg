# WP-100 — Actualizador público sin autenticación y evolución segura de configuración

## Objetivo

Eliminar del flujo permanente `Actualizar SIS-Leg` cualquier dependencia de autenticación GitHub en el host productivo, preservando las compuertas de seguridad ya validadas en WP-029 y dejando un canal público, determinista, verificable y auditable para obtener una release SIS-Leg correspondiente a un SHA exacto de `main`.

Este WP es **DEVELOPMENT ONLY**. No instala ni reemplaza scripts en el host productivo, no ejecuta actualización real, no cambia `/opt/sis-leg`, no modifica launchers `.desktop` y no autoriza cutover.

## Base canónica

Base funcional requerida al iniciar implementación:

`12b6ef432493ae381a891d60ed0db6b3140864e8`

Ese SHA contiene WP-099 integrado, incluida la SPA `zocalo` en el paquete productivo y en las validaciones de despliegue.

## Contexto que debe preservarse

La herramienta `deploy/herramienta_despliegue.py` ya implementa, entre otras defensas:

- SHA Git completo y estricto;
- sidecar SHA-256;
- validación de `release.json`;
- identidad `commit_sha` / `tree_sha`;
- inventario de archivos con tamaño y checksum;
- allowlist de contenido del tar;
- extracción segura;
- release inmutable preparada bajo SHA;
- cambio atómico de enlaces;
- preflight, validaciones de runtime y rollback.

`scripts/empaquetar_produccion.py` ya genera un paquete reproducible `sis-leg-<SHA>.tar.gz` y su sidecar, dejando deliberadamente fuera la configuración institucional local.

La CI actual genera y valida el paquete, pero lo publica como GitHub Actions artifact temporal. WP-029 validó operacionalmente el actualizador productivo que selecciona la CI exacta de `main` y descarga el artifact exacto de esa run. WP-100 debe conservar esos gates conceptuales, sustituyendo la dependencia de Actions artifact/autenticación por un canal público estable.

## Resultado funcional obligatorio

### 1. Canal público de release por SHA

Debe existir una forma pública, sin credenciales del consumidor, de obtener para un SHA exacto validado:

- `sis-leg-<SHA>.tar.gz`;
- `sis-leg-<SHA>.tar.gz.sha256`;
- metadatos suficientes para vincular inequívocamente publicación, commit, tree y CI que habilitó la publicación.

La solución preferida es una **GitHub Release pública e inmutable por SHA**, con tag determinista, por ejemplo `sis-leg-<SHA>`, publicada automáticamente sólo después de que la CI completa de `push` sobre `main` haya terminado con éxito.

Puede elegirse otra representación pública equivalente únicamente si ofrece la misma o mayor trazabilidad, inmutabilidad práctica y verificabilidad sin autenticación.

La publicación no debe depender de una operación manual rutinaria.

### 2. Publicación sólo después de CI completa verde

No alcanza con que el job `Empaquetado · release productiva` esté verde si el resto de la CI todavía no terminó.

El mecanismo de publicación debe exigir objetivamente:

- evento `push` sobre `main`;
- SHA exacto publicado;
- CI completa correspondiente a ese SHA terminada en `success`;
- job `Empaquetado · release productiva` de ese mismo SHA exitoso;
- paquete y sidecar generados/validados por el mecanismo canónico;
- ninguna publicación pública de una release candidata fallida o parcial.

Si la publicación se reintenta para un tag/SHA ya existente, debe ser idempotente o abortar de forma segura ante cualquier diferencia; nunca reemplazar silenciosamente assets de una release ya publicada con otros bytes.

### 3. Consumidor sin autenticación en producción

La lógica versionada que WP-101 pueda instalar posteriormente en producción debe poder ejecutar el flujo sin:

- `gh auth`;
- GitHub CLI logueado;
- PAT;
- `.github_token`;
- token en archivo, variable de entorno, keyring o URL;
- credenciales interactivas.

El host podrá realizar únicamente consultas/descargas públicas HTTPS del repositorio `martinebene/SIS-Leg`.

Es válido que GitHub Actions utilice su `GITHUB_TOKEN` efímero del lado servidor para publicar una release pública; la prohibición de credenciales aplica al **consumidor/updater del host**.

### 4. Selección determinista de la versión

No descargar un asset ambiguo denominado simplemente `latest`.

El flujo lógico del updater debe ser:

1. resolver el SHA completo actual de `main` mediante recurso público;
2. verificar que existe CI `push` exacta para ese SHA, completada con `success`;
3. verificar el job exacto `Empaquetado · release productiva` exitoso;
4. resolver la publicación pública vinculada inequívocamente a ese mismo SHA;
5. exigir nombres de assets exactos derivados del SHA;
6. descargar paquete y sidecar;
7. verificar sidecar SHA-256;
8. validar `release.json`, `commit_sha`, `tree_sha` e inventario mediante la herramienta oficial;
9. recién entonces considerar la release apta para `preparar`.

No mezclar información de distintas runs, SHAs, tags o publicaciones.

### 5. Extender, no duplicar, la herramienta de despliegue

La lógica reutilizable de consulta/descarga/verificación debe vivir en código versionado y testeable del Producto, preferentemente integrada o estrechamente acoplada a `deploy/herramienta_despliegue.py`.

No crear un segundo motor de validación de tar/manifest/checksum en paralelo. El downloader puede ocuparse de transporte y selección, pero la validez de la release debe terminar pasando por las defensas canónicas existentes.

La futura adaptación del wrapper productivo `actualizar-sisleg.sh` corresponde a WP-101/Human Gate, no a este WP.

### 6. Política para configuración local existente

La release sigue sin ser dueña de los valores institucionales locales. Debe preservarse byte-for-byte el principio vigente para:

- `config/system.toml`;
- `config/concejales.csv`;
- `config/apoyo-tecnico/mensajes.csv`;
- `config/bridge/devices.json`;
- cualquier recurso local equivalente ya existente.

Una actualización nunca debe copiar sobre esos archivos desde Git ni desde el paquete.

### 7. Incorporación de recursos nuevos de configuración

WP-100 debe definir un mecanismo explícito para el caso futuro en que una release necesite **un nuevo recurso local de configuración** que antes no existía.

Regla:

- un recurso nuevo puede inicializarse únicamente si está ausente;
- debe provenir de un default/example versionado y explícitamente declarado como bootstrap seguro;
- la creación debe ser atómica y con permisos/ownership previstos;
- jamás se reemplaza un recurso que ya exista;
- la operación debe quedar registrada/diagnosticable.

No basta con copiar indiscriminadamente `config/` ni ejecutar `preparar_config_local.py` durante una actualización.

### 8. Cambios de formato o migraciones

Si una release nueva requiere modificar el formato, semántica o schema de un archivo de configuración local existente, el updater **debe abortar antes de mutar** y explicar que se necesita una migración aprobada por HUMAN_GATE.

No se autoriza:

- migración automática silenciosa;
- completar claves dentro de un archivo local existente sin autorización;
- reescribir TOML/CSV/JSON conservando supuestamente valores;
- restaurar configuración desde Git;
- sustituir un archivo por un example actualizado.

El contrato de release/configuración debe permitir detectar esta incompatibilidad antes de activar una release.

### 9. Compatibilidad con WP-099

Toda release pública producida desde la base de WP-100 debe contener y validar las cinco SPA canónicas:

- Moderación;
- Recinto;
- Simulador;
- Apoyo Técnico;
- Zócalo.

No se acepta un mecanismo nuevo que omita `web/zocalo` o degrade las validaciones ya incorporadas por WP-099.

### 10. Fail-safe y rollback

WP-100 no debe debilitar la arquitectura validada en WP-029.

Ante error de red, rate limit, JSON inválido, ausencia de publicación, assets faltantes, asset duplicado/ambiguo, checksum incorrecto, SHA/tree incongruente, paquete truncado, formato no soportado o incompatibilidad de configuración:

- abortar con error accionable;
- no cambiar `current`;
- no cambiar `previous`;
- no cambiar `target-release`;
- no reiniciar servicios;
- no modificar configuración local;
- no dejar un artefacto parcial tratable como release válida.

La activación/rollback real de servicios sigue siendo responsabilidad de los mecanismos ya auditados y, para producción, queda fuera de este WP.

## Seguridad de transporte

- HTTPS únicamente para el canal GitHub público.
- No aceptar redirects hacia esquemas no HTTPS.
- Timeouts explícitos y tamaño máximo razonable de respuestas/descargas.
- Descarga a archivo temporal; promover sólo después de completar la transferencia y validaciones aplicables.
- No construir comandos shell con datos de GitHub.
- Validar estrictamente SHA, nombres de assets y URLs esperadas.
- No registrar secretos porque el consumidor no debe tener secretos.

## Tests obligatorios

Agregar/actualizar pruebas automatizadas que cubran al menos:

1. publicación pública sólo para `push main` con CI completa verde;
2. identidad exacta SHA/tag/assets;
3. intento de republicación idempotente y rechazo de colisión divergente;
4. resolución pública de `main` sin headers de autenticación;
5. consulta de CI/run/job exactos sin mezclar SHAs;
6. descarga pública de paquete + sidecar sin `gh` ni token;
7. checksum correcto e incorrecto;
8. `release.json` con commit/tree correctos e incorrectos;
9. asset ausente, duplicado, truncado o nombre inesperado;
10. error HTTP, timeout, rate limit y JSON inválido con falla segura;
11. preservación de archivos locales existentes;
12. creación add-only de un recurso nuevo ausente;
13. no sobrescritura de ese recurso si ya existe;
14. detección de cambio de formato/schema y aborto antes de mutación;
15. presencia obligatoria de `web/zocalo` en release;
16. regresión completa de `tests/test_empaquetado_despliegue.py`;
17. ausencia de dependencias operativas en `gh auth`, PAT o `.github_token` para el consumidor.

Los tests no deben requerir acceso real a producción. Las fronteras HTTP, filesystem y procesos deben ser inyectables/mokeables cuando corresponda.

## Validaciones de candidato

Antes del handoff del IMPLEMENTER:

- unit/integration tests relevantes nuevos;
- `tests/test_empaquetado_despliegue.py` completo;
- linters/format/typecheck aplicables;
- validación de workflows si existe mecanismo en el repo;
- build y empaquetado productivo reproducible;
- suite CI completa sobre candidate SHA exacto.

No relajar tests existentes para obtener verde.

## Revisión independiente

REVIEWER debe comprobar sobre el SHA exacto:

- que no exista dependencia de autenticación del lado consumidor;
- que la publicación pública sólo ocurra después de CI completa verde;
- que release/tag/assets estén atados a un SHA único;
- que no pueda mezclarse metadata o assets de SHAs distintos;
- que checksum + manifest + tree continúen siendo gates reales;
- que la configuración existente permanezca intocable;
- que recursos nuevos sean estrictamente add-only;
- que una migración real aborte y requiera HUMAN_GATE;
- que `zocalo` siga incluido;
- que no se toque producción, `.desktop` ni wrappers instalados;
- que WP-101 no haya comenzado.

## Fuera de alcance

- ejecutar `Actualizar SIS-Leg` en producción;
- cambiar `/home/concejo/.local/bin/actualizar-sisleg.sh`;
- cambiar `/usr/local/bin/*`;
- cambiar `/opt/sis-leg/*`;
- cambiar systemd/Nginx/sudoers del host;
- modificar o regenerar launchers `.desktop`;
- activar SIS-Leg o Legacy;
- migrar configuración real;
- borrar releases/logs;
- WP-101/cutover/adaptación productiva.

## Gate de cierre

WP-100 sólo vuelve al ORCHESTRATOR cuando:

- PR de Producto abierta contra `main`;
- candidate SHA exacto y tree SHA fijados;
- CI completa del candidato verde;
- REVIEWER independiente cubrió exactamente ese candidate SHA;
- 0 BLOQUEANTES;
- 0 IMPORTANTES;
- producción no fue tocada;
- `.desktop` no fue tocado;
- WP-101 no fue iniciado.

El merge queda reservado al ORCHESTRATOR después de su auditoría pre-merge.
