# WP-030 - Incorporar lanzador Orca y soporte multi-entorno para iniciar WPs

## Estado documental

`APROBADO`

## Objetivo

Incorporar un lanzador específico para Orca que conserve las validaciones de seguridad/documentación del lanzador actual y delegue en la CLI de Orca la creación del worktree y el lanzamiento del agente, manteniendo a la vez el lanzador genérico existente para otros entornos.

## Resultado esperado

Al integrar este WP, el operador podrá iniciar un WP autorizado desde Orca mediante un comando versionado del repositorio que:

- valide `main`, autorización documental, agente y dependencias;
- compruebe que Orca está disponible y preparado;
- cree el worktree desde `origin/main` usando `orca worktree create`;
- lance el agente dentro de una terminal administrada por Orca;
- verifique la respuesta JSON de Orca y falle de forma conservadora ante inconsistencias;
- preserve el comportamiento y utilidad del lanzador genérico `scripts/iniciar_wp.py` para terminal/SSH/Warp/u otros entornos.

## Dependencias

- WP-001 integrado.
- DEC-002 aprobada.
- DEC-004 aprobada.
- DEC-005 aprobada.
- DEC-007 aprobada.

Este WP es el bootstrap permitido por DEC-007: como implementa el propio lanzador Orca, puede iniciarse manualmente mediante `orca worktree create` después de realizar las mismas validaciones previas exigidas por DEC-007.

## Alcance

### Lanzador Orca

Crear:

```text
scripts/iniciar_wp_orca.py
```

El comando conceptual será:

```text
uv run python scripts/iniciar_wp_orca.py NNN agente
```

Debe aceptar nombres operativos de agentes apropiados para el entorno actual, al menos:

- `antigravity`;
- `opencode`;
- `codex`;
- `claude` cuando su CLI/integración esté disponible.

El detalle interno de mapeo entre nombre operativo, identificador Orca y ejecutable local puede resolverse dentro del WP siempre que sea explícito, testeable y no confunda agente con modelo efectivo.

### Validaciones compartidas

El lanzador Orca debe aplicar las mismas puertas que el lanzador genérico:

1. ejecutarse desde el checkout coordinador correcto;
2. exigir rama `main`;
3. exigir árbol limpio;
4. ejecutar `git fetch --prune origin`;
5. actualizar `main` solo mediante fast-forward;
6. verificar `HEAD == origin/main`;
7. exigir `WP-NNN.md` existente y `APROBADO`;
8. exigir WP `EN_CURSO` en PLAN;
9. exigir coincidencia con el agente asignado;
10. exigir dependencias `INTEGRADO`;
11. detectar conflictos de rama/worktree antes de crear trabajo nuevo.

Debe reutilizar/factorizar la lógica común con `scripts/iniciar_wp.py` cuando hacerlo reduzca duplicación sin cambiar su comportamiento observable. La organización concreta de helpers pertenece a la autonomía técnica del implementador.

### Integración con Orca

Antes de crear el worktree debe comprobar mediante la CLI de Orca, con salida JSON cuando corresponda:

- runtime alcanzable y estado `ready`;
- repositorio coordinador registrado en Orca;
- condiciones necesarias para lanzar el agente solicitado.

La creación normal debe ser equivalente funcionalmente a:

```text
orca worktree create
  --repo path:<checkout-coordinador>
  --name wp/NNN-descripcion
  --base-branch origin/main
  --no-parent
  --agent <agente-orca>
  --prompt <prompt-inicial>
  --setup run
  --activate
  --json
```

No se exige copiar literalmente ese orden de argumentos, pero sí preservar sus garantías.

El prompt inicial debe ser breve y remitir al agente a `AGENTS.md`, `WP-030.md` o al WP solicitado y sus fuentes canónicas. No debe duplicar ni redefinir el contrato del WP.

### Verificación posterior

El lanzador debe interpretar la respuesta JSON y verificar, como mínimo:

- operación Orca reportada como exitosa;
- worktree registrado;
- `head` igual al SHA de `origin/main` validado antes de la creación;
- base equivalente a `origin/main`;
- sin padre Orca para un WP independiente;
- evidencia suficiente de que el agente fue iniciado cuando la versión de Orca exponga el handle correspondiente.

Si el resultado es parcial o inconsistente, debe informar el problema y conservar el estado para diagnóstico. No debe ejecutar limpieza destructiva automática sobre un worktree cuya creación sea incierta.

### Lanzador genérico

`scripts/iniciar_wp.py` debe seguir funcionando para el flujo genérico.

Puede adaptarse para compartir validaciones y para reconocer Antigravity/AGY de forma coherente, incluyendo el mapeo al ejecutable `agy` cuando corresponda, pero no debe obligar a tener Orca instalado ni cambiar a Orca como dependencia del flujo genérico.

### Documentación de uso

Actualizar la documentación operativa necesaria para que quede claro:

- cómo elegir entre lanzador Orca y genérico;
- que el orquestador debe conocer/preguntar el entorno actual;
- que Orca administra su propio path y rama nativa;
- cómo se limpia un WP Orca después del merge;
- que la rama nativa de Orca admitida por DEC-007 no debe renombrarse por detrás;
- que el modelo efectivo del agente/revisor se registra en la PR cuando sea relevante.

- Elegir o cambiar modelos de IA mediante lógica del producto.

- Eliminar automáticamente worktrees o ramas ante un fallo incierto de creación.
- Fijar una versión permanente de Orca o de un modelo concreto en la arquitectura del proyecto.

No deben modificarse aplicaciones backend/frontend, bridge, configuración funcional ni contratos de producto.

## Criterios de aceptación

1. El lanzador genérico mantiene sus validaciones y comandos existentes para los agentes ya soportados.
2. El lanzador Orca rechaza iniciar trabajo si `main` no está limpio o no puede quedar idéntico a `origin/main` mediante fast-forward.
3. Rechaza un WP inexistente, no `APROBADO`, no `EN_CURSO`, asignado a otro agente o con dependencias no integradas.
4. Rechaza o informa claramente un runtime Orca no disponible/no `ready`.
5. Rechaza o informa claramente que el repo coordinador no está registrado en Orca.
6. Para un caso válido, construye una invocación de Orca equivalente a `worktree create` desde `origin/main`, sin padre, con agente, prompt, setup y salida JSON.
7. Verifica que el SHA devuelto por Orca coincide con el `origin/main` previamente validado.
8. Acepta la convención de rama nativa Orca definida por DEC-007 sin intentar renombrarla por detrás.
9. Ante JSON inválido, respuesta incompleta o resultado inconsistente, falla con mensaje claro y no ejecuta borrado destructivo automático.
10. El flujo Orca no hace push, no crea PR, no integra y no modifica documentación canónica por sí mismo.
11. El flujo genérico no adquiere dependencia obligatoria de Orca.
12. Antigravity/AGY puede representarse como agente operativo sin confundir el ID Orca `antigravity` con el ejecutable genérico `agy`.
13. La documentación explica con comandos simples qué lanzador usar según el entorno.
14. El código propio nuevo respeta nomenclatura en español según DEC-001 y contiene documentación/comentarios pedagógicos suficientes.

## Pruebas obligatorias

Agregar/actualizar pruebas automatizadas que cubran como mínimo:

- validación de checkout/rama/árbol limpio;
- sincronización fast-forward y comparación con `origin/main`;
- WP no aprobado;
- PLAN no `EN_CURSO`;
- agente distinto del asignado;
- dependencia no integrada;
- runtime Orca no ready;
- repo Orca inexistente/no registrado;
- construcción correcta de la orden `orca worktree create`;
- parsing de respuesta JSON válida;
- rechazo de SHA/base/lineage inesperados;
- respuesta JSON inválida o parcial sin limpieza destructiva;
- mapeo de Antigravity/AGY;
- no regresión del lanzador genérico.

Las pruebas no deben requerir un runtime Orca real en CI: las invocaciones externas deben poder aislarse/simularse de forma determinista.

Ejecutar al menos los checks Python aplicables del repositorio:

```text
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

Y cualquier otro check de CI que el diff haga aplicable.

## Invariantes y restricciones

- `main` continúa siendo la única rama estable de integración.
- Un WP tiene un único implementador y un worktree propio.
- La revisión sigue siendo independiente y secuencial.
- El lanzador no tiene autoridad documental.
- No usar rebase ni force-push como parte del inicio normal.
- No introducir una dependencia Python externa si la biblioteca estándar + subprocess/JSON son suficientes.
- No asumir que el path físico de un worktree Orca será `/workspace/SIS-Leg-wpNNN`; debe utilizarse la información devuelta por Orca.
- No exigir la forma literal `wp/NNN-...` a la rama Git creada nativamente por Orca; rige DEC-007.
- No ocultar errores de Orca mediante fallbacks que creen un worktree Git externo silenciosamente.
- DEC-001, DEC-003, DEC-004, DEC-005 y DEC-007 son obligatorias para este alcance.

## Herramientas MCP y documentación técnica externa

Cuando sea necesario confirmar opciones o JSON de una versión de Orca:

1. inspeccionar primero `orca ... --help` en el entorno disponible;
2. si sigue habiendo ambigüedad, consultar documentación primaria vigente de Orca aplicando DEC-003;
3. registrar en la PR cualquier diferencia relevante entre la documentación y la versión observada;
4. no copiar secretos ni configuración personal de Orca al repositorio.

## Consulta a producción si existe ambigüedad funcional/UX/visual

No corresponde como fuente técnica para este WP. El sistema histórico de votación no debe usarse para decidir comportamiento del lanzador Orca.
