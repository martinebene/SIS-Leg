# WP-011 - Cálculo y aplicación del resultado de una votación

## Estado documental

`APROBADO`

## Objetivo

Calcular y aplicar automáticamente el resultado institucional de una votación que acaba de cerrar normalmente por completitud, utilizando exclusivamente los votos ordinarios registrados y los datos constitutivos congelados al abrir (`tipo_mayoria`, `factor` y `base`), sin introducir todavía finalización manual, pérdida de quórum resolutiva ni desempate presidencial.

Este WP concentra el cálculo tanto de mayoría `SIMPLE` como `ESPECIAL` conforme a DEC-009 y DEC-010.

## Resultado esperado

Al quedar completa una votación `EN_CURSO` con quórum, el mismo flujo serializado que hoy cierra la recepción debe encadenar inmediatamente:

```text
EN_CURSO + resultado=None
    -> CERRADA + resultado=None
    -> CERRADA + resultado=APROBADA|RECHAZADA|EMPATADA
```

sin liberar el único `EjecutorMutaciones` entre el cierre y el cálculo.

El comportamiento integrado esperado es:

- `SIMPLE`:
  - positivos > negativos -> `APROBADA`;
  - positivos < negativos -> `RECHAZADA`;
  - positivos = negativos -> `EMPATADA`;
  - las abstenciones no integran la comparación;
- `ESPECIAL`:
  - calcula el denominador según `VOTOS_COMPUTABLES`, `PRESENTES` o `CUERPO`;
  - aprueba si el cociente efectivo es `>= factor`;
  - rechaza si es `< factor`;
  - `VOTOS_COMPUTABLES = 0` por existir solo abstenciones produce `RECHAZADA` sin división por cero;
  - nunca produce `EMPATADA`;
- `APROBADA` y `RECHAZADA` son resultados finales y liberan `EstadoOperativo.votacion_activa` después de persistir y aplicar el resultado;
- `EMPATADA` es transitorio, permanece sobre la misma instancia `Votacion`, conserva `estado=CERRADA`, continúa en `votacion_activa` y bloquea nuevas aperturas;
- la misma instancia permanece siempre en el historial ordenado de `Sesion`;
- cada resultado se registra institucionalmente antes de mutar el resultado funcional;
- no existe una ventana concurrente observable en la que otra operación pueda tratar el cierre normal como resuelto antes del cálculo o intercalarse entre cierre y resultado.

## Dependencias

- WP-010 `INTEGRADO`: recepción de voto ordinario, unicidad, irreversibilidad, completitud y autocierre normal ya disponibles.

- DEC-010 `APROBADA`: separación entre estado de recepción y resultado, empate transitorio y liberación de votación pendiente.

## Alcance

### 1. Aplicación evolutiva de resultado sobre `Votacion`

La entidad debe permitir una única transición ordinaria desde:

```text
estado = CERRADA
resultado = None
```

hacia exactamente uno de:

```text
estado = CERRADA
resultado = APROBADA
```

```text
estado = CERRADA
resultado = RECHAZADA
```

```text
estado = CERRADA
resultado = EMPATADA
```

La transición debe estar encapsulada y proteger invariantes incluso ante un uso incorrecto interno.

Como mínimo debe impedir:

- asignar resultado mientras la recepción siga `EN_CURSO`;
- calcular/aplicar por segunda vez una votación que ya tiene resultado;
- asignar `INCONCLUSA` desde el flujo ordinario de este WP;
- transformar una mayoría `ESPECIAL` en `EMPATADA`;
- alterar fecha/hora de cierre, votos o datos constitutivos al aplicar resultado.

`ResultadoVotacion.INCONCLUSA` continúa existiendo en el vocabulario, pero este WP no debe producirlo.

### 2. Conteo ordinario autoritativo

El cálculo utiliza únicamente `Votacion.votos_ordinarios` de la misma instancia autoritativa.

Debe obtener como mínimo:

```text
positivos
negativos
abstenciones
votos_emitidos = positivos + negativos + abstenciones
votos_computables = positivos + negativos
```

No debe reconstruir votos desde presencia dinámica, frontend, eventos CSV ni otra colección paralela.

La presencia actual después del cierre no participa del cálculo de resultado ordinario.

### 3. Mayoría SIMPLE

Para `tipo_mayoria = SIMPLE`:

```text
base canónica = VOTOS_COMPUTABLES
factor canónico = 0
```

El resultado se determina exclusivamente por:

```text
positivos > negativos -> APROBADA
positivos < negativos -> RECHAZADA
positivos = negativos -> EMPATADA
```

Las abstenciones:

- son votos ordinarios válidos;
- permanecen registradas;
- no cuentan como positivas ni negativas;
- no rompen un empate entre positivos y negativos.

Ejemplos obligatorios:

```text
4 POSITIVO, 3 NEGATIVO, 3 ABSTENCION -> APROBADA
3 POSITIVO, 4 NEGATIVO, 3 ABSTENCION -> RECHAZADA
3 POSITIVO, 3 NEGATIVO, 4 ABSTENCION -> EMPATADA
0 POSITIVO, 0 NEGATIVO, N ABSTENCION -> EMPATADA
```

El último caso es válido únicamente cuando la votación alcanzó cierre normal con quórum; no debe reinterpretarse como `INCONCLUSA` en este WP.

### 4. Mayoría ESPECIAL sobre `VOTOS_COMPUTABLES`

Para:

```text
tipo_mayoria = ESPECIAL
base = VOTOS_COMPUTABLES
```

el denominador es:

```text
positivos + negativos
```

Si el denominador es mayor que cero:

```text
positivos / denominador >= factor -> APROBADA
positivos / denominador <  factor -> RECHAZADA
```

Si el denominador es cero porque todos los votos ordinarios fueron abstenciones:

```text
resultado = RECHAZADA
```

sin ejecutar una división por cero.

Las abstenciones no integran ese denominador.

### 5. Mayoría ESPECIAL sobre `PRESENTES`

Para:

```text
tipo_mayoria = ESPECIAL
base = PRESENTES
```

`PRESENTES` conserva el significado institucional cerrado en DEC-009: personas que lograron emitir voto ordinario en esa votación.

El denominador técnico es:

```text
positivos + negativos + abstenciones
```

Por lo tanto:

- un concejal que votó y luego se ausentó continúa integrando el denominador;
- un concejal que ingresó durante `EN_CURSO` y votó también lo integra;
- cambios de presencia posteriores al cierre no recalculan el resultado;
- no se toma una fotografía de `Preparacion.presencias` para calcular esta base.

Resultado:

```text
positivos / votos_emitidos >= factor -> APROBADA
positivos / votos_emitidos <  factor -> RECHAZADA
```

### 6. Mayoría ESPECIAL sobre `CUERPO`

Para:

```text
tipo_mayoria = ESPECIAL
base = CUERPO
```

el denominador es la cantidad total de concejales del padrón/configuración congelados para la sesión.

No se utiliza:

- cantidad de presentes actual;
- cantidad de votos emitidos como denominador;
- una unidad adicional por Presidencia.

Resultado:

```text
positivos / cantidad_total_cuerpo >= factor -> APROBADA
positivos / cantidad_total_cuerpo <  factor -> RECHAZADA
```

El cálculo debe usar el mismo contexto congelado de la sesión/votación, sin releer archivos de configuración desde disco.

### 7. Semántica numérica del factor especial

`factor` conserva exactamente el significado fijado en DEC-009: es el umbral numérico real finito normalizado y congelado al abrir.

La comparación es estrictamente:

```text
cociente >= factor
```

No se agrega silenciosamente:

- redondeo a porcentaje;
- tolerancia epsilon;
- `math.isclose`;
- truncamiento;
- conversión automática a una fracción institucional distinta del número recibido.

Por tanto, valores decimales distintos representan umbrales distintos aunque sean aproximaciones humanas cercanas.

Las pruebas deben distinguir expresamente, por ejemplo, entre:

- un factor cuyo valor efectivo es `2 / 3`, para el cual `8/12` alcanza el umbral;
- un factor `0.6666666667`, ligeramente mayor que `2/3`, para el cual `8/12` no alcanza el umbral.

Este criterio mantiene la semántica canónica `>= factor` y evita que la implementación introduzca una política de redondeo no documentada.

### 8. Encadenamiento obligatorio al autocierre normal

WP-011 no crea un comando manual de “calcular resultado”.

Cuando el flujo ya serializado detecta completitud con quórum:

1. persiste `VOTACION_CERRADA_COMPLETITUD`;
2. muta la misma instancia a `estado=CERRADA`, conserva `resultado=None` y fija `fecha_hora_cierre`;
3. calcula el resultado ordinario sin liberar el `EjecutorMutaciones`;
4. persiste el evento institucional del resultado;
5. aplica el resultado sobre la misma instancia;
6. si el resultado es final (`APROBADA` o `RECHAZADA`), limpia `EstadoOperativo.votacion_activa`;
7. si el resultado es `EMPATADA`, conserva esa misma instancia en `EstadoOperativo.votacion_activa`.

No debe existir entre 2 y 7 un `await`, una nueva adquisición del mismo lock ni otra ventana que permita intercalar una operación concurrente.

El cálculo debe quedar reutilizable de manera razonable por el diseño posterior, pero no debe abrirse un endpoint ni una capacidad pública que permita recalcular arbitrariamente resultados ya aplicados.

### 9. Resultado final y liberación de `votacion_activa`

Después de auditar y aplicar:

```text
APROBADA
```

o

```text
RECHAZADA
```

la misma instancia permanece en `Sesion.votaciones`, pero:

```text
EstadoOperativo.votacion_activa = None
```

La liberación ocurre dentro de la misma sección crítica que aplicó el resultado.

Una operación concurrente que esperaba el serializador puede, después de terminado ese flujo, observar que ya no existe votación pendiente y evaluar una nueva apertura conforme a sus precondiciones normales.

No se borra ni duplica la entidad histórica.

### 10. `EMPATADA` transitorio

Solo una mayoría `SIMPLE` puede producir:

```text
resultado = EMPATADA
```

En ese caso:

- `estado` permanece `CERRADA`;
- `fecha_hora_cierre` permanece la del cierre normal;
- los votos no cambian;
- la misma instancia permanece en el historial;
- la misma instancia permanece en `EstadoOperativo.votacion_activa`;
- una nueva apertura continúa rechazándose como `VOTACION_PENDIENTE`;
- no se agrega todavía voto presidencial;
- no se resuelve el empate en este WP.

Una mayoría `ESPECIAL` nunca debe producir `EMPATADA`, incluso si el cociente coincide exactamente con el factor: la igualdad de umbral aprueba.

### 11. Auditoría del resultado

El resultado ordinario es un hecho institucional L3 y debe persistirse antes de modificar `Votacion.resultado`.

Como mínimo deben distinguirse mediante `event_code` estable:

- resultado ordinario final `APROBADA`/`RECHAZADA`;
- empate ordinario `EMPATADA`.

El código concreto puede reutilizar una categoría estable para resultados finales si el `message` identifica inequívocamente `APROBADA` o `RECHAZADA`, pero `EMPATADA` debe ser distinguible como evento institucional específico conforme a DEC-010.

El mensaje humano de resultado debe permitir reconstruir como mínimo:

- número e id de votación;
- `tipo_mayoria`;
- cantidad de positivos;
- cantidad de negativos;
- cantidad de abstenciones;
- resultado aplicado.

Para `ESPECIAL` debe incluir además:

- `base`;
- denominador efectivo;
- `factor`;
- cociente efectivo cuando el denominador sea mayor que cero;
- indicación explícita del caso sin división cuando `VOTOS_COMPUTABLES=0`.

Para `SIMPLE` debe quedar claro que las abstenciones fueron excluidas de la comparación.

### 12. Fallo cerrado entre cierre y resultado

El cierre y el resultado son hechos institucionales separados.

Si el evento de cierre falla antes de cerrar:

- se conserva la semántica ya integrada: no se marca `CERRADA`;
- no se calcula ni aplica resultado.

Si el cierre ya fue auditado y aplicado, pero falla la persistencia del evento de resultado:

- NO se revierte el cierre ya institucionalizado;
- la votación permanece `CERRADA`;
- `resultado` permanece `None`;
- `votacion_activa` permanece apuntando a esa misma instancia;
- no se publica `APROBADA`, `RECHAZADA` ni `EMPATADA` sin su evento persistido;
- el writer continúa en fallo cerrado;
- la operación externa no debe informarse como éxito técnico si la secuencia obligatoria no pudo completarse.

El estado funcional debe coincidir con el último hecho institucional cuya persistencia quedó garantizada.

### 13. Concurrencia

Todo el encadenamiento cierre -> cálculo -> auditoría de resultado -> aplicación -> liberación/retención debe ejecutar bajo el único `EjecutorMutaciones` ya existente.

No se permiten:

- locks secundarios;
- otro `EjecutorMutaciones`;
- colas paralelas;
- tareas background para calcular resultado;
- publicación diferida del resultado fuera de la sección crítica.

Casos que deben quedar deterministas:

- el último voto que completa puede cerrar y resolver antes de que entre otra pulsación;
- un cambio de presencia que completa puede cerrar y resolver antes de que entre otra operación;
- tras resultado final, una apertura concurrente posterior ve `votacion_activa=None`;
- tras `EMPATADA`, una apertura concurrente posterior ve la votación pendiente y se rechaza;
- si falla la auditoría de resultado, ninguna operación posterior puede observar un resultado ficticio aplicado.

### 14. Contrato HTTP existente

Este WP no agrega un endpoint de cálculo ni un endpoint de voto desde Moderación.

`POST /api/v1/entradas/tecla` continúa siendo el único ingreso de voto ordinario.

La variante `VOTO` puede continuar informando como mínimo:

- aceptación;
- concejal;
- valor ordinario;
- `estado_recepcion`.

No es requisito de este WP agregar el resultado institucional al body de esa respuesta. La fuente de verdad es la entidad backend y las proyecciones/snapshots serán responsabilidad de sus alcances propietarios.

Los contratos de apertura existentes continúan sin cambios.

## Criterios de aceptación

1. El cálculo ordinario solo se ejecuta para una votación `CERRADA` con `resultado=None` proveniente del cierre normal por completitud.
2. El cálculo queda encadenado al autocierre sin liberar ni readquirir el `EjecutorMutaciones`.
3. La misma instancia `Votacion` es la que se cierra, calcula, audita, recibe resultado y permanece en el historial.
4. `SIMPLE` con positivos > negativos produce `APROBADA`.
5. `SIMPLE` con positivos < negativos produce `RECHAZADA`.
6. `SIMPLE` con positivos = negativos produce `EMPATADA`.
7. Las abstenciones no modifican la comparación SIMPLE.
8. Solo abstenciones en una SIMPLE cerrada normalmente producen `EMPATADA`.
9. `ESPECIAL/VOTOS_COMPUTABLES` usa positivos + negativos como denominador.
10. `ESPECIAL/VOTOS_COMPUTABLES` con denominador cero produce `RECHAZADA` sin excepción matemática.
11. `ESPECIAL/PRESENTES` usa todos los votos ordinarios emitidos, incluidas abstenciones.
12. `ESPECIAL/PRESENTES` conserva en el denominador a quien votó y luego se ausentó.
13. `ESPECIAL/PRESENTES` incluye a quien se incorporó durante `EN_CURSO` y alcanzó a votar.
14. `ESPECIAL/CUERPO` usa el total del padrón congelado y no la presencia dinámica.
15. Presidencia no incrementa el denominador `CUERPO`.
16. Una ESPECIAL aprueba al alcanzar exactamente el factor.
17. Una ESPECIAL rechaza cuando el cociente queda por debajo del factor.
18. Una ESPECIAL nunca produce `EMPATADA`.
19. No se introduce redondeo/tolerancia implícita: se compara con el factor numérico efectivamente congelado.
20. El caso `8/12` con factor efectivo `2/3` aprueba.
21. El caso `8/12` con factor `0.6666666667` rechaza.
22. `APROBADA` queda `CERRADA`, conserva fecha de cierre y libera `votacion_activa`.
23. `RECHAZADA` queda `CERRADA`, conserva fecha de cierre y libera `votacion_activa`.
24. `EMPATADA` queda `CERRADA`, conserva fecha de cierre y permanece como `votacion_activa`.
25. Las tres transiciones conservan votos y datos constitutivos inmutables.
26. No existe operación pública para recalcular un resultado ya aplicado.
27. El resultado L3 se persiste antes de mutar `resultado`.
28. `EMPATADA` tiene un evento institucional distinguible del resultado final ordinario.
29. El mensaje de resultado contiene los conteos necesarios para reconstruir la decisión.
30. Un resultado ESPECIAL registra base, denominador, factor y cociente/caso cero.
31. Si falla la auditoría de resultado después de un cierre exitoso, queda `CERRADA + resultado=None`, continúa pendiente y no se revierte el cierre.
32. Un resultado final solo limpia `votacion_activa` después de persistir su auditoría y aplicar el resultado.
33. Un empate nunca limpia `votacion_activa`.
34. Una apertura posterior a resultado final puede ser evaluada normalmente una vez adquirido el serializador.
35. Una apertura posterior a `EMPATADA` sigue rechazándose como `VOTACION_PENDIENTE`.
36. No se crea un segundo lock, ejecutor, cola ni worker de cálculo.
37. Teclas `1/2/3`, presencia `9` y test `8` conservan los contratos ya integrados.
38. El flujo no produce `INCONCLUSA`.
39. El flujo no implementa desempate presidencial.
40. El body de `POST /api/v1/entradas/tecla` no adquiere campos de identidad/resultados aportados por el cliente.
41. El código propio nuevo respeta nomenclatura en español según DEC-001.
42. Clases, funciones y flujos no triviales quedan documentados/comentados de manera pedagógica.
43. El documento y la implementación respetan DEC-003 y DEC-007 cuando correspondan.
44. El documento conserva el formato parseable exigido por `docs/implementation/FORMATO_WP_LANZADORES.md`.

## Pruebas obligatorias

Agregar o ajustar pruebas versionadas que cubran, como mínimo:

### SIMPLE

- aprobación con positivos > negativos;
- rechazo con positivos < negativos;
- empate con positivos = negativos;
- empate con abstenciones presentes;
- solo abstenciones -> `EMPATADA` después de cierre normal;
- conservación de votos, estado `CERRADA` y fecha de cierre;
- liberación de `votacion_activa` para APROBADA/RECHAZADA;
- retención de `votacion_activa` para EMPATADA.

### ESPECIAL `VOTOS_COMPUTABLES`

- aprobación por encima del factor;
- aprobación exactamente en el factor;
- rechazo por debajo del factor;
- abstenciones excluidas del denominador;
- solo abstenciones -> `RECHAZADA` sin división por cero.

### ESPECIAL `PRESENTES`

- ejemplo canónico 6 positivos, 3 negativos, 1 abstención, factor 0.6 -> `APROBADA`;
- igualdad exacta del cociente y factor -> `APROBADA`;
- rechazo por debajo;
- abstención incluida en denominador;
- votante que luego se ausenta continúa integrando denominador;
- concejal que ingresa durante `EN_CURSO` y vota integra denominador.

### ESPECIAL `CUERPO`

- denominador igual al total del padrón congelado;
- presencia dinámica inferior al cuerpo no cambia denominador;
- Presidencia no agrega una unidad;
- `8/12` con factor efectivo `2/3` -> `APROBADA`;
- `8/12` con factor `0.6666666667` -> `RECHAZADA`;
- resultado por debajo del factor -> `RECHAZADA`.

### Auditoría y fallo cerrado

- cierre L3 precede al resultado L3;
- resultado L3 precede a la mutación de `resultado`;
- evento final APROBADA/RECHAZADA contiene conteos y parámetros aplicables;
- evento EMPATADA es distinguible;
- fallo al persistir resultado después de cierre conserva `CERRADA + None` y la referencia activa;
- no se borra el cierre ya persistido/aplicado;
- writer permanece en fallo cerrado y la operación externa no informa éxito técnico.

### Concurrencia

- último voto que completa produce cierre + resultado en una sola adquisición lógica del serializador;
- cambio de presencia que completa produce cierre + resultado en la misma sección crítica;
- apertura concurrente posterior a resultado final observa `votacion_activa=None`;
- apertura concurrente posterior a EMPATADA se rechaza;
- no existe observación intermedia por otra mutación entre `CERRADA+None` y resultado durante un flujo exitoso.

### Regresiones

- apertura y datos constitutivos siguen inmutables;
- doble voto continúa rechazado;
- voto ausente continúa rechazado;
- teclas 8 y 9 conservan comportamiento;
- tecla 7 continúa fuera del alcance funcional vigente;
- cierre de sesión continúa bloqueado mientras exista votación pendiente y no se amplía incidentalmente;
- API/OpenAPI existente continúa válida;
- ninguna prueba introduce finalización manual, `INCONCLUSA` o desempate como comportamiento de este WP.

## Invariantes y restricciones

- Mantener un único proceso/worker productivo y un único `EjecutorMutaciones` como autoridad de orden.
- No introducir locks secundarios ni serialización paralela.
- Mantener una única instancia `Votacion` compartida por historial y estado activo mientras corresponda.
- No modificar votos ordinarios ya aceptados.
- No recalcular una votación después de aplicar un resultado ordinario.
- No usar presencia dinámica como base `PRESENTES` de mayoría especial.
- No sumar Presidencia al padrón/cuerpo.
- No inferir `tipo_mayoria` desde `factor`.
- No convertir `factor=0` en ESPECIAL ni una ESPECIAL en SIMPLE.
