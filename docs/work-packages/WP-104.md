# WP-104 — Canal público compatible con avances documentales de `main`

## Estado y autoridad

Corrección exclusivamente de desarrollo detectada durante el inventario productivo WP-101B I001.

**No autoriza ninguna mutación del host productivo.** WP-101B queda suspendido antes de su primera escritura hasta que este WP quede integrado, revisado, con CI post-merge verde y publicación pública válida.

## Problema demostrado

El diseño actual contiene dos decisiones correctas por separado pero incompatibles entre sí:

1. `CI` exime deliberadamente los pushes a `main` compuestos únicamente por documentación (`docs/**` / `*.md`). Esos pushes no generan CI productiva ni publicación pública.
2. `deploy/actualizador_publico.py::resolver_sha_main()` trata el SHA exacto de la cabeza de `main` como única versión candidata y luego exige una release pública de ese SHA.

Estado observado el 2026-09-14:

- Product `main`: `6a7cacb49cc57e3e0827f5d0b06bafc75fdb5e68`;
- ese commit sólo modifica `docs/implementation/PLAN.md` y, por diseño, no tiene run de CI ni release;
- última release pública productiva: `30b60eb6467ebd5dd5ee125dd9ce6e137ba9316b`, merge funcional de WP-103 con CI post-merge verde y publicación pública completa.

Consecuencia: el actualizador público versionado por WP-100/WP-101A falla cerrado intentando encontrar una publicación de un commit documental que nunca debe publicarse.

## Objetivo

Separar formalmente:

- **HEAD de `main`**: cabeza de gobernanza/desarrollo del repositorio;
- **release productiva vigente del canal público**: última publicación pública válida cuyo commit está demostrado como ancestro de la cabeza actual de `main`.

Un avance exclusivamente documental de `main` no debe crear una release nueva ni debe inutilizar el actualizador.

## Semántica requerida

### 1. Resolver el candidato desplegable

El consumidor público debe:

1. resolver el SHA exacto actual de `main` mediante API pública;
2. obtener la release pública `latest` no draft/no prerelease del repositorio;
3. exigir tag determinista `sis-leg-<SHA>` y `target_commitish` coherente con ese SHA;
4. demostrar mediante API pública de comparación Git que el commit publicado es ancestro de la cabeza actual de `main` —o idéntico a ella—; no alcanza con fechas, orden de releases ni prefijos de SHA;
5. validar la publicación, sus tres assets, metadatos, árbol Git, run/attempt histórico de CI y job de empaquetado exactamente con las garantías vigentes de WP-100;
6. devolver explícitamente tanto `main_head_sha` como `release_sha`, sin confundirlos.

Si la release `latest` no puede demostrarse como ancestro de `main`, el canal debe **fallar cerrado**. No buscar silenciosamente una release más vieja para ocultar una divergencia de gobernanza.

### 2. No debilitar el canal

Se conserva:

- cero autenticación en el consumidor;
- HTTPS y hosts permitidos;
- tag por SHA;
- tres assets exactos;
- checksum SHA-256;
- `release.json` y árbol Git;
- intento histórico exacto de CI;
- workflow `CI`, evento `push`, rama `main`, conclusión `success`;
- job `Empaquetado · release productiva` exitoso;
- límites de tamaño, temporales y validación de redirects;
- ausencia de `latest.tar.gz` mutable o equivalente.

No aceptar “la release más reciente” sólo por fecha. La elegibilidad debe demostrarse criptográficamente/Git contra `main`.

### 3. Revalidación previa a mutación

`operaciones_host.py` actualmente revalida `main` antes de comprometer target/activación para evitar instalar una versión que dejó de ser vigente durante una actualización lenta.

Tras WP-104 la carrera debe evaluarse contra la **identidad desplegable**, no contra cambios documentales irrelevantes:

- si `main` avanza sólo de forma tal que la release desplegable sigue siendo el mismo SHA, continuar es válido;
- si aparece una release productiva nueva y la identidad desplegable cambia antes del commit operacional, abortar fail-safe antes de cambiar `target-release` o activar;
- si la nueva cabeza de `main` vuelve imposible demostrar la ancestralidad/coherencia de la release resuelta, abortar;
- nunca activar automáticamente una release distinta de la que fue descargada, validada y preparada en ese mismo intento.

### 4. CI y publicación

**No eliminar** la exención documental de CI ni forzar releases para commits puramente documentales.

El workflow `publicar-release.yml` continúa publicando sólo a partir de CI productiva completa verde.

Actualizar comentarios/documentación que hoy describan `HEAD de main == release candidata` de forma incompatible con esta semántica.

### 5. CLI y evidencia

La salida del actualizador debe diferenciar claramente, cuando sean distintos:

- `main_head_sha`;
- `release_sha` seleccionada;
- tag público;
- tree SHA;
- CI run / attempt / job.

El historial operativo debe registrar ambos SHAs cuando difieran, sin perder la trazabilidad vigente.

## Casos de prueba obligatorios

Agregar pruebas deterministas, sin red real, que cubran como mínimo:

1. `main == release_sha` → funcionamiento normal existente;
2. `main` uno o varios commits documentales por delante de la última release → selecciona la release ancestro y continúa;
3. `main` avanza documentalmente durante descarga/preparación pero `release_sha` no cambia → revalidación acepta;
4. aparece una nueva release productiva válida durante la operación → revalidación aborta antes de mutar target/servicios;
5. `latest release` no es ancestro de `main` → fail-closed;
6. tag y `target_commitish` divergentes → fail-closed;
7. release draft/prerelease o respuesta inesperada → fail-closed;
8. no existe release pública → fail-closed;
9. evidencia CI inválida, job incorrecto, tree/checksum/assets inconsistentes → siguen fallando como antes;
10. consumidor sigue sin enviar Authorization/Cookie/token;
11. historial/diagnóstico diferencia `main_head_sha` de `release_sha`;
12. ninguna regresión en idempotencia ni rollback de WP-101A.

## Gates de integración

Antes del merge:

- CI candidata completa verde;
- revisión independiente 0 BLOQUEANTES / 0 IMPORTANTES;
- auditoría sustantiva ORCHESTRATOR `APROBADO_PARA_MERGE`;
- pruebas explícitas de todos los casos anteriores;
- no introducir autenticación ni relajación de evidencia.

Después del merge:

- CI post-merge verde sobre SHA exacto;
- publicación pública exitosa del nuevo merge funcional;
- comprobar que esa publicación se resuelve correctamente como release desplegable aunque `main` avance después por un commit sólo documental;
- recién entonces WP-101B puede volver a HUMAN_GATE para planificar la primera mutación productiva.
