# WP-094 - Independizar sondas runtime del cwd del invocador

## Estado documental

`APROBADO / BLOQUEANTE DE WP-029`

## Origen

Detectado durante el smoke post-sesión de WP-029 en producción el 10/09/2026.

La secuencia SIS-Leg -> Legacy fue exitosa. La vuelta Legacy -> SIS-Leg falló al activar la release preparada con:

`find: fallo al restaurar el directorio de trabajo inicial: /home/concejo: Permiso denegado`

El rollback automático restauró correctamente `ESTABLE_LEGACY`, exactamente un bridge activo y configuración local intacta.

## Causa técnica

`deploy/herramienta_despliegue.py` ejecuta sondas de permisos con `runuser` para las identidades reales de runtime. En particular, la validación de solo lectura de la release ejecuta `runuser --user <usuario> -- find <release> ...` sin fijar un `cwd` accesible e independiente del invocador.

Si la herramienta se lanza desde un directorio no atravesable por `sis-leg-backend` o `sis-leg-bridge` —como `/home/concejo` con permisos restrictivos— GNU `find` hereda ese directorio inicial y puede terminar con código 1 al intentar restaurarlo, aunque el recorrido de la release sea válido.

La corrección debe eliminar toda dependencia funcional del cwd del operador.

## Objetivo

Hacer que todas las sondas runtime ejecutadas mediante `runuser` operen desde un directorio de trabajo explícito, seguro, estable y accesible, de forma que la validación produzca exactamente el mismo resultado independientemente del cwd desde el cual se invoque `herramienta_despliegue.py`.

## Alcance

- Modificar `deploy/herramienta_despliegue.py`.
- Revisar todas las invocaciones a `runuser`, no sólo el `find` que manifestó el fallo.
- Fijar un `cwd` seguro para esas sondas mediante la abstracción existente `EjecutorComandos`/`EjecutorSubprocess`; preferencia por `Path("/")` o equivalente claramente justificado.
- Mantener comandos como listas de argumentos; no usar `shell=True`.
- Mantener la identidad real `sis-leg-backend` / `sis-leg-bridge` para las comprobaciones.
- Mantener el chequeo `find -writable` y las pruebas POSIX existentes; no debilitar la validación de permisos.
- Preservar activación, rollback, Nginx, systemd, Device Bridge, manifests y política de releases.

## Diseño esperado

La solución debe ser estructural y mínima.

Preferencia:
- toda sonda `runuser` se ejecuta con `directorio=Path("/")` (o helper común equivalente) a través de `self.ejecutor.ejecutar(...)`;
- el comportamiento no depende de `os.getcwd()` ni del cwd del proceso padre;
- tests inspeccionan explícitamente el `directorio` enviado al ejecutor;
- si existe más de un sitio que usa `runuser`, evitar que uno quede sin protección.

No resolver con:
- `chdir` global del proceso;
- `os.chdir()` persistente;
- ignorar código de salida de `find`;
- suprimir stderr;
- cambiar permisos de `/home/concejo`;
- agregar acceso del usuario runtime al home del operador;
- parche productivo manual.

## Pruebas obligatorias

1. La sonda `find` de solo lectura usa un cwd explícito y accesible, independiente del invocador.
2. Las sondas `test` mediante `runuser` usan la misma política segura de cwd.
3. Un cwd externo no accesible para runtime no altera el resultado de una release válida.
4. Una release realmente escribible por el usuario runtime sigue fallando.
5. Un path requerido no accesible sigue fallando.
6. No se oculta un error real de `runuser`/`find`.
7. No se usa `shell=True`.
8. No se elimina ni reduce la validación de permisos preexistente.
9. Activación normal conserva rollback.
10. Tests existentes de deployment siguen verdes.

Cuando sea posible, reproducir el caso mediante ejecutor inyectable/determinista sin necesitar root real en CI.
