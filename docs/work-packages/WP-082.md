# WP-082 - Endurecer privacidad y exclusividad efectiva del Device Bridge

## Estado documental

`INTEGRADO`

## Objetivo

Corregir ASTRA-003 y ASTRA-004 en la frontera del Device Bridge: no registrar a INFO contenido reconstruible de teclas de dispositivos no autorizados y autorizar entradas sólo desde el descriptor/ruta que efectivamente adquirió exclusividad kernel.

## Resultado esperado

El bridge puede descubrir dispositivos sin filtrar contenido del teclado normal al journal y ninguna coincidencia de fingerprint habilita por sí sola un segundo descriptor no grabado.

## Dependencias

- WP-079 `INTEGRADO`: gate de CI reproducible.
- WP-075 `INTEGRADO`: captura exclusiva EVIOCGRAB vigente.

- `services/device-bridge/src/sis_leg_device_bridge/adaptador_linux.py`.
- `servicio.py`, `fingerprint.py`, `modelos.py`, remapeo/configuración del bridge.
- Tests de Device Bridge.

## Alcance

- Revisar logs INFO de descubrimiento/entrada y eliminar nombre de tecla/secuencia para dispositivos no mapeados/no autorizados.
- Mantener diagnóstico útil sin contenido de entrada sensible.
- Representar exclusividad/autorización por descriptor/ruta/handle efectivo, no únicamente por fingerprint.
- Garantizar que sólo el descriptor con EVIOCGRAB exitoso entrega pulsaciones al backend.
- Mantener fingerprint como identidad/remapeo donde corresponda, separado de la autorización de captura.
- Añadir pruebas con dos descriptores que comparten fingerprint y resultado de grab distinto.

## Fuera de alcance

- Rediseñar fingerprint para cambio de puerto (HIP-06).
- Implementar recuperación SYN_DROPPED (HIP-03).
- Cambiar topología de una sola PC.
- Agregar autenticación de red.

## Componentes previsiblemente afectados

- Device Bridge adaptador/servicio/modelos.
- Logging.
- Tests unitarios/virtuales.
- Documentación operativa del bridge.

## Criterios de aceptación

1. Pulsaciones de un teclado descubierto pero no mapeado no registran nombre de tecla ni secuencia reconstruible a INFO.
2. Los logs conservan información diagnóstica mínima suficiente, sin bajar privacidad por defecto.
3. Dos descriptores con fingerprint idéntico no comparten autorización lógica: sólo el grabado entrega eventos.
4. Un EVIOCGRAB fallido mantiene fail-safe y no habilita entrada.
5. El flujo normal de los numpads mapeados sigue funcionando.
6. Remapeo conserva identidad lógica sin confundirse con autorización de descriptor.

## Pruebas obligatorias

- Unitarias de logging no autorizado.
- Dos descriptores/fingerprint coincidente con uno solo grabado.
- Fallo de EVIOCGRAB.
- Suite completa Device Bridge.
- Checks Python globales aplicables.
- Validación real queda además exigida en WP-029.
- `git diff --check`.

## Invariantes y restricciones

- Minimización de datos en logs.
- Fail-safe de captura exclusiva.
- No afirmar que existe colisión real de hardware hasta probarla.
- No rebase/force-push.

## Herramientas MCP y documentación técnica externa

Si se consulta evdev/EVIOCGRAB, usar documentación kernel/Linux oficial. No usar analogías de librerías para redefinir la política.

## Consulta a producción si existe ambigüedad funcional/UX/visual

No aplica como regla de UI. El comportamiento productivo histórico no prevalece sobre la privacidad/captura aprobadas.

Cambios de fingerprint, política de cableado o autorización de dispositivos no mapeados requieren escalamiento.
