# WP-087 - Endurecer migración, systemd y smoke de release antes del despliegue

## Estado documental

`APROBADO`

## Objetivo

Resolver ASTRA-006, ASTRA-007 y ASTRA-008 antes de cualquier migración productiva: ejecutar la transición de identidad con tooling nuevo congelado e independiente del `current` histórico, garantizar servicios activos y habilitados al boot, y hacer que el smoke pruebe la identidad exacta de la release servida.

## Resultado esperado

Un rehearsal en staging puede demostrar instalación/migración/rollback de una release concreta, incluyendo cold boot, sin depender de scripts de la release antigua ni aceptar una instalación mixta como saludable.

## Dependencias

- WP-029 `INTEGRADO`: validación final de hardware/regresión funcional previa al hardening de despliegue.
- WP-077 `INTEGRADO`: contrato de rename/migración SIS-Leg vigente.

## Fuentes canónicas obligatorias

- `deploy/herramienta_despliegue.py`.
- `docs/MIGRACION-A-SIS-LEG.md`.
- `docs/13-despliegue-y-operacion.md`.
- `deploy/systemd/sis-leg-backend.service`.
- `deploy/systemd/sis-leg-device-bridge.service`.
- Smoke/tests de despliegue existentes.
- Triage Astra ASTRA-006, ASTRA-007 y ASTRA-008.

## Alcance

### Tooling de migración
- La primera activación SIS-Leg posterior al rename debe ejecutarse desde una herramienta nueva congelada que no dependa de `/opt/sis-leg/current` histórico.
- Definir y probar rollback específico de la migración de identidad.
- No depender de redirects/paths legados para ejecutar la herramienta nueva.

### systemd
- Activación debe garantizar y verificar `is-active` e `is-enabled` de unidades SIS-Leg correspondientes.
- Rehearsal debe incluir cold boot y comprobar recuperación automática.

### Smoke
- Incorporar identidad de release desplegada verificable por backend y cada frontend.
- Smoke debe comparar contra SHA/release esperada y detectar mezcla de versiones, virtual host erróneo o frontend antiguo.
- Mantener health funcional además de identidad.

## Fuera de alcance

- Ejecutar la migración productiva real.
- Resolver por sí solo cortes de energía de HIP-05 más allá de los checkpoints/rehearsal incluidos.
- Cambiar topología de red/firewall de HIP-07.
- Introducir un sistema de deployment externo no aprobado.

## Componentes previsiblemente afectados

- Tooling de deploy/migración.
- Units/systemd o scripts que las instalan/habilitan.
- Endpoints/metadatos de release estrictamente necesarios.
- Frontends/build metadata si se requiere identidad servida.
- Smoke automatizado y runbooks.

## Criterios de aceptación

1. La herramienta usada para migrar es inequívocamente la nueva y no se obtiene desde el `current` histórico.
2. Rollback de migración está documentado y ensayado.
3. Tras activación, unidades requeridas están `active` y `enabled`.
4. Tras cold boot de staging/hardware, servicios vuelven automáticamente.
5. Smoke falla si backend o cualquiera de las superficies sirve una release distinta a la esperada.
6. Smoke detecta instalación mixta y virtual host/ruta incorrecta.
7. Rehearsal produce evidencia GO/NO-GO reproducible.
8. No se toca producción durante el WP.

## Pruebas obligatorias

- Tests unitarios/integración del tooling de despliegue.
- Rehearsal en staging de migración + rollback.
- Cold boot.
- Smoke positivo con SHA esperado.
- Smokes negativos: backend viejo, frontend viejo/mixto, host/ruta erróneo.
- Checks estáticos y CI aplicable.
- `git diff --check`.

## Invariantes y restricciones

- Ningún deploy productivo sin HUMAN_GATE explícito.
- No ejecutar scripts históricos para instalar la nueva release.
- La verificación de identidad no reemplaza health funcional.
- No rebase/force-push.

## Herramientas MCP y documentación técnica externa

Para systemd usar documentación oficial. Para Git/build metadata usar mecanismos existentes antes de añadir dependencias.

## Consulta a producción si existe ambigüedad funcional/UX/visual

No consultar producción para decisiones técnicas de despliegue; usar runbooks y contratos canónicos.

## Decisiones que requieren escalamiento

Cualquier cambio de estrategia de deployment, ubicación productiva, privilegios systemd o rollback irreversible requiere HUMAN_GATE.
