# WP-021 - Shell de Moderación, layout responsive y sincronización de estado

## Estado documental

`APROBADO`

## Objetivo

Crear el shell funcional de la aplicación Nuxt de Moderación, reemplazando el scaffold visual mínimo actual por una interfaz responsive con las cuatro áreas operativas principales y conectándola al estado autoritativo del backend exclusivamente mediante `@sis-leg/api-client`.

El resultado debe establecer la infraestructura visual y reactiva común sobre la cual se implementarán posteriormente las funciones específicas de preparación/sesión, votaciones/Orden del Día y palabra/eventos/remapeo.

## Resultado esperado

Al completar el WP:

- `apps/moderacion` es una SPA Nuxt 4 funcional;
- obtiene y mantiene `EstadoModeracion` mediante `ClienteModeracion`;
- utiliza el ciclo canónico snapshot REST -> SSE -> recuperación por snapshot;
- presenta claramente estado de conexión, estado global y revisión;
- conserva el último estado confirmado durante una desconexión;
- distingue visualmente que dicho estado puede estar desactualizado;
- dispone cuatro áreas operativas en una grilla 2×2 en 1920×1080 y 1366×768;
- áreas extensas quedan preparadas para scroll interno sin alterar la altura de los demás paneles;
- no implementa todavía comandos funcionales pertenecientes a etapas posteriores;
- no duplica reglas de negocio ni contratos del backend;
- no incorpora dependencias externas nuevas.

## Alcance

### 1. Consumo de `api-client`

`apps/moderacion` debe consumir el paquete interno `@sis-leg/api-client` mediante dependencia de workspace.

No debe crear un cliente REST/SSE paralelo dentro de la aplicación.

No debe copiar DTOs ni tipos de backend manualmente.

No debe implementar lógica propia de reconexión que duplique la ya existente en `ClienteModeracion`.

### 2. Estado reactivo de Moderación

Crear una frontera Vue/Nuxt única y testeable que mantenga como mínimo:

- último `EstadoModeracion` recibido;
- estado visual de conexión;
- último error técnico relevante cuando exista;
- indicación de si existe un estado confirmado disponible;
- indicación de si el estado mostrado puede estar desactualizado.

Puede implementarse mediante composable, `ref`, `computed`, `useState` u otras primitivas Vue/Nuxt aprobadas.

No utilizar Pinia.

Debe existir una única suscripción activa por instancia de aplicación y debe cancelarse al destruir la instancia correspondiente.

### 3. Ciclo de sincronización

La aplicación debe utilizar `ClienteModeracion.suscribirEstado(...)` y respetar su semántica canónica:

1. snapshot inicial;
2. nueva baseline;
3. SSE;
4. pérdida de conexión;
5. recuperación mediante nuevo snapshot;
6. nueva conexión SSE.

La aplicación no debe comparar revisiones globalmente por su cuenta para rechazar un snapshot posterior a un restart.

El `api-client` sigue siendo responsable de esa lógica.

### 4. Estados visuales de conexión

La UI debe poder representar conceptualmente al menos:

- carga/conexión inicial;
- conectado;
- reconectando con último estado disponible;
- sin conexión y todavía sin snapshot utilizable.

Cuando todavía nunca se obtuvo estado:

- no se inventa `SIN_PREPARAR`;
- se muestra una condición técnica de carga/conexión.

Cuando ya existe un estado confirmado y se pierde la conexión:

- el último estado permanece visible;
- se marca claramente como potencialmente desactualizado;
- no se vacía la interfaz.

Un snapshot recibido durante recuperación puede sustituir el estado anterior aunque su `revision` sea menor, porque puede corresponder a un reinicio del backend.

La condición de conexión plenamente operativa solo se considera recuperada cuando el ciclo correspondiente vuelve a encontrarse conectado.

### 5. Preparación para comandos futuros

Aunque este WP no implementa los comandos funcionales posteriores, el estado reactivo común debe permitir que esos controles puedan determinar posteriormente si existe conexión utilizable.

Durante desconexión no deberá ser posible que futuros componentes interpreten el último estado conservado como autorización para ejecutar una mutación.

No reconstruir localmente reglas de `capacidades`.

### 6. Cabecera del shell

La cabecera debe mostrar de forma permanente y legible:

- identificación de la aplicación: `Moderación`;
- estado de conexión;
- estado global del backend cuando exista;
- número de `revision` del último estado recibido cuando exista.

No debe presentar un estado backend ficticio mientras todavía no existe snapshot.

No es requisito de este WP reproducir exactamente la cabecera histórica.

### 7. Cuatro áreas funcionales

En escritorio se mantienen simultáneamente visibles cuatro áreas conceptuales:

1. Sesión y votación;
2. Orden del Día;
3. Recinto y palabra;
4. Eventos.

WP-021 crea su estructura visual y estados vacíos/placeholders.

No implementa todavía dentro de ellas las funciones completas de:

- preparación/presencia/autoridades/sesión;
- votaciones/desempate/Orden del Día;
- palabra/eventos/remapeo.

Esas funcionalidades se incorporan en WPs posteriores.

Los placeholders no deben simular acciones disponibles ni enviar comandos.

### 8. Layout Full HD

En 1920×1080:

- cabecera visible;
- cuatro áreas en distribución 2×2;
- los cuatro títulos visibles simultáneamente;
- sin solapamientos;
- sin controles o paneles fuera del viewport por tamaños rígidos;
- las áreas no se empujan mutuamente por crecimiento de contenido.

### 9. Layout 1366×768

En 1366×768 se conserva también:

- cabecera;
- distribución 2×2;
- cuatro áreas simultáneamente identificables.

El layout puede compactar espacios, tipografía y padding dentro de límites legibles.

No debe transformarse en una lista vertical simplemente por alcanzar esta resolución.

### 10. Resoluciones menores

Por debajo de las resoluciones de referencia, el layout puede reorganizarse de manera fluida —incluido apilado cuando resulte necesario— siempre que:

- ninguna función quede inaccesible;
- no existan solapamientos;
- el scroll sea predecible;
- los controles futuros dispongan de dimensiones utilizables.

El breakpoint exacto es una decisión local reversible del WP.

### 11. Scroll interno

La estructura debe impedir que contenido creciente de una zona modifique arbitrariamente las dimensiones de las restantes.

Usar una composición equivalente a:

- contenedores con dimensiones flexibles;
- `min-width: 0`;
- `min-height: 0`;
- zonas de contenido con overflow interno cuando corresponda.

No usar coordenadas absolutas o alturas rígidas diseñadas exclusivamente para 1920×1080.

### 12. Configuración de conexión

Producción conserva el contrato de mismo origen:

- `/moderacion/`
- `/api/v1/`

bajo Nginx.

El frontend no incorpora CORS como requisito productivo.

La implementación debe documentar una forma reproducible de desarrollo local para consumir el backend usando mecanismos nativos del stack y sin incorporar una dependencia externa nueva.

Si se usa configuración pública de Nuxt para URL base, su valor productivo por defecto debe seguir siendo mismo origen.

No modificar el contrato productivo de DT-030.

### 13. Errores

Los errores de transporte/protocolo provenientes del cliente deben:

- poder visualizarse de forma comprensible;
- no borrar el último estado confirmado;
- no presentarse como una transición de negocio;
- no simular que una acción tuvo éxito.

Este WP no debe crear una segunda jerarquía incompatible de errores de API.

### 14. Estilo visual

Mantener una interfaz operacional, sobria y de alto contraste.

Puede evolucionarse el scaffold oscuro actualmente existente.

No se exige copia pixel-perfect del frontend histórico.

El frontend de producción anterior puede usarse únicamente como referencia de organización y ergonomía, nunca como fuente técnica ni contractual.

## Criterios de aceptación

1. El scaffold actual queda reemplazado por un shell funcional.
2. Moderación consume `@sis-leg/api-client`; no existe cliente REST/SSE duplicado.
3. No existen DTOs backend copiados manualmente en la aplicación.
4. Existe una sola suscripción activa por instancia.
5. La suscripción se cancela correctamente al destruir la aplicación.
6. El snapshot inicial aparece en la UI.
7. Un estado posterior recibido por SSE actualiza la UI.
8. El estado global visible proviene exclusivamente de `EstadoModeracion`.
9. La revisión visible corresponde al último estado adoptado.
10. Antes del primer snapshot no se inventa estado global.
11. Al perder SSE después de haber recibido estado, dicho estado permanece visible.
12. Durante esa pérdida se muestra claramente estado de reconexión/desactualización.
13. Un snapshot de recuperación sustituye correctamente al anterior incluso si posee una revisión numérica menor por reinicio de backend.
14. Recuperar la conexión elimina la indicación de estado desactualizado.
15. Los cuatro paneles existen y tienen identidad funcional estable.
16. En 1920×1080 aparecen en 2×2 sin solapamientos.
17. En 1366×768 aparecen en 2×2 sin solapamientos.
18. En ambas resoluciones la cabecera y los cuatro títulos permanecen visibles.
19. El crecimiento interno previsto de un panel no debe aumentar la altura de los otros tres.
20. En resoluciones menores la interfaz continúa accesible mediante adaptación fluida.
21. No existen controles funcionales prematuros que pertenezcan a WPs posteriores.
22. No se agregó polling ni WebSocket.
23. No se agregó Pinia.
24. No se agregó una librería UI externa.
25. No se agregó ninguna dependencia externa directa.
26. No se modificó el backend.
27. No se modificó la discrepancia `D-01/dev01`.
28. El build continúa produciendo una SPA estática.
29. El mismo origen sigue siendo el contrato productivo por defecto.
30. Los nombres propios nuevos respetan DEC-001.
31. Los flujos no triviales quedan documentados pedagógicamente en español.
32. El documento conserva el formato parseable requerido para WPs.

## Pruebas obligatorias

### Vitest / Nuxt Test Utils / Vue Test Utils

Agregar pruebas versionadas que cubran como mínimo:

- estado inicial sin snapshot;
- recepción del primer estado;
- actualización posterior;
- conexión abierta;
- pérdida de conexión conservando estado;
- recuperación posterior;
- aceptación en UI de una baseline recuperada con revisión menor;

- cancelación de suscripción al desmontar;
- ausencia de suscripciones duplicadas;
- renderizado de cabecera;
- renderizado de las cuatro áreas.

No duplicar mediante mocks la lógica interna que ya pertenece a `api-client`; las pruebas de Moderación deben validar su integración/consumo y el estado visual derivado.

### Playwright

Agregar pruebas del shell en Chromium para:

- 1920×1080;
- 1366×768.

En ambas:

- cabecera visible;
- cuatro paneles visibles;
- geometría 2×2;
- sin solapamientos;
- sin overflow global indebido;
- títulos accesibles;
- zonas extensibles preparadas para scroll interno.

No se requiere comparación pixel-perfect por screenshot.

Estas pruebas son smoke/responsive del shell, no sustituyen los E2E institucionales completos de la etapa de integración.

Debe existir un comando reproducible para ejecutarlas y deben incorporarse a CI mediante el stack Playwright ya aprobado, sin agregar otra librería de navegador.

- No Pinia.

## Consulta a producción si existe ambigüedad funcional/UX/visual

- cabecera;
- Comandos;
- Orden del Día;
- Estado recinto;
- Eventos;

WP-021 conserva esa simultaneidad conceptual, pero no debe copiar mecánicamente su HTML/CSS/JS.
