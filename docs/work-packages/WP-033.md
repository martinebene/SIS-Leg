# WP-033 - Entorno integrado de desarrollo y prueba manual

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Incorporar un **harness de desarrollo integrado, reproducible y no productivo** que permita ejecutar y probar manualmente SIS-Leg dentro de `agent-dev` con un único origen HTTP, usando el backend FastAPI real, las SPA reales de Moderación y Recinto y el simulador de dispositivos ya versionado.

La experiencia objetivo para el operador es:

```text
pnpm dev:stack
        ↓
http://127.0.0.1:8000/
├── /moderacion/
├── /recinto/
├── /api/v1/
└── /docs
```

El stack debe quedar accesible desde Windows mediante el alias SSH existente de `agent-dev`, sin publicar un puerto nuevo en el host VPS ni modificar Tailscale, Docker, Caddy, UFW, Supervisor o la configuración persistente del contenedor.

El propósito es disponer, desde este WP en adelante, de una forma simple de **ver, manipular y observar el sistema real integrado** durante el desarrollo, sin esperar al despliegue productivo.

## Resultado esperado

Al completar WP-033 debe ser posible, desde un checkout limpio de SIS-Leg dentro de `agent-dev`:

1. ejecutar un único comando documentado desde la raíz:
   ```bash
   pnpm dev:stack
   ```
2. construir las dos SPA para funcionar bajo sus subrutas canónicas;
3. levantar el backend FastAPI real en un servidor ASGI versionado/reproducible;
4. servir bajo un único origen:
   - `/moderacion/`;
   - `/recinto/`;
   - `/api/v1/`;
   - `/docs`;
5. conservar REST + SSE reales entre ambas SPA y FastAPI, sin CORS;
6. usar `tools/device-simulator/` contra `http://127.0.0.1:8000`;
7. observar en Moderación y Recinto los cambios reales de presencia, test, quórum, sesión y palabra ya implementados;
8. detener todo el harness limpiamente con `Ctrl+C`, sin dejar procesos persistentes;
9. acceder desde Windows mediante un túnel SSH local sobre el alias `agent-dev`;
10. repetir el procedimiento después de futuros WPs sin reconfigurar el VPS.

El harness no es el mecanismo de producción ni un servicio persistente del VPS.

## Evaluación de permisos y frontera operativa

Este WP está diseñado expresamente para poder implementarse **íntegramente por un agente residente en `agent-dev`**.

El usuario `dev` dispone ya de:

- escritura en `/workspace`;
- Node.js 24 y pnpm 11;
- `uv`;
- Git/GitHub;
- ejecución de procesos de usuario;
- acceso a puertos loopback internos del contenedor.

Por tanto, la implementación **no requiere un agente externo con acceso administrativo al VPS**.

### Condición de escalamiento por permisos

Si para cumplir un criterio del WP el implementador concluye que necesita cualquiera de estas acciones, debe detener solamente esa parte y escalar:

- modificar `/opt/containers/`;
- modificar Docker/Compose del host;
- editar `/etc` del host o del contenedor;
- tocar Supervisor;
- publicar un puerto nuevo del contenedor;
- modificar Tailscale;
- modificar Caddy/Nginx del VPS;
- modificar UFW/firewall;
- ejecutar cambios sobre otros contenedores;
- instalar una dependencia con `apt` para hacer funcionar el harness;
- crear un servicio persistente.

Esas acciones requieren evaluación separada por un operador/agente externo autorizado y **no forman parte de WP-033**.

El implementador no debe usar `sudo` para conseguir que el WP funcione.

## Alcance

### 1. Comando único `pnpm dev:stack`

Agregar en la raíz del monorepo un comando versionado y reproducible:

```bash
pnpm dev:stack
```

Debe:

1. validar las precondiciones mínimas necesarias;
2. construir Moderación y Recinto para sus subrutas;
3. iniciar el backend real;
4. servir las SPA estáticas y FastAPI bajo un mismo origen;
5. permanecer en primer plano;
6. finalizar limpiamente con `Ctrl+C`.

La implementación puede organizarse bajo `tools/`, `scripts/` o un módulo de desarrollo claramente separado del runtime productivo.

Se prefiere una implementación multiplataforma basada en Python/Node versionados en el repositorio antes que un script Bash específico de Linux, siempre que no agregue complejidad injustificada.

### 2. Mismo origen y rutas

El contrato externo del harness debe ser:

```text
http://127.0.0.1:8000/moderacion/
http://127.0.0.1:8000/recinto/
http://127.0.0.1:8000/api/v1/
http://127.0.0.1:8000/docs
```

También debe funcionar `/openapi.json` si FastAPI lo expone normalmente.

La raíz `/` puede:

- redirigir a una página de índice simple del harness; o
- presentar enlaces a Moderación, Recinto y Swagger.

La elección es local mientras sea mínima, no institucional y esté testeada.

### 3. Binding seguro por defecto

El servidor debe escuchar por defecto exclusivamente en:

```text
127.0.0.1:8000
```

No debe usar `0.0.0.0` por defecto.

Puede admitirse una opción explícita de desarrollo para cambiar host/puerto si es simple y segura, pero:

- no se versiona ninguna IP privada/pública concreta;
- no se modifica infraestructura para publicarla;
- la documentación recomendada para `agent-dev` conserva loopback + túnel SSH.

### 4. Acceso desde Windows mediante SSH existente

Documentar como procedimiento recomendado:

```bash
ssh -N -L 18080:127.0.0.1:8000 agent-dev
```

Con el túnel activo:

```text
http://127.0.0.1:18080/moderacion/
http://127.0.0.1:18080/recinto/
http://127.0.0.1:18080/docs
```

El WP no modifica la configuración SSH de Windows ni el alias `agent-dev`; únicamente documenta su uso.

### 5. SPA bajo subrutas

Moderación debe poder construirse y funcionar bajo:

```text
/moderacion/
```

Recinto debe poder construirse y funcionar bajo:

```text
/recinto/
```

Los assets, rutas internas y referencias generadas deben respetar esas bases.

La configuración normal de desarrollo existente:

```text
pnpm dev:moderacion
pnpm dev:recinto
```

debe seguir funcionando.

La configuración necesaria para las subrutas debe ser compatible con la estrategia productiva ya aprobada por DT-029/DT-030 y no debe fijar en código una URL absoluta del VPS.

### 6. Backend real, no mocks

El harness debe usar la aplicación FastAPI real construida por `crear_aplicacion()`.

No se permiten:

- backend falso;
- mocks de fetch;
- mocks de EventSource;
- snapshots estáticos como autoridad;
- estado frontend prefabricado.

REST, SSE, comandos, configuración, padrón, auditoría y estado volátil deben ser los reales.

### 7. Servidor ASGI reproducible de desarrollo

El repositorio actualmente no versiona un servidor ASGI de ejecución.

WP-033 autoriza agregar, **si resulta necesario**, una dependencia directa estrictamente de desarrollo para ejecutar FastAPI, preferentemente un servidor ASGI estándar y ampliamente usado.

Reglas:

- debe quedar fijada por `uv.lock`;
- debe pertenecer al grupo de desarrollo o herramienta de desarrollo, no introducirse como dependencia funcional del paquete backend productivo salvo necesidad técnica demostrada;
- no se permite instalarla globalmente ni depender de `uv run --with ...` como procedimiento canónico;
- cualquier dependencia nueva debe justificarse en la PR.

### 8. Servicio estático del harness separado de producción

El mecanismo que sirve las dos SPA dentro del harness:

- puede reutilizar FastAPI/Starlette;
- debe estar claramente identificado como tooling de desarrollo;
- no debe convertir el backend productivo en servidor permanente de SPA por efecto colateral;
- no debe sustituir la decisión de producción Nginx + systemd;
- no debe introducir Docker.

La aplicación productiva importada normalmente desde `sis_leg_backend.main:app` debe conservar su contrato actual.

### 9. Reinicio y estado volátil

Cada nuevo inicio del harness debe iniciar FastAPI en:

```text
SIN_PREPARAR
```

conforme a la arquitectura vigente.

Detener el harness durante una preparación/sesión descarta el estado operativo, como cualquier reinicio normal del backend.

No implementar recuperación ni persistencia adicional.

### 10. Simulador real

El procedimiento manual debe incluir:

```bash
uv run python tools/device-simulator/simulador.py --url http://127.0.0.1:8000
```

Las pulsaciones deben atravesar:

```text
simulador -> HTTP real -> FastAPI -> estado real -> SSE real -> frontends reales
```

No conectar el simulador directamente con servicios internos.

### 11. Corrección del fixture lógico de dispositivos

Resolver dentro de WP-033 la discrepancia preexistente del padrón de desarrollo:

```text
D-01 .. D-12
```

debe quedar coherente con el contrato lógico vigente:

```text
dev01 .. dev12
```

Modificar exclusivamente la columna `dispositivo_votacion` de las 12 filas de fantasía de `config/concejales.csv`.

No modificar por este motivo:

- DNI;
- nombre;
- apellido;
- bloque;
- banca;
- ruta de imagen;
- cantidad de concejales;
- configuración de quórum;
- disposición de bancas.

La corrección está respaldada por:

- DEC-006, cuyo request canónico usa `dev01`;
- WP-007, cuyo simulador normaliza a `devNN`;
- `services/device-bridge/config/devices.json`, que ya mapea a `dev01..dev12`.

No se introduce una nueva semántica; se elimina una inconsistencia del fixture de desarrollo.

### 12. Auditoría local de pruebas manuales

El harness utiliza el `config/system.toml` real de desarrollo, incluido:

```toml
[paths]
logs_dir = "logs"
```

Los CSV generados por pruebas manuales permanecen locales y `logs/` continúa ignorado por Git.

No borrar automáticamente logs previos ni introducir limpieza destructiva.

Agregar documentación breve y accionable que cubra, como mínimo:

2. ejecutar `pnpm dev:stack`;
3. abrir el túnel desde Windows;
4. abrir Moderación y Recinto en dos pestañas;
