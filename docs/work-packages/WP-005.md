# WP-005 - Preparación de sala y cancelación

## Estado documental

`APROBADO`

## Objetivo

Implementar el primer ciclo funcional de SIS-Leg que permite pasar de `SIN_PREPARAR` a `PREPARANDO` y cancelar esa preparación, integrando de forma atómica bajo el serializador global el estado operativo de WP-002, la configuración/padrón congelados de WP-003 y la auditoría durable de WP-004.

## Resultado esperado

El backend expone el recurso REST `/api/v1/preparacion` con comandos para preparar y cancelar una sala.

Una preparación exitosa carga y congela `config/system.toml` y `config/concejales.csv`, crea el contexto operativo limpio con todos los concejales ausentes, crea y conserva un escritor de auditoría L1/L2/L3, persiste el evento institucional de inicio y recién entonces deja el sistema en `PREPARANDO`.

Una cancelación exitosa persiste el evento institucional de cancelación, cierra definitivamente los CSV, descarta todo el contexto operativo activo y devuelve el sistema a `SIN_PREPARAR`.

Las operaciones no confirman éxito si configuración, padrón o auditoría obligatoria no pueden garantizar sus contratos.

## Dependencias

- WP-002 integrado: estado operativo único, lifespan y `EjecutorMutaciones` global.
- WP-003 integrado: carga, validación y snapshots inmutables de configuración y padrón.
- WP-004 integrado: `EscritorAuditoriaCsv`, jerarquía L1/L2/L3, `flush` + `fsync`, cierre irreversible y fallo cerrado.
- DEC-005 vigente para planificación y autoridad documental del orquestador.

## Alcance

### Preparación de sala

Implementar `POST /api/v1/preparacion` sin body.

La operación completa debe ejecutarse dentro del `EjecutorMutaciones` único de WP-002 y solo es válida cuando `estado_global == SIN_PREPARAR`.

Una preparación válida debe:

1. tomar la fecha/hora local real correspondiente al inicio de la operación;
2. cargar `config/system.toml` mediante la interfaz pública de WP-003;
3. cargar `config/concejales.csv` y validarlo contra la configuración cargada;
4. conservar los snapshots inmutables de configuración y padrón para toda la preparación/sesión futura;
5. crear el `EscritorAuditoriaCsv` usando el directorio de registros definido por la configuración;
6. persistir antes de confirmar éxito el evento institucional:
   - nivel: `L3`;
   - tag: `PREPARACION`;
   - `event_code`: `PREPARACION_INICIADA`;
   - mensaje: `Preparación de sala iniciada`;
7. crear/instalar el contexto de preparación activo con estado operativo limpio;
8. dejar a todos los concejales ausentes, sin conservar presencia ni otro estado operativo de una ejecución anterior;
9. asociar al contexto activo el escritor/rutas de auditoría necesarios para los WPs posteriores;
10. cambiar `estado_global` a `PREPARANDO` únicamente cuando los pasos obligatorios anteriores hayan completado correctamente;
11. responder `204 No Content` sin body.

La representación interna concreta de la preparación, presencias y referencias de auditoría queda bajo autonomía técnica local siempre que respete el modelo conceptual, los contratos previos y permita a los WPs posteriores extender el contexto sin duplicar autoridad.

### Cancelación de preparación

Implementar `DELETE /api/v1/preparacion` sin body.

La operación completa debe ejecutarse dentro del mismo `EjecutorMutaciones` y solo es válida cuando `estado_global == PREPARANDO`.

La cancelación:

1. no recibe ni exige motivo;
2. persiste antes de confirmar éxito el evento institucional:
   - nivel: `L3`;
   - tag: `PREPARACION`;
   - `event_code`: `PREPARACION_CANCELADA`;
   - mensaje: `Preparación de sala cancelada`;
3. cierra definitivamente el escritor de auditoría activo;
4. descarta el contexto de preparación, configuración/padrón congelados y referencias de auditoría activas;
5. deja nuevamente el estado operativo limpio en `SIN_PREPARAR`;
6. conserva en disco los CSV generados por esa preparación;
7. responde `204 No Content` sin body.

### Fallos antes de establecer `PREPARANDO`

Si falla la carga/validación de configuración o padrón, no se crea una preparación activa y el sistema permanece en `SIN_PREPARAR`.

Si durante la creación del conjunto CSV o el registro de `PREPARACION_INICIADA` se alcanzaron a crear archivos antes de producirse un error:

- esos archivos se conservan como evidencia técnica y no se eliminan para simular que nunca existieron;
- el escritor se cierra en la medida segura posible sin ocultar el error original;
- el sistema permanece en `SIN_PREPARAR`;
- no queda una preparación activa reutilizable;
- un intento posterior utiliza normalmente la regla de nombres libres de WP-004 y nunca sobrescribe archivos previos;
- la API responde el error técnico correspondiente, nunca `204`.

No se implementa rollback destructivo de archivos de auditoría parcialmente creados.

### Fallo cerrado al cancelar

La cancelación solo se confirma cuando puede persistirse el evento obligatorio y completarse el cierre del conjunto de auditoría.

Si falla el registro de `PREPARACION_CANCELADA` o no puede garantizarse el cierre de los CSV:

- la API responde `503 AUDITORIA_NO_DISPONIBLE`;
- no se responde éxito parcial;
- `estado_global` permanece `PREPARANDO`;
- no se inventa un cuarto estado reglamentario;
- la preparación queda operativamente en fallo cerrado para nuevas mutaciones dependientes de auditoría;
- la recuperación práctica ante esa condición grave es el reinicio del backend, que por las reglas vigentes comienza nuevamente en `SIN_PREPARAR` sin reconstruir la preparación anterior.

Si el evento alcanzó a persistirse antes de que falle el cierre posterior, no se reescriben ni borran retrospectivamente los CSV; el `503` sigue indicando que la cancelación completa no pudo confirmarse.

### Contrato de errores HTTP

Las respuestas de error propias de este WP utilizan siempre:

```json
{
  "codigo": "CODIGO_ESTABLE",
  "mensaje": "Mensaje legible por personas."
}
```

Mapeo obligatorio:

- `409 Conflict` + `ESTADO_INCOMPATIBLE`:
  - preparar cuando el sistema no está en `SIN_PREPARAR`;
  - cancelar cuando el sistema no está en `PREPARANDO`.
- `503 Service Unavailable` + `CONFIGURACION_INVALIDA`:
  - `ErrorTomlInvalido`;
  - `ErrorValidacionConfiguracion`.
- `503 Service Unavailable` + `PADRON_INVALIDO`:
  - `ErrorPadronInvalido`.
- `503 Service Unavailable` + `AUDITORIA_NO_DISPONIBLE`:
  - creación, persistencia o cierre de auditoría que no puede garantizar el contrato obligatorio.
- `500 Internal Server Error` + `ERROR_INTERNO`:
  - fallos inesperados no clasificados por los contratos anteriores, reutilizando el tratamiento estable ya existente.

Los mensajes pueden aportar diagnóstico humano seguro, pero el cliente debe poder decidir por `codigo` y no por comparar textos variables.

### Integración con las fundaciones previas

- Reutilizar `EstadoOperativo`, `RecursosAplicacion` y `EjecutorMutaciones`; no crear una segunda fuente global de estado ni un segundo lock de negocio.
- Reutilizar exclusivamente las interfaces públicas de carga de WP-003; no duplicar parser/validaciones TOML o CSV.
- Reutilizar `EscritorAuditoriaCsv` de WP-004; no implementar otro writer, buffering o estrategia alternativa de durabilidad.
- Ampliar los tipos/campos mínimos dejados deliberadamente abiertos por WP-002 solo en lo necesario para representar la preparación activa.
- Mantener un único proceso/worker como supuesto de ejecución.

## Criterios de aceptación

1. **CA-001 regresión:** un backend recién iniciado sigue en `SIN_PREPARAR`, sin preparación/sesión/votación activa ni auditoría abierta.
2. **CA-002, parte WP-005:** `POST /api/v1/preparacion` válido pasa a `PREPARANDO`, carga configuración/padrón congelados, crea tres CSV y deja a todos los concejales ausentes.
3. **CA-003:** cualquier configuración/padrón inválido contemplado por WP-003 impide preparar, devuelve código HTTP estable y deja el sistema en `SIN_PREPARAR`.
4. Una preparación desde un estado distinto de `SIN_PREPARAR` se rechaza con `409 ESTADO_INCOMPATIBLE` sin modificar estado ni crear un nuevo conjunto de auditoría.
5. Una preparación no devuelve `204` antes de que `PREPARACION_INICIADA` esté durablemente persistido.
6. Si falla la creación/persistencia inicial de auditoría, el sistema permanece `SIN_PREPARAR`, conserva cualquier archivo ya creado y devuelve `503 AUDITORIA_NO_DISPONIBLE`.
7. **CA-008:** `DELETE /api/v1/preparacion` desde `PREPARANDO` registra cancelación, cierra los CSV, vuelve a `SIN_PREPARAR` y conserva los archivos generados.
8. La cancelación no admite ni requiere motivo y una llamada válida sin body puede completarse con `204 No Content`.
9. Cancelar fuera de `PREPARANDO` devuelve `409 ESTADO_INCOMPATIBLE` sin alterar estado.
10. Si la auditoría falla al cancelar, no se confirma éxito: se devuelve `503 AUDITORIA_NO_DISPONIBLE`, el estado permanece `PREPARANDO` y queda fallo cerrado para nuevas mutaciones auditables.
11. **CA-053/CA-054, integración:** cada preparación usa el writer de WP-004, conserva nombres no sobrescribibles y los eventos L3 de este WP aparecen en L1+L2+L3 con el mismo `seq`.
12. **CA-055, integración:** los dos eventos propietarios no se consideran confirmados antes de escritura + `flush` + `fsync` provistos por WP-004.
13. **CA-056, integración:** después de una cancelación exitosa el writer queda cerrado y esos archivos no vuelven a modificarse por el backend.
14. **CA-057, parte WP-005:** reiniciar durante `PREPARANDO` crea un nuevo `EstadoOperativo` en `SIN_PREPARAR`; no reconstruye preparación desde los CSV ni modifica archivos previos retrospectivamente.
15. **CA-058, parte WP-005:** dos comandos concurrentes de preparación/cancelación se ordenan por el único `EjecutorMutaciones`; no crean estados simultáneos ni corrompen auditoría.
16. **CA-059:** cambios en `system.toml` o `concejales.csv` después de preparar no alteran los snapshots activos; una preparación nueva posterior vuelve a cargar desde disco.
17. El OpenAPI generado expone `POST` y `DELETE /api/v1/preparacion` sin body de entrada y con respuestas coherentes con el contrato documentado.
18. No se introduce base de datos, segundo worker, segundo serializador de negocio ni nuevas dependencias directas sin escalamiento.

## Pruebas obligatorias

### Dominio/servicio

- Preparación exitosa desde `SIN_PREPARAR` y construcción del contexto congelado.
- Todos los concejales comienzan ausentes.
- Rechazo por estado incompatible.
- Configuración inválida sin estado parcial.
- Padrón inválido sin estado parcial.
- Fallo de creación del writer sin transición a `PREPARANDO`.
- Fallo al persistir `PREPARACION_INICIADA` sin transición a `PREPARANDO` y sin eliminación retrospectiva de archivos creados.
- Cancelación exitosa, evento final, cierre y limpieza completa del contexto.
- Fallo de persistencia/cierre durante cancelación: `PREPARANDO` permanece y el flujo queda en fallo cerrado.
- Nueva preparación posterior a una cancelación exitosa comienza limpia y usa un conjunto de auditoría distinto.
- Modificación de archivos de configuración/padrón durante `PREPARANDO` no cambia snapshots activos.
- Reinicio/lifespan nuevo vuelve a `SIN_PREPARAR` sin reconstrucción.
- Concurrencia mínima que demuestre orden único mediante `EjecutorMutaciones`.

### API

- `POST /api/v1/preparacion` exitoso: `204` y body vacío.
- `DELETE /api/v1/preparacion` exitoso: `204` y body vacío.
- Ninguno de los dos comandos requiere body.
- `409 ESTADO_INCOMPATIBLE` en transiciones inválidas.
- `503 CONFIGURACION_INVALIDA` para errores TOML/configuración.
- `503 PADRON_INVALIDO` para errores de padrón.
- `503 AUDITORIA_NO_DISPONIBLE` para fallos obligatorios de auditoría.
- `500 ERROR_INTERNO` continúa cubriendo fallos inesperados sin filtrar detalles internos.
- OpenAPI refleja rutas, métodos, ausencia de body y respuestas documentadas.

### Calidad

- Ruff verde.
- Ruff formatter verde.
- Pyright verde.
- pytest completo verde.

## Invariantes y restricciones

- Únicos estados globales: `SIN_PREPARAR`, `PREPARANDO`, `SESION_ABIERTA`; este WP solo implementa las dos primeras transiciones de su alcance.
- Máximo una preparación/sesión activa.
- Estado activo exclusivamente en memoria y sin recuperación desde disco.
- Una nueva preparación carga snapshots nuevos; una preparación activa nunca relee archivos para mutarse.
- Todos los concejales comienzan ausentes.
- Toda mutación de este WP pasa por el `EjecutorMutaciones` único.
- La auditoría institucional se escribe síncronamente y en fallo cerrado.
- Los archivos de auditoría alcanzados por un intento fallido no se borran ni reescriben para ocultar el fallo.
- `POST`/`DELETE /api/v1/preparacion` no reciben rutas, configuración, padrón ni motivo desde el cliente.
- No crear un nuevo estado reglamentario para representar la falla técnica de auditoría.
- No incorporar dependencias directas nuevas sin autorización.
- Aplican DEC-001 y DEC-003 transversalmente.

## Decisiones que requieren escalamiento

Escalar antes de:

- cambiar `POST`/`DELETE /api/v1/preparacion`, sus códigos de éxito o incorporar body obligatorio;
- cambiar el mapeo `409/503/500` o los códigos estables definidos;
- exigir o agregar motivo de cancelación;
- cambiar nivel, tag, `event_code` o mensaje de `PREPARACION_INICIADA`/`PREPARACION_CANCELADA`;

- pasar a `SIN_PREPARAR` después de una cancelación cuyo evento/cierre de auditoría no pudo garantizarse;
- crear un estado reglamentario adicional de fallo;
- cambiar responsabilidades entre backend, frontend o bridge;
- introducir persistencia operativa/recuperación de sesión;
- cambiar serialización, formato/durabilidad de auditoría, dependencias o arquitectura global.

Usar el formato de escalamiento de DT-038 y detener solo la parte dependiente.
