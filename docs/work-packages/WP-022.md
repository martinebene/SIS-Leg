# WP-022 - UI de preparación, presencia, autoridades, sesión y advertencia de cierre

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Implementar sobre el shell de Moderación integrado por WP-021 la experiencia operativa completa correspondiente a:

- preparación de sala;
- visualización del padrón y disposición de bancas;
- presencia y test físico de dispositivos;
- quórum;
- número de sesión;
- Presidencia;
- Secretaría Legislativa;
- apertura de sesión;
- actualización de autoridades durante una sesión abierta;
- cierre de sesión;
- advertencia confirmatoria de cierre cuando exista un orador actual o al menos un pedido de palabra pendiente.

El frontend debe representar exclusivamente el estado autoritativo recibido mediante `EstadoModeracion` y ejecutar los comandos ya expuestos por `ClienteModeracion`.

WP-022 no introduce nuevas reglas de negocio, contratos HTTP, transporte, DTOs ni fuentes de estado.

## Resultado esperado

Al completar el WP, Moderación debe permitir recorrer funcionalmente:

`SIN_PREPARAR -> PREPARANDO -> SESION_ABIERTA -> SIN_PREPARAR`

Y también:

`SIN_PREPARAR -> PREPARANDO -> SIN_PREPARAR`

con estas propiedades observables:

- en `SIN_PREPARAR`, `Preparar sala` es la acción institucional principal;
- la preparación exitosa se refleja únicamente cuando el backend publica el nuevo `EstadoModeracion`;
- durante `PREPARANDO` se visualiza el padrón congelado y su disposición de bancas;
- cada banca muestra identidad, imagen, presencia y señal temporal de test;
- Moderación no puede acreditar ni retirar presencia manualmente;
- se visualizan cantidad de presentes, quórum requerido, estado de quórum y faltantes;
- pueden editarse número de sesión, Presidencia y Secretaría Legislativa;
- el botón de apertura depende de la capacidad `abrir_sesion` informada por backend;
- los motivos que impiden abrir se muestran de forma comprensible;
- puede cancelarse la preparación;
- al abrir sesión, el número queda presentado como dato inmutable;
- Presidencia y Secretaría permanecen editables durante `SESION_ABIERTA`, incluso si existe una votación;
- puede cerrarse la sesión cuando `capacidades.cerrar_sesion` lo permita;
- si existe orador o cola de palabra, la UI advierte y solicita confirmación antes de enviar `Cerrar sesión`;
- cancelar esa advertencia no envía ningún comando;
- confirmar envía el cierre normal y no modifica localmente cola u orador;
- los controles mutantes quedan inhabilitados cuando no existe una conexión plenamente utilizable;
- durante reconexión se conserva visible el último estado confirmado, marcado como potencialmente desactualizado;
- ningún éxito se simula mediante mutaciones optimistas de estado local;
- no se agregan dependencias externas nuevas.

## Alcance

### 1. Extender el shell existente, no reemplazarlo

WP-022 trabaja sobre los componentes y la sincronización integrados por WP-021.

Debe conservar:

- Nuxt 4;
- Vue 3;
- TypeScript estricto;
- Tailwind CSS v4;
- componentes propios;
- SPA estática;
- cuatro áreas principales;
- layout 2×2 en Full HD y 1366×768;
- scroll interno;
- cabecera permanente;
- estado visual de conexión;
- misma suscripción compartida;
- mismo `useEstadoModeracion`;
- mismo `ClienteModeracion`.

No crear una segunda aplicación, store, bus de estado institucional, cliente REST ni suscripción SSE.

### 2. Uso exclusivo de `EstadoModeracion`

Toda representación funcional debe surgir del snapshot autoritativo vigente.

Campos relevantes para este WP incluyen conceptualmente:

- `estado_global`;
- `preparacion`;
- `sesion`;
- `configuracion`;
- `concejales`;
- `quorum`;
- `palabra`;
- `auditoria`;
- `capacidades`.

La UI no consulta archivos de configuración directamente.

La UI no lee `concejales.csv`.

La UI no consulta `devices.json`.

La UI no deriva presencia, autoridades o sesión desde variables persistentes del navegador.

Después de recarga o reconexión debe reconstruirse completamente desde `EstadoModeracion`.

### 3. Uso exclusivo de `ClienteModeracion`

Los comandos de este WP deben usar las interfaces ya existentes:

- `prepararSala()`;
- `actualizarPreparacion(...)`;
- `cancelarPreparacion()`;
- `abrirSesion()`;
- `actualizarSesion(...)`;
- `cerrarSesion()`.

No llamar directamente a `fetch`.

No copiar endpoints REST dentro de componentes.

No modificar `packages/api-client/` si el contrato existente es suficiente.

Si durante implementación se detecta que el contrato real integrado no permite satisfacer un requisito aprobado de este WP:

- no crear un bypass local;
- no modificar OpenAPI/backend de forma oportunista;
- detener ese alcance;
- documentar la incompatibilidad;
- escalar conforme DT-038.

### 4. Gate común de comandos mutantes

Todo control que envíe una mutación debe considerar simultáneamente:

1. existencia de un `EstadoModeracion` confirmado;
2. conexión plenamente utilizable según la frontera integrada por WP-021;
3. `capacidades.<operacion>.habilitada`;
4. validez local mínima del body específico que el operador intenta enviar, cuando corresponda.

La UI no puede tratar un snapshot conservado durante `RECONECTANDO` como autorización suficiente para mutar.

Durante reconexión:

- el último estado confirmado permanece visible;
- se mantiene la indicación visual de stale/reconexión;
- los controles mutantes permanecen deshabilitados.

No reconstruir localmente las precondiciones que ya informa `capacidades`.

### 5. Estado `SIN_PREPARAR`

Cuando `estado_global == SIN_PREPARAR`, la interfaz debe:

- mostrar claramente que no existe preparación activa;
- ofrecer `Preparar sala` como acción institucional principal;
- no mostrar campos activos para número o autoridades como si ya existiera una preparación;
- no mostrar controles funcionales de votación;
- no mostrar controles funcionales de palabra;
- no permitir presencia manual.

`Preparar sala` debe ejecutar exclusivamente `ClienteModeracion.prepararSala()`.

Después de un `204`:

- no cambiar manualmente el estado a `PREPARANDO`;
- esperar/adoptar el estado autoritativo actualizado del backend.

Un error debe permanecer visible y no debe simularse éxito.

### 6. Estado `PREPARANDO`: datos institucionales

Durante `PREPARANDO`, Moderación debe permitir ver y editar:

- `numero_sesion`;
- `presidencia`;
- `secretaria_legislativa`.

Los valores visibles confirmados provienen de `estado.preparacion`.

#### Número de sesión

El operador debe poder ingresar un entero positivo.

El frontend puede aplicar controles de entrada apropiados para evitar errores obvios, pero:

- no valida secuencia;
- no valida unicidad;
- no consulta historial;
- el backend conserva la validación definitiva.

Durante `PREPARANDO` puede modificarse varias veces.

#### Presidencia y Secretaría Legislativa

Son texto libre.

Durante `PREPARANDO` pueden:

- cargarse;
- modificarse;
- limpiarse.

La interfaz no busca Presidencia en el padrón.

No vincula Presidencia con un concejal.

No altera presencia si el texto coincide con una persona del padrón.

#### Persistencia de las ediciones

Cada cambio se envía utilizando `ClienteModeracion.actualizarPreparacion(...)`.

La mecánica visual concreta de edición —por campo, por conjunto, mediante acción explícita de guardado u otra solución equivalente— es autonomía local reversible del implementador.

Debe cumplir siempre:

- no simular una actualización antes de la respuesta del backend;
- permitir conocer qué valor está confirmado por backend;
- mantener una interacción clara para el operador;
- no producir una tormenta innecesaria de requests;
- no introducir una segunda fuente de verdad.

### 7. Cancelar preparación

Durante `PREPARANDO`, debe existir la acción `Cancelar preparación`, que utiliza `ClienteModeracion.cancelarPreparacion()`.

Su disponibilidad depende de `capacidades.cancelar_preparacion`.

Después del éxito:

- no limpiar localmente el estado institucional para simular `SIN_PREPARAR`;
- esperar/adoptar el nuevo snapshot.

No existe motivo obligatorio de cancelación.

WP-022 no introduce una nueva precondición reglamentaria.

### 8. Representación de bancas

El área `Recinto y palabra` creada por WP-021 debe incorporar en este WP la representación de las bancas correspondiente a preparación y sesión.

La disposición se construye usando exclusivamente datos proyectados, especialmente:

- `configuracion.filas_bancas`;
- `concejales[].banca`.

Debe respetar la disposición configurada y no asumir rígidamente 12 bancas ni filas 3/4/5 como constantes de código.

Los valores actuales sirven únicamente como configuración de referencia.

Cada banca debe permitir identificar al menos:

- número de banca;
- nombre;
- apellido;
- bloque cuando exista;
- imagen;
- presencia;
- señal de test activa.

El identificador lógico de dispositivo puede mostrarse de manera secundaria para diagnóstico en Moderación si la composición visual lo permite.

No debe convertirse en una identidad alternativa del concejal.

### 9. Imágenes de concejales

La imagen de cada banca se resuelve exclusivamente desde `concejal.ruta_imagen`.

No utilizar una relación `banca -> nombre de archivo` hardcodeada en frontend.

No utilizar `1.png` a `12.png` como convención implícita de negocio.

El padrón actual proyecta rutas internas bajo `assets/bancas/...`.

Si los archivos correspondientes todavía no existen en SIS-Leg, este WP queda autorizado a incorporar únicamente los assets históricos necesarios desde `martinebene/Botonera`, rama `main`, ruta `app/web/static/bancas/`, y ubicarlos/nombrarlos dentro del frontend de SIS-Leg de forma que las rutas canónicas declaradas por `ruta_imagen` puedan resolverse correctamente.

No modificar `concejales.csv` simplemente para acomodarlo a los nombres históricos de archivo.

No copiar el frontend histórico completo.

Si una imagen no puede cargarse:

- no romper el renderizado completo del recinto;
- mostrar una degradación visual legible;
- conservar identidad textual y estado funcional de esa banca.

### 10. Presencia

Moderación solo visualiza presencia.

Para cada concejal, `presente == true` debe distinguirse claramente de `presente == false`.

La representación debe tener suficiente contraste para operación a distancia en las resoluciones objetivo.

Está expresamente prohibido agregar:

- botón Presente/Ausente;
- checkbox de presencia;
- click sobre banca para cambiar presencia;
- endpoint alternativo;
- llamada a `/entradas/tecla`;
- simulación de tecla `9`.

La presencia solo cambia por la entrada física autorizada y el frontend refleja el nuevo snapshot.

### 11. Test de dispositivo

Cuando `concejal.test_activo == true`, la banca debe mostrar una señal visual temporal evidente que permita al operador confirmar qué teclado físico fue probado.

La señal:

- no cambia presencia;
- no modifica quórum;
- no agrega estado de negocio local;
- desaparece cuando el estado autoritativo deja de indicar test activo.

`test_expira_en` puede utilizarse únicamente para mejorar la representación visual.

No crear un temporizador local que se convierta en autoridad funcional independiente del backend.

El frontend no puede activar el test.

### 12. Quórum

Cuando existe contexto operativo, la interfaz debe mostrar claramente:

- `cantidad_presentes`;
- `requerido`;
- `alcanzado`;

desde `estado.quorum`.

También debe informar cuántos concejales faltan para alcanzar el quórum cuando éste todavía no fue alcanzado.

Puede derivarse exclusivamente para presentación:

`faltantes = max(0, requerido - cantidad_presentes)`.

Ese cálculo es informativo.

No puede utilizarse como sustituto de `capacidades.abrir_sesion.habilitada`.

La decisión de si una sesión puede abrirse sigue perteneciendo al backend.

### 13. Apertura de sesión

Durante `PREPARANDO` debe existir la acción `Abrir sesión`.

La habilitación institucional proviene de `capacidades.abrir_sesion.habilitada`.

Si está deshabilitada, los `motivos` del backend deben poder presentarse de forma comprensible.

Como mínimo deben contemplarse visualmente los códigos ya vigentes:

- `QUORUM_INSUFICIENTE`;
- `NUMERO_SESION_REQUERIDO`;
- `PRESIDENCIA_REQUERIDA`;
- `SECRETARIA_LEGISLATIVA_REQUERIDA`;
- `AUDITORIA_NO_DISPONIBLE`;
- `ESTADO_INCOMPATIBLE`.

No es obligatorio mostrar el código técnico crudo como único texto.

Puede acompañarse con un mensaje humano estable.

No inferir ni mantener otra lista independiente de precondiciones para decidir autoridad.

La acción utiliza `ClienteModeracion.abrirSesion()`.

Después del éxito, la transición visible a `SESION_ABIERTA` debe provenir del nuevo estado backend.

### 14. Estado `SESION_ABIERTA`

Durante una sesión abierta, el área de sesión debe mostrar al menos:

- número de sesión;
- Presidencia vigente;
- Secretaría Legislativa vigente;
- cantidad de presentes;
- quórum;
- estado institucional de sesión abierta.

El número de sesión debe presentarse como inmutable.

No existe edición de número mediante `PATCH /sesion`.

### 15. Autoridades durante sesión abierta

Durante `SESION_ABIERTA`, Presidencia y Secretaría Legislativa permanecen editables.

Los cambios usan exclusivamente `ClienteModeracion.actualizarSesion(...)`.

Las autoridades:

- no pueden quedar vacías durante sesión abierta;
- son texto libre;
- no se vinculan al padrón;
- pueden modificarse aun cuando exista una votación.

WP-022 no debe deshabilitar edición de autoridades simplemente porque `estado.votacion != null` si el backend informa que `actualizar_sesion` continúa habilitada.

La mecánica concreta de edición es autonomía local reversible, bajo las mismas reglas de estado autoritativo y ausencia de optimismo falso establecidas para preparación.

### 16. Cierre de sesión

Durante `SESION_ABIERTA` debe existir `Cerrar sesión`.

La disponibilidad se toma de `capacidades.cerrar_sesion`.

No reconstruir localmente los estados de votación que permiten o impiden cerrar.

Si backend informa un motivo como:

- `VOTACION_PENDIENTE`;
- `AUDITORIA_NO_DISPONIBLE`;
- `ESTADO_INCOMPATIBLE`;

debe mostrarse claramente al operador.

Si la capacidad está habilitada, la acción normal usa `ClienteModeracion.cerrarSesion()`.

No se implementa un endpoint alternativo.

### 17. Advertencia de cierre con palabra pendiente

Antes de enviar `Cerrar sesión`, la UI debe consultar exclusivamente el `EstadoModeracion` vigente.

Existe palabra pendiente cuando se cumple al menos una:

- `estado.palabra?.orador != null`;
- `estado.palabra?.cola.length > 0`.

Si no existe palabra pendiente:

- el cierre continúa normalmente sin esta advertencia específica.

Si existe palabra pendiente:

- mostrar una advertencia confirmatoria clara;
- indicar que existen concejales usando o esperando el uso de la palabra;
- no presentar esa situación como error backend;
- no limpiar la cola;
- no quitar al orador;
- no otorgar palabra;
- no enviar ningún comando al abrir la advertencia.

Si el operador cancela:

- cerrar la advertencia;
- no llamar `cerrarSesion()`;
- dejar la sesión, cola y orador sin cambios.

Si el operador confirma:

- ejecutar normalmente `ClienteModeracion.cerrarSesion()`;
- no ejecutar comandos de palabra previamente;
- dejar que el backend aplique todas las reglas de cierre institucional.

La implementación visual concreta de la confirmación —modal propio, diálogo accesible u otra solución con componentes existentes— es autonomía local reversible.

No agregar una nueva dependencia UI.

### 18. Convivencia con votaciones

WP-022 no implementa la UI de votaciones.

Sin embargo, su parte de sesión debe convivir correctamente con un `EstadoModeracion` que ya contenga `votacion != null`.

En particular:

- autoridades siguen editables según capacidades;
- presencia/quórum siguen visibles;
- cierre de sesión sigue tomando `capacidades.cerrar_sesion`;
- la advertencia de palabra pendiente sigue funcionando;
- no se destruye ni oculta información de sesión necesaria para WP-023.

No agregar controles de:

- abrir votación;
- finalizar votación;
- desempate;
- formularios de mayoría.

Eso pertenece a WP-023.

### 19. Frontera con WP-024

WP-022 consume `estado.palabra` únicamente para:

- mostrar información mínima necesaria si resulta útil;
- determinar la advertencia confirmatoria de cierre.

No implementa:

- `Otorgar palabra`;
- `Quitar palabra`;
- edición manual de cola;
- selección de orador;
- tecla `7`;
- remapeo.

Los controles completos de palabra y remapeo pertenecen a WP-024.

El área visual debe mantenerse compatible con esa extensión posterior.

### 20. Errores de comandos

Los errores provenientes de `@sis-leg/api-client` deben:

- mostrarse de manera legible;
- no borrar el último estado confirmado;
- no convertirse en una transición local ficticia;
- no ocultarse silenciosamente;
- no provocar una segunda solicitud automática del mismo comando;
- permitir al operador volver a intentar cuando el estado/capacidad lo permita.

No crear una segunda taxonomía de errores HTTP.

Cuando exista un error estructurado del backend, debe preservarse su código estable como base para el tratamiento.

### 21. Éxito de comandos y actualización de estado

Los comandos mutantes pueden ofrecer feedback visual de envío/éxito/error.

Pero:

- `204` no habilita a modificar manualmente `estado_global`;
- no alterar localmente presencia;
- no alterar localmente autoridades como estado confirmado;
- no limpiar localmente sesión;
- no inventar revisiones;
- no actualizar manualmente capacidades.

El siguiente `EstadoModeracion` confirmado es el que determina la representación institucional.

### 22. Responsive y preservación del shell

Debe conservarse el contrato responsive de WP-021.

En `1920×1080` y `1366×768` deben permanecer:

- cabecera visible;
- cuatro paneles 2×2;
- títulos visibles;
- sin solapamientos;
- sin crecimiento de Q1/Q3 que empuje los restantes paneles;
- controles accesibles.

La incorporación de:

- formulario de sesión;
- autoridades;
- bancas;
- quórum;
- mensajes de capacidad;

no puede romper el aislamiento de altura ya implementado.

Cuando el contenido exceda el espacio disponible, usar scroll interno o composición equivalente.

En resoluciones menores puede producirse reflow/apilado conforme WP-021.

### 23. Estilo y jerarquía visual

Mantener:

- estilo oscuro;
- sobrio;
- alto contraste;
- apto para operación institucional;
- lectura rápida.

Debe resultar fácil distinguir visualmente:

- `SIN_PREPARAR`;
- `PREPARANDO`;
- `SESION_ABIERTA`;
- presente/ausente;
- quórum alcanzado/no alcanzado;
- test activo;
- control habilitado/deshabilitado;
- estado conectado/stale.

No se exige copia pixel-perfect de producción.

La organización histórica puede utilizarse como referencia ergonómica, no contractual.

### 24. Autonomía local de UX

Quedan bajo autonomía técnica/visual reversible del implementador, siempre que se respeten los contratos anteriores:

- disposición exacta de campos dentro de Q1;
- tamaño relativo de controles;
- iconografía;
- uso de etiquetas/badges;
- forma de presentar los motivos de una capacidad;
- mecanismo concreto de guardado de autoridades;
- estilo del diálogo confirmatorio;
- animación concreta del test;
- breakpoint por debajo de 1366×768;
- tratamiento visual de imagen faltante.

Estas decisiones no autorizan:

- nuevas reglas de negocio;
- nuevos endpoints;
- cambios OpenAPI;
- dependencias externas;
- presencia manual;
- estado optimista autoritativo;
- modificación de las fronteras entre WP-022, WP-023 y WP-024.
