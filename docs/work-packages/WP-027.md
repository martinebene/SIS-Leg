# WP-027 - E2E críticos integrando backend, simulador y ambos frontends

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Incorporar una capa automatizada de pruebas **End-to-End (E2E) integradas** que verifique los recorridos institucionales críticos de SIS-Leg ejecutando juntos:

```text
Simulador CLI real
        ↓
HTTP /api/v1/entradas/tecla
        ↓
FastAPI real + dominio + auditoría + snapshots/SSE
        ↓
@sis-leg/api-client real
        ↓
Moderación real + Pantalla del Recinto real
        ↓
Playwright/Chromium
```

El objetivo no es reemplazar los tests unitarios, de backend, de componentes ni los Playwright deterministas existentes, sino cerrar el hueco entre ellos y los smokes manuales realizados durante WPs anteriores.

Al terminar WP-027, CI debe ejecutar automáticamente al menos un recorrido institucional crítico completo contra el stack real de desarrollo integrado por WP-033, sin mocks de backend, fetch, EventSource ni estado institucional.

## Qué significa E2E en este proyecto

Una prueba E2E de WP-027 debe atravesar interfaces reales entre componentes.

Ejemplo válido:

1. Playwright pulsa `Preparar sala` en Moderación.
2. FastAPI real crea la preparación.
3. Playwright observa el nuevo snapshot/SSE real.
4. El simulador CLI ejecuta `dev01-9`.
5. FastAPI real cambia presencia.
6. Moderación y Recinto reciben el nuevo estado por sus clientes reales.
7. Playwright comprueba el cambio en ambas interfaces.

No es E2E integrado si el test:

- inyecta directamente un `EstadoModeracion` o `EstadoRecinto` prefabricado;
- mockea `fetch`;
- mockea `EventSource`;
- llama servicios Python internos evitando HTTP;
- reemplaza el simulador por una función TypeScript que inventa pulsaciones;
- verifica solamente una SPA aislada.

Los Playwright actuales con backend controlado siguen siendo útiles y deben conservarse: son pruebas frontend deterministas, no el nuevo gate E2E integrado.

## Resultado esperado

El repositorio debe ofrecer dos niveles claramente separados:

### Nivel A — pruebas frontend deterministas existentes

Continúan ejecutándose mediante:

```bash
pnpm test:e2e
```

Pueden usar estados públicos/moderación controlados para:

- casos visuales;
- errores;
- responsive;
- fake clocks;
- escenarios de borde difíciles de producir con rapidez.

No deben degradarse ni desaparecer.

### Nivel B — E2E integrado real nuevo

Debe existir un comando canónico distinto, por ejemplo:

```bash
pnpm test:e2e:integrado
```

El nombre exacto puede variar solo si conserva una semántica inequívoca y queda documentado.

Ese comando debe:

- construir o reutilizar de forma reproducible las SPA;
- iniciar el harness real de WP-033 o la misma fábrica `crear_aplicacion_integrada()`;
- ejecutar un único proceso FastAPI/Uvicorn con el contrato real;
- abrir Moderación y Recinto bajo el mismo origen;
- usar el simulador CLI real;
- ejecutar Chromium mediante Playwright;
- completar los recorridos críticos;
- finalizar el stack;
- comprobar que no queda listener/proceso huérfano;
- devolver exit code distinto de cero ante cualquier fallo.

## Principio de diseño de la suite

La suite E2E integrada debe ser:

- **real** en fronteras institucionales;
- **pequeña**: probar recorridos críticos, no duplicar 847+ tests backend;
- **determinista** en datos y orden;
- **serializada** cuando comparte el único estado backend;
- **diagnosticable** al fallar;
- **reproducible** en `agent-dev` y GitHub Actions;
- **independiente de hardware físico**;
- **sin dependencias nuevas** salvo escalamiento DT-038;
- **sin cambiar reglas productivas para facilitar tests**.

## Arquitectura de ejecución esperada

### 1. Stack real y mismo origen

La prueba integrada debe usar:

```text
http://127.0.0.1:<puerto>/
├── /moderacion/
├── /recinto/
├── /api/v1/
└── /docs
```

Debe utilizar la misma aplicación integrada de WP-033.

No levantar:

- un backend falso;
- un servidor Node que intercepte `/api/v1`;
- CORS para separar orígenes;
- un segundo backend;
- Docker/Compose.

Se permite elegir un puerto de prueba distinto de 8000 para evitar colisiones, siempre ligado a loopback y documentado.

### 2. Ciclo de vida controlado por la prueba

La suite debe poder:

- iniciar el stack;
- esperar readiness mediante endpoint real;
- capturar stdout/stderr útiles;
- terminarlo incluso cuando un assert falle;
- verificar exit/cleanup;
- reiniciarlo cuando un escenario necesite comprobar CA-057.

Preferencia: que el runner de pruebas sea dueño explícito del proceso que inicia, para poder comprobar restart y cleanup.

No matar procesos ajenos por patrón global.

### 3. Un solo worker institucional

Los escenarios que mutan el mismo backend no pueden ejecutarse en paralelo.

El E2E integrado debe configurar explícitamente:

- un único worker o serialización equivalente;
- orden de preparación/limpieza claro;
- sin `fullyParallel` sobre un mismo estado.

Los Playwright deterministas existentes pueden conservar su paralelismo cuando no comparten backend real.

### 4. Dos vistas reales simultáneas

El recorrido principal debe mantener al menos:

- una página/contexto de Moderación;
- una página/contexto de Recinto.

Las dos consumen la misma instancia real.

La prueba debe observar propagación real mediante REST/SSE; no inyectar manualmente estados en una de las páginas.

### 5. Simulador real

Las entradas de dispositivo deben atravesar:

```bash
uv run python tools/device-simulator/simulador.py <pulsacion> --url http://127.0.0.1:<puerto>
```

o el modo `--escenario` real.

Puede existir un helper de tests que invoque el CLI mediante subprocess, pero no debe duplicar la semántica de teclas.

El helper debe:

- capturar exit code;
- capturar stdout/stderr;
- fallar con diagnóstico si el simulador falla;
- no importar servicios internos del backend.

### 6. Interacción de Moderación

Cuando una acción institucional pertenece al operador, el recorrido E2E principal debe ejecutarla desde la UI real siempre que sea razonable:

- Preparar sala;
- informar número/autoridades;
- Abrir sesión;
- carga/selección de Orden del Día;
- Abrir votación;
- Finalizar votación;
- Desempatar;
- Otorgar/Quitar palabra;
- Cerrar sesión.

No convertir el E2E principal en una colección de POST directos a FastAPI.

Se permiten consultas HTTP auxiliares para:

- readiness;
- verificar una propiedad de seguridad no observable por UI;
- diagnóstico;
- preparar casos secundarios cuyo foco no sea la UI de ese comando.

Toda excepción debe quedar justificada en código de test.

## Recorridos críticos obligatorios

### Recorrido 1 — arranque, preparación, presencia y sesión

Partiendo de proceso nuevo:

1. verificar `SIN_PREPARAR` en backend y ambas UI;
2. preparar sala desde Moderación;
3. verificar `PREPARANDO`;
4. comprobar que aparecen las 12 bancas/configuración de referencia;
5. enviar al menos una tecla `8` por simulador y observar el indicador de test si el timing resulta determinista;
6. acreditar mediante simulador los presentes necesarios para quórum;
7. verificar quórum en Moderación y Recinto;
8. cargar número de sesión, Presidencia y Secretaría desde UI;
9. abrir sesión desde UI;
10. verificar `SESION_ABIERTA` en backend y ambas UI.

La tecla `8` no debe convertir la suite en flaky: ver sección de estabilización temporal.

### Recorrido 2 — palabra y advertencia al abrir votación

Con sesión abierta:

1. un concejal presente pulsa `7` mediante simulador;
2. verificar cola real en Moderación y Recinto;
3. otorgar palabra desde Moderación;
4. comprobar orador en ambas interfaces;
5. intentar abrir votación;
6. verificar advertencia de palabra pendiente CA-062;
7. cancelar y confirmar que no se abrió votación;
8. intentar nuevamente;
9. confirmar advertencia;
10. comprobar que la votación se abre y el orador/cola no se alteran por esa confirmación.

### Recorrido 3 — secreto, voto ordinario, autocierre y revelado

Con votación SIMPLE `EN_CURSO`:

1. verificar metadata real en ambas interfaces;
2. verificar countdown público;
3. emitir votos por simulador;
4. antes del cierre:
   - Recinto no muestra votos;
   - Recinto no muestra conteos;
   - inspeccionar `GET /api/v1/estado/recinto` y confirmar que no transporta votos individuales;
5. comprobar el retardo de Moderación conforme deadline/configuración sin introducir timer propio;
6. completar votos de todos los presentes;
7. comprobar autocierre;
8. comprobar resultado ordinario;
9. verificar votos por banca en Recinto;
10. verificar conteos;
11. verificar que el resultado desaparece tras su deadline público.

Debe incluir al menos positivo, negativo y abstención.

### Recorrido 4 — empate y desempate presidencial

Abrir una SIMPLE que termine:

```text
positivos == negativos
```

con quórum.

Verificar:

1. resultado `EMPATADA`;
2. votos/conteos públicos;
3. otra apertura queda impedida;
4. esperar más que la ventana normal de resultado y confirmar que el empate sigue visible;
5. emitir desempate desde Moderación;
6. verificar resultado final;
7. verificar voto presidencial separado;
8. confirmar que conteos ordinarios no cambian;
9. confirmar expiración final posterior.

### Recorrido 5 — pérdida de quórum / INCONCLUSA

Con nueva votación `EN_CURSO`:

1. registrar uno o más votos;
2. retirar presencia mediante tecla `9` hasta quedar debajo del quórum;
3. comprobar finalización automática `INCONCLUSA`;
4. votos previos permanecen;
5. Recinto no inventa votos faltantes;
6. recuperar quórum y comprobar que esa votación no se reabre;
7. comprobar que una nueva votación puede abrirse cuando backend vuelve a habilitarlo.

Esto cubre prioritariamente CA-035 y CA-036 en integración real.

### Recorrido 6 — finalización manual por moción

Con votación `EN_CURSO`:

1. mantener palabra operativa;
2. emitir cero o algunos votos;
3. finalizar desde Moderación con motivo;
4. comprobar `INCONCLUSA`;
5. conservar votos parciales;
6. no calcular un resultado ordinario;
7. abrir luego otra votación válida.

Cobertura integrada principal: CA-034, CA-048 y CA-049.

### Recorrido 7 — Orden del Día como asistencia

Usar un fixture CSV versionado y canónico.

Verificar desde Moderación:

1. cargar archivo real mediante input de archivo;
2. backend lo acepta;
3. puntos aparecen;
4. seleccionar un punto;
5. sus datos se copian al formulario de votación;
6. editar al menos un dato permitido antes de abrir;
7. abrir una votación con esos datos finales;
8. el punto seleccionado no se convierte en autoridad institucional paralela.

No exigir secuencia ni unicidad de números.

### Recorrido 8 — cierre de sesión con palabra pendiente

Con orador o cola pendiente:

1. pulsar `Cerrar sesión`;
2. comprobar advertencia CA-063;
3. cancelar;
4. verificar sesión/palabra sin cambios;
5. volver a cerrar;
6. confirmar;
7. verificar retorno a `SIN_PREPARAR`;
8. Moderación y Recinto adoptan el nuevo estado real.

Cuando resulte razonable, realizar este caso con una votación `EN_CURSO` para verificar conjuntamente CA-042; si esa combinación vuelve el test excesivamente opaco, cubrir CA-042 en un recorrido separado pequeño.

### Recorrido 9 — reinicio técnico

Durante una preparación o sesión real:

1. confirmar estado distinto de `SIN_PREPARAR`;
2. detener limpiamente el proceso del stack;
3. iniciar una nueva instancia sobre la misma working copy/configuración;
4. comprobar que backend vuelve a `SIN_PREPARAR`;
5. recargar/reconectar Moderación y Recinto;
6. comprobar que ninguna UI reconstruye la sesión anterior desde su estado local;
7. confirmar que los CSV previos no se utilizan para recovery.

Cobertura principal: CA-057 y CU-28.

## Cobertura que NO debe forzarse dentro del E2E integrado

No convertir esta suite en una duplicación de todos los criterios CA-001..CA-063.

Pueden seguir cubiertos primordialmente por tests backend/unit/componentes:

- validaciones exhaustivas de esquemas inválidos;
- matriz completa de mayoría especial y floating point;
- todas las variantes de errores HTTP;
- concurrencia de bajo nivel;
- fallos inyectados de fsync;
- allowlists de serialización campo por campo.

WP-027 debe seleccionar caminos institucionales representativos y conservar las pruebas propietarias existentes.

## Remapeo y hardware

WP-027 depende de WP-024 porque el frontend final debe coexistir correctamente, pero **no** debe fingir una validación física del remapeo.

El harness de WP-033 no inicia el device-bridge físico.

Por lo tanto:

- conservar tests deterministas de WP-024 para UI/contrato de remapeo;
- no agregar un bridge falso al E2E principal sólo para obtener un “verde”;
- no usar `evdev` falso como sustituto de hardware real;
- la validación bridge + numpads físicos pertenece a WP-029.

Si puede verificarse alguna propiedad de remapeo sin falsear la frontera física, puede añadirse como caso secundario, pero no es requisito de aprobación de WP-027.

## Auditoría en E2E

La suite integrada debe verificar mínimamente que las mutaciones críticas generan persistencia real, sin duplicar todos los tests de auditoría.

Como mínimo:

1. obtener listado/tamaño inicial de los archivos de auditoría relevantes;
2. después de preparar/abrir/votar, comprobar que existe el nuevo conjunto de logs;
3. comprobar que al menos eventos críticos esperados quedan persistidos;
4. tras cerrar/cancelar, comprobar que los archivos cerrados no son reutilizados para una nueva preparación.

No borrar logs preexistentes de un entorno de desarrollo.

En CI, donde el checkout parte limpio, la suite puede trabajar con el directorio `logs/` normal ignorado.

La verificación debe apoyarse en el formato canónico, no en sleeps arbitrarios: las mutaciones confirmadas ya exigen persistencia síncrona.

## Estabilización de la flake temporal de test_activo

WP-026 registró una flake preexistente:

`tests/backend/test_api_estado.py::test_rest_preparando_y_sesion_abierta_reconstruyen_todo_el_contexto`

El test activa una señal con:

```text
device_test_seconds = 0.6
```

y realiza varias operaciones reales antes de afirmar `test_activo`.

En CI bajo contienda, el indicador puede expirar legítimamente antes del assert.

WP-027 **autoriza estabilizar ese test** porque es trabajo de infraestructura de pruebas directamente relacionado con la confiabilidad del nuevo gate.

La corrección debe:

- no aumentar `device_test_seconds` productivo sólo para tests;
- no cambiar semántica backend;
- preferir reloj/monotónico inyectado, aserción inmediata, fixture controlado o separación de responsabilidades;
- no ocultar un fallo real mediante retry interno;
- dejar una prueba determinista.

Si para estabilizarlo fuese necesario cambiar API productiva o arquitectura de relojes, escalar DT-038 antes de continuar esa parte.

## Playwright integrado: separación de configuración

Preferir una configuración/ubicación distinta para el E2E real, por ejemplo:

```text
tests/playwright/                 # frontend determinista existente
tests/playwright-integrado/       # stack real
playwright.config.ts
playwright.integrado.config.ts
```

Los nombres exactos son autonomía local.

Debe quedar imposible confundir:

- `pnpm test:e2e`;
- `pnpm test:e2e:integrado`.

La configuración integrada debe:

- usar loopback;
- un único worker;
- timeouts razonables para procesos reales;
- traces/screenshots/video o artefactos útiles ante fallo según capacidades existentes;
- no usar retries como mecanismo para esconder flakes de producto;
- limpiar procesos siempre.

En CI puede permitirse un retry de infraestructura únicamente si la política general lo justifica, pero la suite debe ser determinista sin depender de él.

## Seguridad del secreto

El E2E integrado debe verificar CA-050 en dos niveles:

1. DOM del Recinto durante `EN_CURSO`;
2. respuesta de red real de `GET /api/v1/estado/recinto`.

No alcanza con ocultar por CSS.

Si el payload contiene un voto individual durante `EN_CURSO`, la prueba debe fallar aunque el DOM lo oculte.

## SSE y reconexión

La suite debe comprobar al menos un caso donde:

- ambos frontends reciben cambios reales sin polling;
- se interrumpe/reestablece una conexión o se reinicia el backend;
- una baseline nueva reemplaza estado previo;
- revisión 0 después de restart es aceptada.

No hace falta inspeccionar números de revisiones contiguos: el contrato no exige continuidad.

## Timeouts y esperas

Evitar `sleep(N)` largos como mecanismo principal.

Preferir:

- `expect(...).toPass()`/esperas de Playwright sobre condición observable;
- esperar endpoints/listeners;
- deadlines reales expuestos por el backend;
- eventos de UI;
- polling **del test** sobre readiness/condición técnica cuando sea inevitable.

La prohibición de polling del producto no impide que un test espere técnicamente una condición, pero esa espera debe tener timeout explícito y no ocultar un bug de propagación.

Los timers institucionales 4 s / 6 s pueden recorrerse en E2E real porque se está probando la integración temporal real. Mantener esos recorridos acotados para que la suite no se vuelva innecesariamente lenta.

## Diagnóstico de fallos

Ante fallo del E2E integrado, CI debe dejar evidencia suficiente para identificar la frontera afectada.

Como mínimo, cuando sea posible:

- paso/recorrido fallido;
- stdout/stderr del stack;
- stdout/stderr del simulador;
- screenshot/trace Playwright;
- URL/estado esperado;
- exit code del proceso.

Nunca imprimir secretos/credenciales.

## Invariantes y restricciones

- Estado en memoria sigue siendo volátil.
