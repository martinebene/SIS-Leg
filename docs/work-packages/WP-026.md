# WP-026 - Experiencia pública de votación, secreto, revelado, resultados y temporizadores

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Completar la Pantalla del Recinto para representar de punta a punta la experiencia pública de una votación utilizando exclusivamente el `EstadoRecinto` autoritativo ya publicado por FastAPI:

- información general de la votación mientras está `EN_CURSO`;
- cuenta regresiva/efecto inicial derivado del deadline backend;
- secreto estricto de votos individuales durante toda la recepción;
- revelado por banca una vez cerrada;
- conteos y resultado institucional;
- `EMPATADA` pendiente de Presidencia;
- resultado posterior a desempate presidencial;
- `INCONCLUSA`;
- permanencia transitoria del resultado;
- limpieza automática de esa presentación;
- reconexión/reload sin reiniciar temporizadores ni revivir resultados expirados.

El frontend debe **representar** el contrato temporal existente, no recalcular resultado, mayoría, quórum, cierre, secreto ni deadlines institucionales.

## Resultado esperado

Al completar WP-026, `apps/recinto/` debe transformar el shell público integrado en WP-025 en una experiencia pública completa de votación.

Durante una votación `EN_CURSO`:

- se muestra de forma prominente qué se está votando;
- puede mostrarse el efecto/cuenta regresiva inicial;
- ninguna banca muestra el sentido de un voto;
- no se muestran conteos que el DTO público no habilita;
- palabra, quórum y demás estado público siguen coexistiendo con la votación.

Cuando la recepción deja `EN_CURSO`:

- cada voto ordinario recibido se asocia a su banca;
- se muestran los conteos autoritativos recibidos;
- se muestra inequívocamente `APROBADA`, `RECHAZADA`, `EMPATADA` o `INCONCLUSA`;
- un voto presidencial de desempate se representa separado de los votos ordinarios;
- una banca sin voto ordinario no recibe un valor inventado;
- `EMPATADA` permanece mientras el backend la siga publicando;
- un resultado final desaparece cuando vence su deadline público/backend deja de publicarlo;
- una nueva votación sustituye inmediatamente cualquier presentación anterior.

El frontend nunca necesita inspeccionar auditoría, DTOs de Moderación ni estado de dominio privado.

## Alcance

### 1. Componente público de votación

Incorporar una representación específica de `EstadoRecinto.votacion` dentro del shell público.

Cuando `votacion != null`, debe mostrar como mínimo:

- `numero_votacion`;
- `tipo`;
- `tema`;
- estado de recepción/resultado en lenguaje público claro;
- información de mayoría cuando aporte contexto, derivada directamente de:
  - `tipo_mayoria`;
  - `factor`;
  - `base`.

La UI puede convertir enums a etiquetas humanas, pero no inferir ni recalcular reglas.

Ejemplos conceptuales permitidos:

- `SIMPLE` → “Mayoría simple”;
- `ESPECIAL` → “Mayoría especial” y su factor/base recibidos.

No calcular el resultado ni porcentajes de aprobación a partir de esos campos.

### 2. Votación EN_CURSO

Mientras:

```text
votacion.estado_recepcion == EN_CURSO
```

la pantalla debe:

- identificar inequívocamente que la votación está en curso;
- mostrar número/tipo/tema;
- conservar quórum y uso/pedidos de palabra;
- no mostrar voto individual alguno;
- no atribuir visualmente “votó/no votó” a una banca usando información no provista;
- no mostrar conteos inventados;
- no reconstruir el total de votos mediante otro endpoint;
- no consultar Moderación;
- no consumir auditoría ni eventos crudos.

En el contrato vigente, `votos_individuales` y `conteos` son `null` durante `EN_CURSO`. El frontend debe tratar esa ausencia como frontera de seguridad, no como un campo que deba completar desde otra fuente.

### 3. Cuenta regresiva pública inicial

Si `cuenta_regresiva_hasta` es futura, mostrar una cuenta regresiva/efecto inicial prominente.

Referencia UX aprobada para este WP: **overlay visual sobre la zona del recinto**, preservando la identidad/contexto general de la votación.

Reglas:

- el frontend no usa una constante local de 4 segundos;
- no inicia un nuevo “4” al recibir un snapshot/SSE;
- el deadline autoritativo es `cuenta_regresiva_hasta`;
- `generado_en` puede utilizarse como referencia temporal del backend para evitar depender innecesariamente del desfase del reloj del cliente;
- el decremento visible puede realizarse localmente;
- no se consulta el backend una vez por segundo;
- no se emite ninguna mutación;
- al vencer, desaparece el overlay aunque la votación continúe;
- el fin del countdown **no** habilita votos ni conteos públicos.

El texto/número exacto del overlay puede resolverse localmente si es inequívoco y accesible.

No usar el polling como mecanismo de temporización.

### 4. Votos individuales después del cierre

Cuando el backend entregue `votos_individuales`, asociarlos a las bancas exclusivamente mediante `VotoPublico.banca`.

No usar posición del array de votos ni del array de concejales como identidad.

Cada voto recibido debe tener representación textual inequívoca además del color:

- `POSITIVO` → “Positivo” + semántica visual verde;
- `NEGATIVO` → “Negativo” + semántica visual roja;
- `ABSTENCION` → “Abstención” + semántica visual amarilla.

El color por sí solo no cumple accesibilidad.

Una banca sin entrada correspondiente en `votos_individuales`:

- conserva sus estados públicos normales;
- no recibe un voto ficticio;
- no debe ser contabilizada localmente como abstención, ausencia ni negativo.

Esto es especialmente importante para `INCONCLUSA` con recepción parcial.

### 5. Coexistencia de voto, presencia, test y palabra

El nuevo estado visual de voto no puede destruir ni ocultar semánticamente:

- presencia/ausencia;
- test activo;
- condición de orador;
- número/identidad de banca.

La implementación puede usar fondos, bordes, badges o regiones internas, pero debe permitir que los estados simultáneos continúen siendo comprensibles.

No adoptar una precedencia CSS que haga desaparecer silenciosamente el voto cuando exista test/orador, ni viceversa.

### 6. Conteos

Cuando `votacion.conteos != null`, mostrar los valores recibidos:

- `positivos`;
- `negativos`;
- `abstenciones`;
- `total`.

No recontar los votos individuales para producir la fuente mostrada.

Puede comprobarse en tests que los datos sean coherentes, pero la UI debe consumir `conteos` como autoridad de presentación.

El voto presidencial no incrementa ninguno de esos cuatro valores.

### 7. Resultado institucional

La UI debe distinguir claramente:

- `APROBADA`;
- `RECHAZADA`;
- `EMPATADA`;
- `INCONCLUSA`.

Etiquetas públicas mínimas:

- “Aprobada”;
- “Rechazada”;
- “Empatada”;
- “Inconclusa”.

El resultado debe ser más prominente que información técnica de recepción.

No derivar `APROBADA/RECHAZADA/EMPATADA/INCONCLUSA` desde los conteos. Mostrar exclusivamente `votacion.resultado`.

### 8. EMPATADA

Mientras el backend publique la misma votación con:

```text
estado_recepcion = CERRADA
resultado = EMPATADA
```

la pantalla debe:

- mantener visibles sus votos ordinarios;
- mantener conteos;
- mostrar inequívocamente “Empatada”;
- indicar de forma pública clara que está pendiente de desempate presidencial;
- no iniciar una expiración local de seis segundos;
- no inventar ni inferir el sentido del futuro voto presidencial.

Una pérdida posterior de quórum no altera esta representación mientras el backend conserve `EMPATADA`.

### 9. Desempate presidencial

El campo público `voto_presidencial` sólo se representa cuando el backend lo exponga.

Debe mostrarse de forma **separada** de:

- bancas;
- `votos_individuales`;
- `conteos`.

Mostrar como mínimo:

- que existió desempate presidencial;
- `presidencia`;
- sentido `POSITIVO|NEGATIVO` en etiqueta humana.

No:

- agregar ese voto a una banca;
- incrementar conteos ordinarios;
- alterar visualmente un voto de concejal;
- inferirlo durante un estado parcial donde backend lo omite.

Después del desempate, el resultado final sigue viniendo de `votacion.resultado`.

### 10. INCONCLUSA

`INCONCLUSA` debe ser visualmente distinta de:

- empate;
- rechazo;
- ausencia de votación.

Puede coexistir con una lista parcial o vacía de votos ordinarios.

La UI no debe explicar una causa que el DTO público no contenga. En particular, no inventar si fue por pérdida de quórum, finalización manual o cierre de sesión.

### 11. Permanencia pública del resultado

Para `APROBADA`, `RECHAZADA` o `INCONCLUSA`, `resultado_visible_hasta` define la vigencia de la presentación transitoria.

Reglas:

- no usar una constante local de 6 segundos;
- no iniciar seis segundos desde la recepción del snapshot;
- no reiniciar la ventana por SSE/reconexión;
- la UI puede derivar localmente si el deadline ya venció para no mantener una presentación obsoleta durante una desconexión;
- el backend sigue siendo quien retira la votación del DTO y publica la revisión correspondiente;
- una reconexión posterior al deadline no revive el resultado;
- una nueva votación sustituye inmediatamente el resultado anterior.

Si `resultado_visible_hasta` es `null` en `EMPATADA`, no aplicar expiración local.

### 12. Estado local permitido para presentación temporal

Se permite estado Vue **exclusivamente de presentación**, por ejemplo:

- instante local de referencia;
- número visible del countdown;
- ticker/timeout cancelable;
- indicador de overlay.

Ese estado:

- no guarda historia institucional;
- no guarda votos que el backend ya retiró;
- no calcula resultados;
- no modifica el `EstadoRecinto`;
- debe cancelarse al desmontar;
- debe reaccionar correctamente cuando cambia el id/deadline de la votación;
- no debe reiniciarse de forma incorrecta ante un nuevo payload de la misma votación.

Preferir un mecanismo eficiente que sólo esté activo mientras existe una frontera temporal relevante.

### 13. Reconexión y baseline

Conservar la política integrada en WP-025:

- último snapshot confirmado durante una reconexión;
- indicador de conexión degradada;
- nueva baseline completa reemplaza la anterior.

Sobre esa baseline:

- un countdown ya expirado no se reinicia;
- un resultado ya expirado no se revive;
- una votación nueva reemplaza cualquier UI temporal anterior;
- revisión 0 tras restart vuelve a obedecer `SIN_PREPARAR`;
- estado temporal local asociado a una votación anterior debe limpiarse.

### 14. Palabra durante votación

La experiencia de votación no puede ocultar o inutilizar la información pública de palabra.

Durante `EN_CURSO`, `CERRADA`, `EMPATADA` y la ventana de resultado:

- orador actual sigue visible;
- cola FIFO sigue visible;
- resaltado de banca del orador sigue disponible.

Si el layout necesita priorizar un resultado prominente, puede reorganizar paneles responsivamente, pero no eliminar información de palabra autoritativa.

### 15. Quórum durante votación

El indicador de quórum sigue consumiendo exclusivamente `EstadoRecinto.quorum`.

No recalcular quórum desde:

- concejales;
- cantidad de votos;
- `conteos.total`.

Una votación `INCONCLUSA` puede coexistir con quórum actualmente no alcanzado; ambos estados deben poder entenderse sin que la UI intente recomputar causalidad.

### 16. Eventos públicos

WP-026 **no necesita agregar eventos públicos** para cumplir la experiencia.

El `EstadoRecinto` vigente no transporta eventos crudos y eso es aceptable.

No agregar eventos de Moderación/auditoría a la pantalla para enriquecer el resultado.

Si se considera imprescindible un nuevo evento público o campo backend, detener esa parte y escalar: el contrato actual debe asumirse suficiente salvo evidencia contraria.

### 17. No modificar backend/OpenAPI por iniciativa propia

La implementación vigente de `VotacionPublica` ya entrega:

- metadata de votación;
- estado de recepción;
- resultado;
- `cuenta_regresiva_hasta`;
- `resultado_visible_hasta`;
- `votos_individuales`;
- `conteos`;
- `voto_presidencial`.

Por diseño de este WP, no se esperan modificaciones a:

- backend;
- dominio;
- endpoints;
- OpenAPI;
- tipos generados.

Si el implementador detecta que un criterio **realmente** no puede cumplirse con el DTO vigente, debe:

1. no ampliar el DTO unilateralmente;
2. describir el caso exacto;
3. demostrar por qué el contrato actual es insuficiente;
4. escalar según DT-038.

### 18. Responsive

Mantener la referencia de WP-025 y DT-020:

- 1920×1080 Full HD;
- 1366×768.

Durante countdown y resultado:

- no debe haber solapamientos que oculten voto/resultado;
- el tema debe seguir siendo legible o truncarse de forma controlada con acceso al texto completo cuando corresponda;
- las bancas deben conservar identificación;
- palabra/quórum deben seguir utilizables visualmente;
- no introducir scroll global innecesario en Full HD.

El resultado puede modificar temporalmente la jerarquía visual, pero no depender de coordenadas absolutas rígidas.

## Invariantes y restricciones

- FastAPI es la única autoridad institucional.
- `EstadoRecinto` es la única fuente institucional del Recinto.
- El secreto durante `EN_CURSO` se garantiza en servidor y la UI no intenta sortearlo.
- REST snapshot + SSE siguen siendo el transporte.
- Sin polling periódico.
- Sin WebSocket.
- Sin Pinia.
- Sin estado institucional optimista.
- Sin cálculo local de mayoría/resultado/quórum.
- Voto presidencial separado de votos ordinarios.
- Temporizadores de frontend exclusivamente presentacionales y derivados de deadlines backend.
- Una nueva baseline manda sobre cualquier estado temporal local.
- No nuevas dependencias directas por iniciativa propia.
- No cambios backend/OpenAPI por iniciativa propia.
- Código/idioma/comentarios conforme DEC-001.
- Herramientas/fallbacks conforme DEC-003.
- Entorno/agentes conforme DEC-007.
- Handoffs conforme DEC-017.
- DT-038 aplica ante cualquier ampliación de contrato o arquitectura.
