# WP-020 - Remapeo rápido físico a dispositivo lógico coordinado por backend

## Estado documental

`APROBADO`

## Objetivo

Implementar el flujo coordinado de remapeo rápido de un teclado físico hacia un identificador lógico `devXX` existente, iniciado desde Moderación a través de FastAPI y ejecutado por el `device-bridge`, permitiendo al operador confirmar el cambio como `TEMPORAL` o `PERSISTENTE` sin interrumpir el tráfico normal de los demás dispositivos ni alterar identidad, presencia, votos o palabra.

## Resultado esperado

Al integrar este WP debe existir un contrato backend/bridge completo y testeable que permita:

- iniciar una única operación de remapeo para un `devXX` del padrón activo;
- mantener funcionando normalmente todos los fingerprints ya mapeados mientras el bridge espera candidato;
- capturar exclusivamente un fingerprint elegible no mapeado mediante su primer `keydown`;
- exponer el candidato en `EstadoModeracion` y propagar su cambio mediante REST snapshot + SSE;
- cancelar sin mutar mapping;
- confirmar el candidato eligiendo `TEMPORAL` o `PERSISTENTE`;
- aplicar un cambio temporal solo en memoria del bridge;
- aplicar un cambio persistente mediante reemplazo atómico y validado de `devices.json`;
- auditar antes de autorizar cualquier aplicación confirmada;
- reconciliar comandos de control mediante un `remapeo_id` idempotente;
- conservar íntegramente las reglas de negocio en FastAPI.

La UI visual de Moderación no se implementa todavía: este WP entrega contratos, estado y tipos para que la interfaz posterior los consuma.

## Dependencias

- WP-019 `INTEGRADO`: bridge físico Linux, fingerprint, mapping efectivo, `devices.json` y captura `evdev` ya disponibles.
- WP-017 `INTEGRADO`: `EstadoModeracion`, revisión monotónica y SSE ya disponibles para publicar el estado del remapeo.
- WP-018 `INTEGRADO`: OpenAPI versionado y `api-client` TypeScript derivado ya disponibles para mantener sincronizado el nuevo contrato REST.

## Alcance

### 1. Estado de remapeo en backend

Incorporar al estado operativo del backend una única operación de remapeo activa, con identidad `remapeo_id` UUID y datos mínimos para Moderación.

El estado distingue conceptualmente al menos captura en curso, candidato físico disponible y confirmación/aplicación en progreso cuando corresponda.

No se persiste como sesión recuperable después de reiniciar FastAPI: el backend sigue usando estado operativo en memoria conforme DT-004/DT-009.

### 2. Estados permitidos

Permitir iniciar remapeo únicamente en `PREPARANDO` y `SESION_ABIERTA`, incluida una votación activa.

En `SIN_PREPARAR` se rechaza con error funcional estable. El backend valida que el `devXX` solicitado pertenece al padrón activo/congelado. No se crean dispositivos lógicos nuevos mediante este flujo.

### 3. Contrato REST Moderación/backend

Implementar:

```text
POST   /api/v1/remapeos
POST   /api/v1/remapeos/{remapeo_id}/confirmacion
DELETE /api/v1/remapeos/{remapeo_id}
```

Inicio:

```json
{
  "dispositivo": "dev05"
}
```

Confirmación:

```json
{
  "persistencia": "TEMPORAL"
}
```

`persistencia` admite exclusivamente `TEMPORAL` o `PERSISTENTE`. Los bodies son cerrados (`extra="forbid"`) y usan tipos estrictos.

Los errores funcionales/técnicos deben distinguir como mínimo estado incompatible, dispositivo inexistente en padrón activo, otro remapeo activo, ID no coincidente, confirmación sin candidato, bridge no disponible, aplicación/persistencia rechazada y auditoría no disponible.

### 4. Endpoint interno bridge -> backend

Implementar un endpoint interno vinculado a `remapeo_id` para que el bridge informe el candidato capturado. Solo acepta candidato de la operación activa y nunca aplica el remapeo. El frontend no consume este endpoint.

### 5. API de control local del bridge

Agregar un servidor HTTP de control usando exclusivamente biblioteca estándar de Python. Escucha en loopback por defecto y permite configurar host/puerto.

La superficie versionada permite como mínimo:

- iniciar captura para `{remapeo_id, devXX}`;
- consultar estado por `remapeo_id` para reconciliación;
- confirmar/aplicar el fingerprint candidato esperado con `TEMPORAL|PERSISTENTE`;
- cancelar.

Los paths exactos deben quedar documentados y testeados. No agregar FastAPI, Flask, aiohttp ni otro framework al bridge.

### 6. Idempotencia de control

El mismo `remapeo_id` identifica toda la operación. Repetir el mismo comando con el mismo ID y parámetros debe ser seguro y no aplicar dos veces. El mismo ID con parámetros incompatibles debe rechazarse.

Una respuesta perdida no puede crear un segundo remapeo ni provocar doble aplicación. El backend puede consultar el estado del bridge para reconciliar.

Esta idempotencia corresponde solo a control: las pulsaciones físicas normales conservan máximo un intento HTTP y cero retry/replay según WP-019.

### 7. Captura concurrente con operación normal

El modo captura no detiene ni intercepta indebidamente los dispositivos ya mapeados.

Durante `CAPTURANDO` o `CANDIDATO`:

- las pulsaciones de fingerprints efectivamente mapeados continúan por el flujo normal y llegan al backend;
- un fingerprint mapeado nunca puede convertirse en candidato;
- presencia, voto, test o palabra continúan operando en los demás dispositivos;
- `keyup` y autorepeat siguen excluidos;
- el candidato surge únicamente de un `keydown` de fingerprint elegible no mapeado.

La implementación debe ser thread-safe/serializada entre API de control y loop de captura física.

### 8. Elegibilidad exacta del candidato

Un fingerprint puede ser candidato para el `devXX` objetivo solamente si:

1. no forma parte del mapping efectivo vigente de ningún dispositivo lógico; y
2. si aparece en `devices.json`, está asociado al mismo `devXX` objetivo.

Esto permite volver al fingerprint base después de un remapeo temporal, pero impide apropiarse del fingerprint base de otro dispositivo lógico.

El primer candidato elegible queda congelado hasta confirmar o cancelar. Otro dispositivo desconocido no lo reemplaza silenciosamente.

### 9. Remapeo temporal

Al confirmar `TEMPORAL`:

- reemplazar el fingerprint efectivo del `devXX` solo en memoria;
- dejar `devices.json` sin modificar;
- conservar todas las demás asociaciones;
- mantener el override hasta reinicio del bridge o hasta otro remapeo del mismo `devXX`;
- no revertir automáticamente por cerrar sesión o cancelar preparación;
- al reiniciar el bridge, reconstruir el mapping únicamente desde `devices.json`, eliminando el override temporal.

Debe poder volver al fingerprint base mediante un nuevo remapeo del mismo `devXX`.

### 10. Remapeo persistente

Al confirmar `PERSISTENTE`:

- construir un nuevo mapping base completo;
- retirar la asociación base anterior del `devXX` objetivo;
- asociar el candidato al mismo `devXX`;
- conservar sin cambios el resto;
- validar con las mismas invariantes de `devices.json`;
- escribir mediante archivo temporal en el mismo directorio, `flush`/`fsync` y reemplazo atómico;
- instalar el nuevo mapping efectivo solo después de persistencia exitosa.

Ante cualquier fallo, `devices.json` anterior y mapping efectivo anterior deben conservarse. No se degrada silenciosamente a temporal. Tras reinicio, el nuevo fingerprint persistente debe seguir asociado al mismo `devXX`.

### 11. Auditoría previa a aplicar

Antes de autorizar al bridge a modificar el mapping, el backend persiste un evento L3 obligatorio de autorización humana con al menos:

- `remapeo_id`;
- dispositivo lógico objetivo;
- fingerprint efectivo anterior conocido;
- fingerprint candidato;
- persistencia seleccionada.

El evento representa autorización, no afirma que el cambio ya fue aplicado. Si la auditoría falla, responder `503 AUDITORIA_NO_DISPONIBLE`, no enviar la orden al bridge y no modificar mapping.

### 12. Fallos y reconciliación

Distinguir bridge inaccesible al iniciar/confirmar, rechazo técnico, timeout con resultado incierto, persistencia fallida y operación ya aplicada/cancelada.

Ante respuesta perdida tras confirmar, usar `remapeo_id` y consulta de estado para resolver si se aplicó, sin crear nuevo ID ni reaplicar a ciegas. No implementar rollback distribuido automático.

### 13. Proyección Moderación y SSE

Extender `EstadoModeracion` con submodelo explícito suficiente para mostrar ID, `devXX`, estado, candidato e información diagnóstica física segura.

No incluir remapeo/fingerprint en `EstadoRecinto`. Cada transición relevante incrementa revisión y se propaga por SSE canónico, sin polling.

### 14. OpenAPI y api-client

Actualizar snapshot OpenAPI y regenerar tipos TypeScript conforme DEC-014. Agregar al `ClienteModeracion` operaciones públicas de remapeo necesarias para la futura UI.

El endpoint interno bridge->backend no se expone como método de alto nivel de Moderación. `ClienteRecinto` continúa read-only y no expone remapeo.

### 15. Concurrencia backend

Las mutaciones de remapeo respetan el único `EjecutorMutaciones`; no crean una vía paralela frente a voto/presencia/palabra.

Una pulsación que llega como `dev05` antes o después del cambio sigue siendo `dev05`; el remapeo nunca cambia retroactivamente identidad ni hechos previos.

### 16. Dependencias

No agregar nuevas dependencias directas Python, TypeScript o runtime. Usar biblioteca estándar para control HTTP local, UUID, sincronización y persistencia atómica. Cualquier necesidad adicional requiere escalamiento DT-038.

### 17. Logging

El bridge debe registrar inicio/cancelación, candidato, rechazos de candidatos no elegibles, confirmación temporal/persistente, persistencia exitosa/fallida, reconciliación/idempotencia y fin de operación. Estos logs no reemplazan auditoría institucional backend.

## Criterios de aceptación

1. El remapeo solo puede iniciarse con preparación activa o sesión abierta.
2. Backend valida que el `devXX` pertenece al padrón activo.
3. Solo existe una operación activa con `remapeo_id` UUID estable.
4. Navegador nunca se comunica directamente con bridge.
5. API de control escucha loopback por defecto y no agrega dependencia.
6. Fingerprints mapeados continúan transmitiendo normalmente durante captura.
7. Ningún fingerprint efectivamente mapeado puede ser candidato.
8. Primer fingerprint elegible queda candidato y no se transmite como pulsación normal.
9. Configuración base de otro `devXX` nunca puede apropiarse como candidato.
10. Fingerprint base del mismo objetivo puede recuperar un remapeo temporal.
11. Cancelar no modifica mapping ni `devices.json`.
12. Confirmar exige `TEMPORAL` o `PERSISTENTE`.
13. `TEMPORAL` modifica solo memoria y desaparece tras reinicio del bridge.
14. `TEMPORAL` no se revierte al cerrar sesión/cancelar preparación.
15. `PERSISTENTE` reemplaza solo la entrada física del `devXX` objetivo.
16. Persistencia es atómica/validada y su fallo conserva archivo/mapping anteriores.
17. Persistente sobrevive reinicio del bridge.
18. Antes de aplicar existe evento L3 durable de autorización con ID, fingerprints, devXX y persistencia.
19. Auditoría no disponible impide aplicar.
20. Comandos de control son idempotentes y una respuesta perdida puede reconciliarse sin doble aplicación.
21. Presencia, votos, identidad y palabra permanecen inalterados.
22. `EstadoModeracion` refleja operación/candidato; `EstadoRecinto` no expone información física.
23. REST snapshot + SSE continúan siendo la sincronización; no polling.
24. OpenAPI/api-client quedan sincronizados; `ClienteModeracion` expone comandos y `ClienteRecinto` no.
25. No se agregan dependencias directas.
26. Suite completa funciona sin hardware real, sin destruir configuración versionada y sin red externa.
27. Código nuevo respeta DEC-001 y documenta pedagógicamente flujos no triviales.

## Pruebas obligatorias

### Backend

- `SIN_PREPARAR` rechaza inicio;
- `PREPARANDO` y `SESION_ABIERTA` aceptan;
- inicio durante votación activa no altera votación;
- `devXX` inexistente rechazado;
- segundo remapeo simultáneo rechazado;
- callback candidato con ID incorrecto rechazado;
- candidato actualiza `EstadoModeracion` y revisión/SSE;
- confirmación sin candidato rechazada;
- persistencia enum estricta y bodies cerrados;
- cancelación limpia;
- auditoría ocurre antes de ordenar aplicación;
- fallo de auditoría evita invocar bridge;
- timeout/respuesta perdida usa consulta de estado/idempotencia;
- presencia, votos y palabra invariantes antes/después.

### Bridge

- servidor de control ligado a loopback/configurable usando puerto efímero/fakes;
- inicio idempotente por ID;
- ID repetido con otro `devXX` rechazado;
- dispositivos mapeados siguen enviando mientras captura está activa;
- pulsar un mapeado nunca genera candidato;
- primer no mapeado elegible genera candidato;
- candidato posterior no reemplaza al primero;
- base del mismo objetivo elegible bajo override temporal;
- base de otro objetivo no elegible;
- `TEMPORAL` cambia mapping efectivo y no toca archivo;
- recreación/reinicio elimina override temporal;
- `PERSISTENTE` reemplaza exactamente el fingerprint objetivo;
- persistencia usa temporal/reemplazo atómico;
- error de escritura/fsync/replace conserva mapping/archivo anterior;
- reinicio carga mapping persistente;
- confirmación repetida no duplica escritura/cambio;
- cancelación no altera mapping;
- keyup/repeat continúan fuera de captura.

### Contratos/api-client

- endpoints backend y modelos OpenAPI;
- drift check OpenAPI/tipos;
- métodos públicos de `ClienteModeracion`;
- ausencia de mutaciones en `ClienteRecinto`;
- proyección pública sin fingerprint/remapeo.

- `fingerprint -> devXX -> concejal` conserva DT-014/DEC-015.
- `devXX -> concejal` nunca cambia mediante remapeo.
- dispositivos mapeados siguen operativos durante captura.
- votos aceptados continúan irreversibles.
- bridge no incorpora reglas de negocio.
- no conexión directa navegador -> bridge.
- no dependencias directas nuevas sin DT-038.
- no retries/replay de pulsaciones.
- `devices.json` solo puede modificarse por confirmación humana explícita `PERSISTENTE` y escritura segura.
