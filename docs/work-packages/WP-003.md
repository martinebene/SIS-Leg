# WP-003 - Configuración y padrón: carga, validación y congelamiento

## Estado documental

`APROBADO`

## Objetivo

Implementar la carga y validación técnica de `config/system.toml` y `config/concejales.csv`, produciendo snapshots inmutables utilizables por una futura preparación.

## Resultado esperado

El backend puede cargar una configuración válida y un padrón válido, rechazar errores definidos y entregar objetos inmutables que no cambian aunque los archivos de disco sean modificados después de la carga.

Este WP no cambia todavía el estado global a `PREPARANDO`; esa integración corresponde a WP-005.

## Alcance

### `config/system.toml`

Implementar este esquema tipado mínimo canónico:

```toml
[session]
quorum = 7

[room]
rows = [3, 4, 5]

[voting]
types = ["Ratificación", "Despacho OP", "Despacho Gob", "Despacho AS", "Despacho HA", "Despacho Eco", "Mocion", "P. Sobre Tabla", "Otro"]

[timers]
moderation_vote_reveal_seconds = 4
public_initial_countdown_seconds = 4
public_result_display_seconds = 6

[paths]
logs_dir = "logs"
```

Reglas técnicas:

- `session.quorum`: entero positivo;
- `room.rows`: lista no vacía de enteros positivos;
- `voting.types`: lista de textos no vacíos; preservar el orden configurado;
- temporizadores: números no negativos;
- `paths.logs_dir`: ruta no vacía interpretada por backend, sin crear todavía archivos de auditoría.

No agregar otros campos por conveniencia sin necesidad documentada.

### `config/concejales.csv`

Encabezado canónico exacto:

```text
dni,nombre,apellido,bloque,banca,dispositivo_votacion,ruta_imagen
```

Reglas:

- `dni`: identificador textual obligatorio, trim, único;
- `nombre`: obligatorio tras trim;
- `apellido`: obligatorio tras trim;
- `bloque`: puede quedar vacío;
- `banca`: entero positivo y único;
- `dispositivo_votacion`: texto obligatorio, trim, único;
- `ruta_imagen`: texto obligatorio que representa una ruta interna del mismo sistema, no una URL externa; este WP valida el contrato de ruta pero no exige que el asset físico ya exista en el build de los frontends.

La columna `presente` **no existe** en SIS-Leg. El formato histórico que la incluía no se acepta como padrón canónico nuevo.

### Correspondencia padrón/disposición

- La capacidad total del recinto es `sum(room.rows)`.
- La cantidad de filas del padrón debe ser exactamente igual a esa capacidad.
- Cada banca debe estar entre `1` y la capacidad total.
- Las bancas deben ser únicas.
- Como consecuencia, el padrón válido debe cubrir exactamente todas las bancas `1..capacidad` sin faltantes ni sobrantes.

### Snapshot congelado

- Crear objetos tipados/inmutables para configuración y padrón.
- Una carga exitosa devuelve snapshots independientes de los archivos de disco.
- Modificar los archivos después de obtener el snapshot no cambia los objetos ya cargados.
- Una nueva carga futura puede obtener nuevos valores; la decisión de cuándo cargar pertenece a WP-005.

## Criterios de aceptación

1. Un `system.toml` válido carga en un modelo tipado y no mutable por referencia externa.
2. Un padrón válido carga preservando DNI como identidad y banca/dispositivo como asociaciones únicas.
3. **CA-003:** se rechaza padrón con DNI vacío/duplicado, nombre/apellido vacío, banca inválida/vacía/duplicada, dispositivo vacío/duplicado o `ruta_imagen` inválida/vacía; bloque vacío es válido.
4. El padrón canónico no contiene `presente`; un archivo con el encabezado histórico no se acepta silenciosamente como el nuevo contrato.
5. La cantidad de concejales debe coincidir exactamente con `sum(room.rows)`.
6. Las bancas deben cubrir exactamente `1..sum(room.rows)`.
7. `ruta_imagen` queda disponible en el snapshot del concejal para que los frontends puedan utilizarla posteriormente, sin asociación hardcodeada por banca.
8. Un cambio en archivos de disco después de cargar no modifica snapshots ya creados.
9. **CA-059, parte técnica:** el mecanismo de snapshot permite que una futura preparación conserve la configuración cargada aunque cambie el disco.
10. Los errores de parseo/validación son deterministas y testeables; no contienen reglas institucionales adicionales.
11. No se introduce base de datos ni persistencia secundaria.

## Pruebas obligatorias

- Unitarias de `system.toml` válido/inválido para cada regla.
- Unitarias de padrón válido y cada condición bloqueante de CA-003.
- Test de bloque vacío.
- Test que rechace el encabezado histórico con `presente`.
- Test de `ruta_imagen` vacía y URL externa.
- Test de duplicados DNI/banca/dispositivo.
- Test de cantidad de filas menor y mayor que `sum(room.rows)`.
- Test de banca fuera de capacidad configurada y de hueco en la cobertura de bancas.
- Test de congelamiento: cambiar/reemplazar archivos o estructuras fuente no modifica snapshots cargados.
- Ruff, Pyright y pytest verdes.

## Invariantes y restricciones

- No agregar validaciones institucionales no documentadas.
- No usar datos reales de concejales en fixtures/versionado.
- No hacer hot reload.
- No introducir base de datos.
- No volver a incorporar presencia al padrón.
- No hardcodear imágenes por banca.
- No cambiar nombres/formato canónico aprobado en este WP sin escalamiento.
- No leer todavía configuración del bridge.

## Decisiones que requieren escalamiento

Durante implementación debe escalarse cualquier necesidad de:

- agregar/eliminar/renombrar campos canónicos;
- cambiar reglas de validación;
- reincorporar `presente` o aceptar automáticamente el padrón histórico;
- cambiar la regla de correspondencia exacta padrón/disposición;
- incorporar una nueva librería directa de configuración/CSV no prevista;
- aceptar formatos alternativos no documentados;
- introducir recarga dinámica.
