# WP-093 - Esperar convergencia efectiva de Nginx tras reload de despliegue

## Estado documental

`APROBADO / BLOQUEANTE DE WP-029`

## Origen

Detectado durante la primera conmutación reversible de WP-029 en la PC real de producción el 09/09/2026.

El candidato `50abb3832317afefac2175ac51a12acb8d7d583d` logró:
- backend SIS-Leg activo y healthy;
- Device Bridge activo;
- EVIOCGRAB exitoso sobre los 12 numpads mapeados;
- health `/api/v1/health` directo y vía Nginx.

La activación falló inmediatamente después de `systemctl reload nginx.service` porque `GET /moderacion/` alcanzó todavía el proxy Legacy y fue enviado al backend SIS-Leg, que respondió 404. El rollback externo de WP-029 restauró `ESTABLE_LEGACY`.

## Causa técnica

`deploy/herramienta_despliegue.py::_verificar_servicios_y_nginx()` asume que al retornar `systemctl reload nginx.service` todas las nuevas solicitudes ya serán atendidas por workers con la configuración nueva.

Nginx realiza reload graceful: inicia workers con la configuración nueva y ordena a los workers viejos cerrar de forma gradual. Durante esa convergencia puede existir una ventana donde un cliente/conexión todavía sea atendido con la configuración anterior.

El health `/api/v1/health` no discrimina generaciones de configuración porque tanto el vhost Legacy como el de SIS-Leg pueden hacerlo llegar al backend. En cambio las rutas estáticas `/moderacion/`, `/recinto/`, `/tecnico/`, `/manual/` y `/simulador/` sí demuestran que el vhost SIS-Leg efectivo está sirviendo el release correcto.

## Objetivo

Hacer que la verificación post-reload sea health-gated y tolere exclusivamente la convergencia transitoria de Nginx, sin introducir sleeps ciegos ni ocultar fallos persistentes.

## Alcance

- Modificar únicamente la lógica productiva necesaria alrededor de la verificación post-`reload` de Nginx.
- Mantener `nginx -t` y `systemctl reload nginx.service`.
- Después del reload, esperar de forma acotada a que el vhost SIS-Leg sea observable realmente.
- La condición de convergencia debe incluir como mínimo:
  - `/api/v1/health` vía Nginx con JSON `estado == "ok"`;
  - `/moderacion/` servida como HTML válido;
  - las demás superficies mismas-origen requeridas por el despliegue como HTML válido.
- Reintentar sólo errores compatibles con convergencia temporal (404/errores de conexión/HTML todavía no esperado) dentro de un presupuesto acotado.
- Si el presupuesto se agota, fallar cerrado y conservar el rollback existente.
- No convertir errores permanentes en éxito.
- No usar un `sleep` único como supuesto de sincronización.
- No reiniciar Nginx como solución normal.
- Preservar el comportamiento de rollback de primera instalación y de releases posteriores.

## Diseño esperado

Preferencia por un helper explícito, testeable e inyectable, por ejemplo una espera acotada de convergencia de Nginx, con:
- número de intentos y pausa definidos de forma clara;
- último diagnóstico preservado en el error;
- reloj/sleeper inyectable o diseño equivalente para tests deterministas;
- validación de todas las superficies requeridas en la misma iteración o en una secuencia que no permita éxito parcial.

No fijar como requisito una duración real de producción. La política es `health-gated`.

## Pruebas obligatorias

1. Reload + primera consulta estática devuelve 404/Legacy y la siguiente converge a HTML SIS-Leg => activación exitosa.
2. Varias respuestas transitorias y posterior convergencia => éxito.
3. Nunca converge dentro del presupuesto => `ErrorDespliegue` y rollback.
4. Health proxy queda incorrecto => fallo cerrado.
5. Una superficie estática nunca entrega HTML válido => fallo cerrado.
6. No se omiten `/moderacion/`, `/recinto/`, `/simulador/`, `/tecnico/`, `/manual/`.
7. La espera no duplica `reload` ni reinicia Nginx.
8. Primera instalación sin release anterior conserva rollback correcto.
9. Regresión de activación normal sin transición: una sola convergencia inmediata funciona.
10. Tests del deployment tool deterministas, sin sleeps reales largos.
