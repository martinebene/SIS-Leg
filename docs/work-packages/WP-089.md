# WP-089 - Validar el timeout del canal de control del Device Bridge

## Estado documental

`INTEGRADO`

## Objetivo

Endurecer la configuración por entorno del cliente backend→Device Bridge para que `SIS_LEG_BRIDGE_CONTROL_TIMEOUT` sólo acepte una duración finita y estrictamente positiva, falle temprano con diagnóstico claro ante valores inválidos y no pueda trasladar `nan`, infinitos, cero o negativos a `urllib`.

## Resultado esperado

El backend conserva el default actual de 3.0 s y acepta valores finitos positivos configurados por entorno. Un valor inválido impide iniciar de forma determinista el recurso de control con un error que identifica `SIS_LEG_BRIDGE_CONTROL_TIMEOUT`, en lugar de diferir el fallo hasta una operación de remapeo o producir semántica de socket indefinida.

## Dependencias

- WP-020 `INTEGRADO`: canal de control/remapeo backend↔Device Bridge al que pertenece este timeout.

## Fuentes canónicas obligatorias

- `apps/backend/src/sis_leg_backend/recursos.py`.
- `apps/backend/src/sis_leg_backend/servicios/cliente_bridge.py`.
- Tests backend de recursos/remapeo/cliente bridge.
- Configuración/despliegue donde se documenten variables `SIS_LEG_BRIDGE_CONTROL_*`.
- Hallazgo fuera de alcance registrado por WP-086.

## Hallazgo confirmado

`crear_recursos_aplicacion()` construye hoy el timeout mediante:

`float(os.getenv("SIS_LEG_BRIDGE_CONTROL_TIMEOUT", "3.0"))`

Eso permite que `nan` e `inf` atraviesen el parseo y que valores cero/negativos lleguen al cliente. Un texto no numérico falla con un `ValueError` genérico. La configuración queda validada tarde o de forma poco diagnóstica, pese a que el valor gobierna un timeout de red local.

## Alcance

- Centralizar la lectura/validación de `SIS_LEG_BRIDGE_CONTROL_TIMEOUT`.
- Mantener default exacto `3.0`.
- Aceptar enteros/decimales representables como float, finitos y estrictamente positivos.
- Rechazar `nan`, `inf`, `+inf`, `-inf`, cero, negativos, vacío y texto no numérico.
- El error debe identificar literalmente la variable `SIS_LEG_BRIDGE_CONTROL_TIMEOUT`.
- Fallar al construir los recursos, antes de una operación de remapeo.
- Evaluar una defensa equivalente en `ClienteControlBridge.__init__` para que llamadas directas no puedan saltar la invariante; implementarla si no duplica de forma innecesaria una única frontera de validación.
- Actualizar documentación operativa si la variable está documentada o si hace falta fijar el contrato.

## Fuera de alcance

- Mover esta variable a `system.toml`.
- Cambiar `SIS_LEG_BRIDGE_CONTROL_URL`.
- Introducir retries.
- Cambiar el protocolo de remapeo/control.
- Cambiar el default 3.0 s.
- Modificar timeouts ajenos al canal de control.
- Resolver disponibilidad o autenticación de red.

## Criterios de aceptación

1. Variable ausente produce exactamente 3.0 s.
2. Valores finitos positivos válidos se aceptan.
3. `nan`, `inf`, `+inf`, `-inf`, `0`, negativos, vacío y texto inválido se rechazan.
4. El mensaje de error identifica `SIS_LEG_BRIDGE_CONTROL_TIMEOUT`.
5. El fallo ocurre durante construcción de recursos/startup, no recién al usar remapeo.
6. No cambia URL, protocolo, retries ni comportamiento de un valor válido.
7. Tests prueban la frontera pública relevante y no sólo un helper aislado.
8. Suite y CI quedan verdes.

## Pruebas obligatorias

## Invariantes y restricciones

- No fallback silencioso a 3.0 cuando la variable existe pero es inválida.
- No rebase/force-push.
- No introducir dependencia nueva para validar un float.
