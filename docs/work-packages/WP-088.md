# WP-088 - Evitar reconstrucción del sentido del voto desde logs operativos del Device Bridge

## Estado documental

`INTEGRADO`

## Objetivo

Eliminar de los logs operativos del Device Bridge cualquier combinación de datos que permita reconstruir el sentido de una pulsación de voto de una banca identificable, preservando diagnóstico suficiente de transporte, mapping y exclusividad sin debilitar el secreto temporal del voto.

## Resultado esperado

Los logs de proceso/journal del Device Bridge, incluso con nivel DEBUG, no exponen la tecla normalizada/raw ni cuerpos de respuesta que puedan combinarse con dispositivo lógico, fingerprint o ruta para deducir `1/2/3 -> POSITIVO/ABSTENCION/NEGATIVO`. El backend y los CSV institucionales conservan sus contratos actuales; sólo se endurece observabilidad operativa del bridge.

## Dependencias

- WP-082 `INTEGRADO`: baseline vigente de privacidad, descriptor efectivo y EVIOCGRAB.
- WP-019 `INTEGRADO`: contrato base del Device Bridge y cliente HTTP.

- `services/device-bridge/src/sis_leg_device_bridge/cliente_http.py`.

## Hallazgo confirmado

La auditoría posterior a WP-082 detectó que el problema no se limita a una sola línea DEBUG:

- `servicio.py` registra al despachar `dispositivo_logico -> tecla_normalizada` junto con fingerprint;
- `cliente_http.py` registra dispositivo + tecla en DEBUG, INFO, WARNING y ERROR para envío, aceptación/rechazo y fallos;
- algunos errores registran cuerpos HTTP/JSON crudos que hoy pueden incluir o en el futuro podrían incluir nuevamente dispositivo, tecla, identidad o valor de voto.

Como `1/2/3` tienen semántica de voto y el dispositivo lógico identifica una banca, esas trazas pueden reconstruir el sentido individual antes de la frontera autoritativa de revelado.

## Alcance

- Auditar todos los logs del Device Bridge que se ejecutan por una pulsación individual.
- Eliminar de logs de despacho/transporte/resultado la tecla raw o normalizada.
- Evitar loggear request payloads o cuerpos de respuesta crudos del endpoint de pulsaciones.
- Mantener códigos HTTP, clase de resultado, motivo estable y detalle técnico no sensible cuando sean útiles.
- Permitir logging de identidad física/lógica para descubrimiento, mapping, remapeo y exclusividad siempre que no se combine con contenido de tecla de una pulsación.
- Para una pulsación funcional, ningún mensaje de log individual debe contener una combinación que permita inferir simultáneamente quién/banca y sentido.
- Mantener diagnóstico de tecla física desconocida sólo si el valor no se normaliza a una tecla funcional enviada al backend; si el implementador encuentra ambigüedad, preferir redacción sin contenido de tecla.
- Incorporar tests de no filtración por niveles DEBUG/INFO/WARNING/ERROR y por caminos de éxito/fallo.
- Documentar explícitamente el límite entre logs operativos del bridge y auditoría institucional durable del backend.

## Fuera de alcance

- Cambiar el contrato `{dispositivo, tecla}` entre bridge y backend.
- Cambiar la semántica de teclas `1/2/3/7/8/9`.
- Reescribir CSV históricos o eliminar del backend la auditoría durable aprobada.
- Cambiar la proyección segura de eventos L2/L3 ya implementada.
- Introducir cifrado de logs, SIEM, autenticación de red o rotación nueva.
- Rediseñar fingerprint, EVIOCGRAB, remapeo o topología.
- Resolver validación física real; queda en WP-029.

## Criterios de aceptación

1. Ningún log de una pulsación funcional, a ningún nivel, contiene la tecla raw/normalizada junto con dispositivo, fingerprint, ruta o identidad de banca.
2. `cliente_http.py` no registra `solicitud.tecla` ni serializa el payload completo en logs.
3. Respuestas HTTP inválidas/errores no vuelcan cuerpos crudos que puedan contener campos sensibles de la pulsación.
4. Logs de aceptación/rechazo/transporte siguen permitiendo distinguir éxito, rechazo funcional, HTTP error, timeout y excepción sin revelar sentido.
5. Mapping/remapeo/exclusividad conservan diagnóstico útil y no se degradan.
6. Tests adversariales demuestran ausencia de filtración con teclas `1/2/3` y un dispositivo/fingerprint identificable.
7. Un test con body de backend sintético que ecoe `dispositivo`, `tecla` y `valor` demuestra que el log no los reproduce.
8. No cambia el contrato HTTP, ni el secreto/auditoría durable del backend, ni el despacho funcional.
9. Suite Device Bridge, calidad estática y CI completas quedan verdes.

## Pruebas obligatorias

- `caplog`/equivalente sobre:
  - despacho DEBUG;
  - aceptación INFO;
  - rechazo INFO;
  - respuesta no JSON;
  - esquema JSON inválido;
  - HTTPError;
  - timeout/URLError;
  - excepción inesperada.
- Casos con `devXX`, fingerprint/ruta y teclas `1`, `2`, `3`.
- Caso de cuerpo de respuesta malicioso/eco con datos sensibles.
- Regresiones de mapping/remapeo/exclusividad WP-075/WP-082.
- Suite completa Device Bridge.
- `uv run ruff check .`.
- `uv run ruff format --check .`.
- `uv run pyright`.
- `uv run pytest`.
- `git diff --check`.

## Invariantes y restricciones

- El backend sigue siendo autoridad exclusiva del significado de la tecla.
- El secreto temporal del voto no puede degradarse por observabilidad operativa.
- La auditoría institucional durable del backend conserva el contrato ya aprobado.
- No rebase/force-push.
- No silenciar errores completos cuando pueda conservarse diagnóstico no sensible.
- Evitar filtros basados en texto frágil si una redacción segura por construcción es posible.
