# WP-006 - Entrada lógica de dispositivos, presencia, test y quórum

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Implementar la primera capa funcional de entrada lógica de dispositivos de SIS-Leg para `SIN_PREPARAR` y `PREPARANDO`, integrando el padrón/configuración congelados de WP-003, el estado y serializador únicos de WP-002/WP-005 y la auditoría durable de WP-004.

El resultado principal debe permitir recibir una pulsación `{dispositivo, tecla}`, resolver el concejal por su dispositivo lógico, alternar presencia con tecla `9`, activar/renovar el test visual temporal con tecla `8`, derivar cantidad de presentes/quórum y responder mediante el contrato REST estable aprobado en DEC-006.

## Resultado esperado

Al completar WP-006 debe quedar integrado un único flujo backend de pulsaciones lógicas bajo `/api/v1/entradas/tecla` que:

- rechace sin efecto ni auditoría las pulsaciones recibidas en `SIN_PREPARAR`;
- durante `PREPARANDO` registre cada pulsación recibida y su resultado mediante el escritor activo de la preparación;
- use exclusivamente el dispositivo lógico congelado en el padrón para identificar al concejal;
- habilite únicamente teclas `8` y `9` durante `PREPARANDO`;
- alterne presencia de forma durable/auditable y derive presentes/quórum;
- active un test temporal configurable y renovable sin modificar estado de negocio;
- rechace dispositivos no asignados y teclas no habilitadas mediante `200 OK` + motivo estable;
- responda `503 AUDITORIA_NO_DISPONIBLE` y no confirme mutaciones cuando la auditoría obligatoria falle;
- quede preparado para que WP-008, los WPs de votación, WP-015 y WP-019 reutilicen el contrato y las primitivas sin duplicar responsabilidades.

## Alcance

### 1. Ampliar la configuración canónica para el test de dispositivo

WP-006 debe incorporar al contrato ejecutable de `system.toml` la clave aprobada:

```text
[timers]
device_test_seconds = 0.6
```

Debe:

- agregarse al archivo de configuración de referencia versionado;
- cargarse mediante las mismas interfaces públicas de WP-003;
- representarse en `ConfiguracionSistema` como número entero o decimal no negativo, siguiendo la semántica ya utilizada por los otros temporizadores;
- rechazarse configuración ausente, no numérica, booleana o negativa conforme al patrón de validación de WP-003;
- quedar congelada dentro de la `Preparacion` activa y no releerse del disco durante las pulsaciones.

No se crea un parser alternativo ni una segunda fuente de configuración.

### 2. Crear el contrato HTTP de entrada lógica

Implementar exactamente:

```text
POST /api/v1/entradas/tecla
```

Body Pydantic:

```text
{
  dispositivo: string no vacío,
  tecla: string no vacío
}
```

No recibe DNI, banca, concejal, fingerprint físico ni rutas de archivos.

La API debe exponer mediante OpenAPI la forma de request, `200`, `422`, `503` y `500` correspondiente al contrato de DEC-006.

### 3. Respuesta funcional estable

Para un body válido, una pulsación aceptada o rechazada normalmente devuelve `200 OK` con la forma base:

```text
aceptada
dispositivo
tecla
motivo
concejal | null
resultado | null
```

`concejal`, cuando exista, contiene únicamente:

```text
dni
nombre
apellido
banca
```

Motivos iniciales obligatorios:

- `PRESENCIA_ACTUALIZADA`;
- `TEST_ACTIVADO`;
- `SIN_PREPARAR`;
- `DISPOSITIVO_NO_ASIGNADO`;
- `TECLA_NO_HABILITADA`.

Resultado de presencia:

```text
tipo = PRESENCIA
presente
presentes
quorum_alcanzado
```

Resultado de test:

```text
tipo = TEST
activo = true
duracion_segundos = valor congelado de device_test_seconds
```

El agente puede decidir la organización interna concreta de los modelos Pydantic, pero no alterar campos, semántica, motivos ni códigos HTTP.

### 4. Comportamiento en `SIN_PREPARAR`

Una pulsación cuyo body es válido:

- no produce efecto funcional;
- no busca crear/usar CSV;
- no modifica estado;
- responde `200`;
- `aceptada=false`;
- `motivo=SIN_PREPARAR`;
- `concejal=null`;
- `resultado=null`.

No se registra `PULSACION_RECIBIDA` ni ningún otro evento porque no existe preparación/auditoría activa.

### 5. Resolución del dispositivo en `PREPARANDO`

Toda resolución `dispositivo lógico -> concejal` se realiza contra `Preparacion.padron`, congelado por WP-005/WP-003.

No se recorre/consulta configuración del bridge ni se recibe fingerprint físico.

Si el dispositivo lógico no está asignado:

- se registra la pulsación recibida;
- se registra el rechazo;
- se responde `200`, `aceptada=false`, `motivo=DISPOSITIVO_NO_ASIGNADO`, `concejal=null`, `resultado=null`.

### 6. Teclas habilitadas durante `PREPARANDO`

Solo `8` y `9` tienen efecto funcional.

`1`, `2`, `3`, `7` y cualquier otra tecla que haya superado la validación de transporte:

- se registran como pulsación recibida;
- se registran como pulsación rechazada;
- no modifican estado;
- responden `200`, `aceptada=false`, `motivo=TECLA_NO_HABILITADA`;
- si el dispositivo estaba asociado, la respuesta puede identificar al concejal mediante el DTO canónico.

No debe implementarse lógica provisional de voto o palabra.

### 7. Presencia por tecla `9`

Con dispositivo asignado y estado `PREPARANDO`:

1. calcular el nuevo valor de presencia (`not valor_actual`);
2. persistir `PULSACION_RECIBIDA`;
3. persistir `CONCEJAL_PRESENTE` o `CONCEJAL_AUSENTE` según el nuevo valor;
4. solo después de garantizar ambos eventos, aplicar la mutación a `Preparacion.presencias`;
5. calcular cantidad actual de presentes;
6. calcular `quorum_alcanzado = presentes >= preparacion.configuracion.quorum`;
7. responder `200` con `PRESENCIA_ACTUALIZADA` y resultado `PRESENCIA`.

Moderación no obtiene ningún endpoint alternativo para acreditar/retirar presencia.

El cálculo de presentes/quórum debe quedar organizado de forma reutilizable por WP-008 y WPs posteriores sin convertirse en una segunda fuente de verdad independiente de `presencias + configuracion.quorum`.

### 8. Test visual por tecla `8`

Con dispositivo asignado y estado `PREPARANDO`:

1. persistir `PULSACION_RECIBIDA`;
2. persistir `TEST_DISPOSITIVO_ACTIVADO`;
3. solo después activar/renovar el estado visual temporal del concejal;
4. responder `200` con `TEST_ACTIVADO` y resultado `TEST`.

El test:

- no modifica presencia;
- no modifica quórum;
- no crea estado de negocio nuevo;
- debe poder consultarse técnicamente como activo/inactivo para ser proyectado por WPs posteriores;
- utiliza una fuente de tiempo monotónica o mecanismo equivalente inmune a cambios del reloj civil; la forma interna concreta pertenece a la autonomía local del implementador;
- ante nueva tecla `8` mientras sigue activo, la expiración resultante nunca puede ser anterior a `ahora + device_test_seconds` ni acortar una expiración ya posterior.

### 9. Auditoría exacta

Reutilizar exclusivamente `Preparacion.escritor_auditoria` de WP-004/WP-005.

No modificar el formato CSV ni crear otro writer.

Eventos obligatorios exactos de DEC-006:

- `L2 | INPUT | PULSACION_RECIBIDA`;
- `L2 | INPUT | PULSACION_RECHAZADA`;
- `L3 | PRESENCIA | CONCEJAL_PRESENTE`;
- `L3 | PRESENCIA | CONCEJAL_AUSENTE`;
- `L2 | INPUT | TEST_DISPOSITIVO_ACTIVADO`.

Los mensajes y placeholders deben ser exactamente los definidos por DEC-006.

Orden obligatorio:

- presencia aceptada: recibida → presencia/ausencia → mutación;
- test aceptado: recibida → test → activación/renovación;
- rechazo normal: recibida → rechazada → respuesta.

### 10. Fallo cerrado de auditoría

Todo procesamiento en `PREPARANDO` debe ocurrir bajo el `EjecutorMutaciones` único.

Si falla cualquiera de los eventos obligatorios o el escritor ya está fallado/cerrado:

- no confirmar la mutación funcional dependiente;
- no crear un segundo escritor;
- no reabrir archivos;
- no limpiar/borrar evidencia parcial;
- mantener el escritor en fallo cerrado conforme a WP-004;
- responder `503 AUDITORIA_NO_DISPONIBLE` usando el manejador estable ya existente/reutilizable;
- no devolver `200` con aceptación/rechazo normal para una pulsación cuya auditoría no pudo garantizarse.

Si `PULSACION_RECIBIDA` se persistió y el segundo evento falla, esa primera fila permanece como evidencia; no se intenta rollback destructivo.

### 11. Concurrencia

Dos o más pulsaciones concurrentes deben pasar por el mismo `EjecutorMutaciones` del proceso.

El orden bajo el lock determina simultáneamente:

- el orden oficial de procesamiento;
- los `seq` de auditoría;
- la evolución de presencia/test;
- el resultado de presentes/quórum devuelto por cada request.

No se agrega un segundo lock al servicio de entradas ni al modelo de presencia/test.

### 12. Preparación para extensiones posteriores

La ruta, request y forma base de respuesta quedan estables para extensiones posteriores.

WP-006 puede crear helpers/modelos internos reutilizables para entrada/presencia/test/quórum, pero no debe implementar entidades o reglas de WPs futuros para anticiparlas.

## Criterios de aceptación

1. `POST /api/v1/entradas/tecla` existe bajo `/api/v1`, recibe únicamente `dispositivo` y `tecla` no vacíos y su OpenAPI coincide con DEC-006.
2. Body ausente, JSON inválido, campos ausentes o textos vacíos se rechazan como validación de transporte (`422`) sin ejecutar mutaciones funcionales.
3. En `SIN_PREPARAR`, cualquier pulsación con body válido devuelve `200`, `aceptada=false`, `motivo=SIN_PREPARAR`, `concejal=null`, `resultado=null`, sin crear/escribir CSV ni modificar estado.
4. Durante `PREPARANDO`, cada pulsación procesable registra primero `PULSACION_RECIBIDA` en L2 antes de resolver su resultado funcional.
5. Un dispositivo no asociado se rechaza con `200` + `DISPOSITIVO_NO_ASIGNADO`, registra `PULSACION_RECHAZADA`, no modifica estado y devuelve `concejal=null`.
6. Con dispositivo asociado, teclas distintas de `8`/`9` se rechazan con `200` + `TECLA_NO_HABILITADA`, registrando recibida + rechazada y sin modificar presencia/test.
7. Tecla `9` del dispositivo asignado alterna exclusivamente la presencia del concejal correspondiente; no existe operación de Moderación equivalente.
8. Una presencia aceptada registra `CONCEJAL_PRESENTE` o `CONCEJAL_AUSENTE` como L3 antes de aplicar la mutación, usando exactamente el mensaje canónico de DEC-006.
9. Tras presencia aceptada, `presentes` coincide con la cantidad de valores `true` de la preparación y `quorum_alcanzado` equivale a `presentes >= configuracion.quorum`.
10. Cruzar el umbral de quórum hacia arriba o abajo se refleja inmediatamente en la respuesta de la pulsación que produjo el cambio, sin guardar un quórum independiente como fuente de verdad.
11. Tecla `8` de dispositivo asignado activa el test temporal con la duración congelada configurada y responde `TEST_ACTIVADO` sin cambiar presencia ni quórum.
12. Repetir tecla `8` durante un test activo garantiza al menos una nueva ventana completa desde la última pulsación y nunca acorta una expiración posterior existente.
13. `device_test_seconds` se carga/valida mediante WP-003, acepta entero/decimal no negativo, queda congelado y cambios posteriores de `system.toml` no alteran una preparación activa.
14. El estado temporal de test expira automáticamente según la fuente de tiempo elegida y puede consultarse sin requerir una mutación o tarea en background para “apagarlo”.
15. Si falla la auditoría al registrar `PULSACION_RECIBIDA`, no se modifica presencia/test y la API responde `503 AUDITORIA_NO_DISPONIBLE`.
16. Si `PULSACION_RECIBIDA` fue durable pero falla el evento funcional/rechazo posterior, la primera fila permanece, no se modifica el efecto dependiente y la API responde `503 AUDITORIA_NO_DISPONIBLE`.
17. Una vez que el escritor entra en fallo cerrado, nuevas pulsaciones auditables no son confirmadas como respuestas funcionales normales ni producen nuevas mutaciones.
18. Dos pulsaciones concurrentes generan un orden único coherente entre secuencias CSV, mutaciones y resultados devueltos (CA-058).
19. El mapeo dispositivo lógico → concejal usa exclusivamente el padrón congelado; modificar `concejales.csv` durante `PREPARANDO` no cambia el procesamiento activo (CA-059).
20. La respuesta de presencia contiene exactamente `tipo=PRESENCIA`, `presente`, `presentes`, `quorum_alcanzado`; la de test contiene `tipo=TEST`, `activo=true`, `duracion_segundos`; los rechazos tienen `resultado=null`.
21. La identidad de concejal expuesta por esta respuesta se limita a `dni`, `nombre`, `apellido`, `banca` y no acepta identidad enviada por cliente.
22. El WP no implementa funcionalidad de teclas `1`, `2`, `3` o `7`, sesión, votación, palabra, bridge físico, SSE ni frontend.
23. No se introduce segundo estado global, segundo lock, segundo parser de configuración ni segundo escritor de auditoría.
24. El código propio nuevo respeta nomenclatura en español según DEC-001.
25. Clases, funciones y flujos no triviales quedan explicados pedagógicamente en español, especialmente serialización, orden auditoría→mutación, test temporal y cálculo de quórum.
26. No se agregan dependencias directas nuevas salvo escalamiento y aprobación previa conforme a DT-038.
27. Toda la suite previa continúa verde y las pruebas nuevas cubren los escenarios obligatorios del WP.

## Invariantes y restricciones

- `EstadoOperativo` continúa siendo la única fuente de verdad global (DT-004).
- Producción continúa usando un solo worker (DT-005).
- Toda mutación/persistencia de entrada pasa por el mismo `EjecutorMutaciones` de WP-002.
- `Preparacion` de WP-005 sigue siendo el contexto propietario de configuración, padrón, presencias y escritor durante `PREPARANDO`.
- `ConfiguracionSistema`/`Padron` continúan siendo snapshots inmutables de WP-003.
- El backend recibe dispositivo lógico; fingerprint físico pertenece al bridge.
- Presencia solo cambia por tecla `9` del dispositivo asignado.
- Moderación no puede acreditar/retirar presencia.
- El quórum se deriva de presencias + configuración congelada; cualquier caché interna no puede convertirse en autoridad independiente.
- Test no altera estado de negocio.
- En `SIN_PREPARAR` no existe auditoría de pulsaciones.
- En `PREPARANDO`, una operación que requiera registro no se confirma antes de persistir sus eventos obligatorios.
- CSV cerrados/fallados no se reabren ni reemplazan.
- La API nueva se mantiene bajo `/api/v1` y OpenAPI/Pydantic son el contrato técnico.
- No introducir base de datos, threads de estado paralelos, tareas en background necesarias para expirar tests ni persistencia de test fuera de memoria.
- No agregar semántica de `SESION_ABIERTA` para resolver aceptación del WP.
- No modificar el significado reglamentario de quórum ni adelantar consecuencias de pérdida/recuperación durante sesión/votación.
- No agregar dependencia directa nueva sin aprobación humana/documentada.
- Aplican íntegramente DT-038 y DEC-001/DEC-003.
