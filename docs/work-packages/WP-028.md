# WP-028 - Empaquetado, despliegue productivo y rollback

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Implementar y versionar el mecanismo de empaquetado y despliegue productivo de SIS-Leg conforme DT-027 a DT-032, de manera que una versión ya validada pueda:

1. convertirse en un artefacto trazable por commit;
2. prepararse en la máquina productiva sin modificar la release activa;
3. instalarse bajo una estructura de releases inmutables;
4. activarse mediante cambio de `current`;
5. ejecutar FastAPI y el device-bridge como servicios nativos de systemd;
6. servir Moderación y Recinto como SPA estáticas mediante Nginx;
7. conservar REST + SSE bajo un único origen;
8. preservar configuración y auditoría fuera de las releases;
9. impedir un despliegue deliberado mientras exista estado institucional activo;
10. realizar rollback a la release anterior de forma reproducible.

WP-028 implementa **el mecanismo y sus artefactos**, pero no autoriza a un agente de desarrollo a modificar la máquina real del Concejo ni el VPS de desarrollo.

La primera aplicación del mecanismo sobre el equipo productivo es una intervención administrativa separada con aprobación humana y validación posterior de hardware/regresión.

## Resultado esperado

Desde un checkout limpio del SHA candidato debe existir un comando canónico:

```bash
pnpm empaquetar:produccion
```

que genere un paquete de despliegue identificable por el SHA Git exacto, sin incluir configuración institucional, logs, dependencias Node ni outputs ajenos.

Conceptualmente:

```text
SIS-Leg @ <commit>
        │
        ├── pnpm build
        ├── fuentes runtime Python + uv.lock
        ├── SPA Moderación generada
        ├── SPA Recinto generada
        ├── systemd units
        ├── Nginx site
        ├── herramienta de despliegue
        └── manifest
                 ↓
       sis-leg-<full-sha>.tar.gz
       sis-leg-<full-sha>.tar.gz.sha256
```

El paquete debe poder transferirse al equipo productivo y prepararse sin Git, sin checkout activo y sin Node/pnpm.

## Contexto operativo de desarrollo

La implementación puede realizarse completamente dentro de `agent-dev`.

Hechos operativos vigentes:

- `agent-dev` es un contenedor de desarrollo, no el host productivo de SIS-Leg;
- PID 1 no es systemd;
- disponer de `sudo` dentro de `agent-dev` no autoriza cambios en el host VPS;
- no existe motivo para modificar Docker, Supervisor, Tailscale, Caddy, UFW ni servicios persistentes del VPS;
- el harness `pnpm dev:stack` de WP-033 continúa siendo exclusivamente de desarrollo.

## Topología productiva canónica

La topología debe quedar:

```text
Navegadores
    │
    ▼
Nginx :80
    ├── /moderacion/ ──► SPA estática
    ├── /recinto/    ──► SPA estática
    └── /api/v1/     ──► 127.0.0.1:8000
                              │
                              ▼
                    FastAPI / un worker
                              │
               control bridge 127.0.0.1:8765
                              │
                              ▼
                    device-bridge systemd
                              │
                              ▼
                         /dev/input/*
```

Reglas:

- FastAPI escucha exclusivamente en loopback.
- Device-bridge controla su API exclusivamente en loopback.
- Nginx es el único punto de entrada HTTP normal.
- No CORS.
- No WebSocket.
- SSE conserva entrega inmediata y sin buffering de proxy.
- No servidor Node/Nitro en producción.
- No Docker/Compose.

## Plataforma y prerequisitos del equipo productivo

Referencia:

- Linux Mint 22.3 Cinnamon;
- arquitectura x86_64;
- systemd;
- Nginx;
- Python 3.14 disponible mediante un path estable;
- `uv` instalado como herramienta administrativa de preparación de releases.

Node.js y pnpm **no son prerequisitos runtime del equipo productivo**.

La herramienta de despliegue debe verificar prerequisitos y fallar con diagnóstico claro; no instalar paquetes del sistema silenciosamente.

La instalación o actualización de Python, uv o Nginx en la máquina real es una acción administrativa separada.

## Runtime ASGI productivo

La aplicación productiva existente es:

`sis_leg_backend.main:app`.

WP-028 autoriza explícitamente utilizar **Uvicorn** como servidor ASGI productivo bajo systemd, con:

- un único proceso;
- `--workers 1`;
- bind `127.0.0.1:8000`;
- sin Gunicorn ni supervisor adicional.

`uvicorn>=0.41,<0.42` ya existe en el lockfile como dependencia de desarrollo. WP-028 autoriza moverlo/reclasificarlo como dependencia runtime directa del paquete backend para que una instalación `--no-dev` contenga el servidor ASGI requerido.

No se autoriza agregar otro servidor ASGI ni una dependencia externa nueva.

## Estructura productiva

La instalación objetivo debe respetar conceptualmente:

```text
/opt/sis-leg/
├── releases/
│   ├── <sha-completo-A>/
│   ├── <sha-completo-B>/
│   └── <sha-completo-C>/
├── current  -> releases/<sha-activo>
├── previous -> releases/<sha-anterior>       # si existe
├── config/
│   ├── system.toml
│   ├── concejales.csv
│   └── bridge/
│       └── devices.json
└── logs/
```

`previous` es metadata operacional para rollback, no estado institucional.

No existe obligación de conservar exactamente tres releases. WP-028 no debe borrar releases automáticamente.

### Configuración

`config/` nunca pertenece a una release.

El backend continúa cargando sus rutas canónicas relativas:

- `config/system.toml`;
- `config/concejales.csv`.

Por eso el servicio backend debe usar:

`WorkingDirectory=/opt/sis-leg`.

El bridge recibe explícitamente:

`/opt/sis-leg/config/bridge/devices.json`.

El directorio de auditoría configurado debe resolver exactamente fuera de la release y hacia:

`/opt/sis-leg/logs`.

Se puede aceptar en `system.toml` tanto una ruta absoluta equivalente como una ruta relativa que, desde el WorkingDirectory productivo, resuelva exactamente allí.

### Permisos

La implementación debe documentar una separación de privilegios mínima.

Preferencia aprobada para este WP:

- usuario de sistema `sis-leg-backend`;
- usuario de sistema `sis-leg-bridge`;
- ambos sin login interactivo;
- releases propiedad administrativa, legibles pero no escribibles por los servicios;
- `logs/` escribible únicamente por backend;
- `system.toml` y `concejales.csv` legibles por backend, no escribibles por él;
- `config/bridge/` escribible por el usuario del bridge porque el remapeo `PERSISTENTE` utiliza archivo temporal + `fsync` + `os.replace`;
- el servicio bridge recibe `SupplementaryGroups=input` sin otorgar ese acceso al backend.

No usar root como usuario runtime.

## Contenido de una release

Una release preparada debe contener sólo lo necesario para ejecutar y auditar la versión.

Estructura conceptual:

```text
<sha>/
├── app/
│   ├── pyproject.toml
│   ├── uv.lock
│   ├── .python-version
│   ├── apps/backend/
│   └── services/device-bridge/
├── web/
│   ├── moderacion/
│   └── recinto/
├── deploy/
│   ├── systemd/
│   │   ├── sis-leg-backend.service
│   │   └── sis-leg-device-bridge.service
│   ├── nginx/
│   │   └── sis-leg.conf
│   └── herramientas necesarias
└── release.json
```

No incluir:

- `node_modules`;
- caches;
- `.git`;
- worktrees;
- tests generales;
- logs;
- configuración institucional;
- `config/system.toml` de desarrollo;
- `config/concejales.csv` de desarrollo;
- `devices.json` de desarrollo;
- secretos;
- una `.venv` construida en otra máquina.

Las SPA se incluyen ya generadas.

## Manifest de release

`release.json` debe incluir al menos:

- commit SHA completo;
- tree SHA si es fácilmente obtenible;
- identificador/formato de release;
- versión del formato;
- rutas esperadas de Moderación y Recinto;
- versión objetivo de Python;
- identidad de los paquetes Python incluidos.

No incluir timestamps volátiles si impiden reproducibilidad sin aportar valor.

El archivo comprimido debe acompañarse por SHA-256 en un sidecar.

La herramienta productiva debe rechazar:

- checksum incorrecto;
- manifest inválido;
- SHA solicitado distinto del manifest;
- path traversal del tar;
- symlinks o entradas inesperadas capaces de escapar del destino;
- release ya preparada con contenido incompatible.

## Preparación de release en producción

Preparar una release **no cambia `current`**.

Procedimiento obligatorio:

1. verificar artefacto y SHA-256;
2. verificar manifest;
3. crear `/opt/sis-leg/releases/<sha-completo>` sin tocar la release activa;
4. extraer exclusivamente entradas permitidas;
5. crear la `.venv` dentro de la ruta final de esa release;
6. ejecutar desde `app/`:
   `uv sync --frozen --no-dev --all-packages` usando Python 3.14;
7. verificar imports de backend y bridge;
8. verificar que Uvicorn esté disponible;
9. verificar los outputs estáticos;
10. verificar archivos Nginx/systemd;
11. marcar la release como preparada sólo después de completar todo.

La `.venv` se crea **en su ruta final** para evitar scripts/shebangs que apunten a un directorio staging posteriormente renombrado.

Una release marcada como preparada no se modifica in-place.

Si la preparación falla, `current` debe permanecer intacto.

## Configuración productiva antes de activar

La herramienta debe validar, usando los parsers propietarios existentes cuando sea posible:

- `system.toml`;
- `concejales.csv`;
- `devices.json`.

La validación de despliegue no inventa nuevas reglas institucionales.

Además debe verificar la invariante operacional:

- los logs resuelven fuera de la release y exactamente a `/opt/sis-leg/logs`.

No copiar automáticamente la configuración de desarrollo del repositorio como configuración de producción.

## Servicios systemd

### Backend

Unidad conceptual:

`sis-leg-backend.service`.

Debe:

- ejecutarse como `sis-leg-backend`;
- usar `WorkingDirectory=/opt/sis-leg`;
- ejecutar el Python de `current/.venv`;
- importar `sis_leg_backend.main:app`;
- bindear `127.0.0.1:8000`;
- usar exactamente un worker;
- reiniciar ante fallo según una política acotada;
- emitir logs técnicos a journald/stdout/stderr;
- usar `PYTHONDONTWRITEBYTECODE=1` para no escribir dentro de una release;
- no tener permiso de escritura sobre las releases.

### Device bridge

Unidad conceptual:

`sis-leg-device-bridge.service`.

Debe:

- ejecutarse como `sis-leg-bridge`;
- arrancar después del backend;
- utilizar el Python de `current/.venv`;
- ejecutar la CLI real del bridge;
- leer/escribir `/opt/sis-leg/config/bridge/devices.json`;
- enviar entradas a `http://127.0.0.1:8000`;
- escuchar control sólo en `127.0.0.1:8765`;
- recibir acceso al grupo `input`;
- no ejecutarse como root;
- terminar correctamente con SIGTERM;
- emitir logs técnicos a journald.

No se requiere que el bridge real funcione dentro de CI sin hardware.

## Nginx

Debe existir una configuración productiva versionada que:

- escuche HTTP en puerto 80;
- mantenga el origen conceptual `http://botonera/`;
- sirva `/moderacion/` desde `current/web/moderacion/`;
- sirva `/recinto/` desde `current/web/recinto/`;
- preserve fallback SPA a `index.html`;
- haga proxy de `/api/v1/` a `127.0.0.1:8000`;
- mantenga el URI de API sin reescrituras incompatibles;
- desactive buffering/cache de proxy donde corresponda para SSE;
- utilice HTTP/1.1 hacia FastAPI;
- tenga un timeout de lectura compatible con streams SSE duraderos;
- no habilite CORS;
- no exponga directamente el puerto 8000;
- no introduzca TLS sin una decisión posterior.

La raíz `/` puede redirigir a `/moderacion/`.

## Guard de estado institucional antes de activar

Una release nueva no puede activarse deliberadamente si el backend vigente responde:

- `PREPARANDO`;
- `SESION_ABIERTA`.

La herramienta debe consultar directamente el backend vigente y exigir:

`estado_global == SIN_PREPARAR`.

Reglas de borde:

- primera instalación sin `current`: puede continuar;
- servicio backend explícitamente `inactive` o `failed`: no existe un runtime activo que preservar y puede continuarse con advertencia clara;
- servicio marcado `active` pero backend inaccesible/inconsistente: **refusar** el cambio automático;
- nunca ofrecer un flag silencioso tipo `--force` para ignorar una sesión activa.

## Activación

La activación debe ser transaccional en lo razonablemente posible:

1. validar release preparada;
2. validar configuración;
3. aplicar guard de `SIN_PREPARAR`;
4. validar las unidades systemd de la release;
5. preparar/validar la configuración Nginx;
6. recordar el target previo de `current`;
7. cambiar `current` mediante reemplazo atómico de symlink en el mismo filesystem;
8. ejecutar `systemctl daemon-reload` si correspondió actualizar unidades;
9. reiniciar backend;
10. esperar `GET http://127.0.0.1:8000/api/v1/health`;
11. iniciar/reiniciar bridge;
12. verificar estado de ambos servicios;
13. recargar Nginx sólo después de `nginx -t`;
14. verificar por Nginx:
    - `/api/v1/health`;
    - `/moderacion/`;
    - `/recinto/`;
15. sólo con todas las verificaciones correctas actualizar `previous` al release anterior.

No ejecutar `git pull` en producción.

## Rollback automático ante fallo de activación

Si una activación falla después de modificar `current`:

1. restaurar el symlink anterior;
2. restaurar/aplicar las unidades y configuración Nginx pertenecientes a la release anterior cuando corresponda;
3. reiniciar servicios;
4. verificar salud de la release restaurada;
5. informar claramente:
   - fallo original;
   - rollback realizado;
   - resultado de la recuperación.

Si el rollback también falla, detener cualquier acción adicional y dejar diagnóstico explícito para intervención humana.

No borrar la release fallida automáticamente.

## Rollback explícito

Debe existir un comando explícito de rollback.

Por defecto utiliza `previous`.

Puede aceptar un SHA de release preparada existente.

Debe aplicar el mismo guard institucional y las mismas verificaciones que una activación.

Un rollback exitoso puede intercambiar `current` y `previous` para permitir un roll-forward inmediato.

Nunca toca:

- `config/`;
- `logs/`.

## Herramienta de despliegue

Se prefiere una herramienta propia versionada con Python estándar antes que una colección de comandos manuales difíciles de auditar.

Puede dividirse en varios módulos/scripts si mejora claridad.

Debe ofrecer, conceptualmente:

```text
preflight
bootstrap
preparar
activar
rollback
estado
```

Los nombres exactos pueden adaptarse a DEC-001.

Requisitos:

- mensajes claros;
- exit codes útiles;
- `--help`;
- no secretos;
- no comandos construidos mediante shell cuando puedan pasarse como argv;
- no `shell=True` para acciones privilegiadas;
- validación estricta de rutas bajo `/opt/sis-leg`;
- rechazo de SHA/rutas ambiguas;
- operaciones de filesystem seguras;
- testabilidad mediante raíz alternativa o inyección de ejecutor de comandos.

`bootstrap` puede crear usuarios/directorios/permisos en la máquina real, pero no instala paquetes del SO ni copia configuración de desarrollo.

## Pruebas de la herramienta sin tocar el host

Los tests deben poder validar con directorios temporales:

- estructura inicial;
- symlinks `current`/`previous`;
- release preparada/no preparada;
- rechazo de traversal;
- checksum;
- manifest;
- guard de estado;
- activación;
- rollback;
- rollback automático ante health fallido;
- preservación de `config/` y `logs/`;
- permisos/ownership como plan declarativo cuando no sea posible aplicarlos sin root;
- idempotencia segura de bootstrap/preparación.

Los comandos externos `systemctl`, `nginx` y health pueden inyectarse/mockearse únicamente para probar la **herramienta de despliegue**.

Esto no convierte el E2E institucional de WP-027 en un test mockeado.

## Validación de configuración Nginx/systemd

Además de tests propios:

- validar sintaxis Nginx con una versión real de Nginx en CI;
- usar `systemd-analyze verify` o mecanismo oficial equivalente sobre las unidades;
- usar documentación primaria actual de systemd y Nginx conforme DEC-003.

No instalar Nginx dentro del contenedor persistente `agent-dev` sólo para satisfacer el WP.

GitHub Actions puede instalar/usar paquetes del runner efímero cuando sea necesario para verificar sintaxis.

## Smoke de la release extraída

En CI, extraer el artefacto producido y validar el runtime desde ese contenido, no desde el checkout original.

Como mínimo:

1. verificar SHA-256;
2. extraer a temporal;
3. crear `.venv` con dependencias `--no-dev`;
4. arrancar FastAPI desde la release en un puerto loopback de prueba;
5. comprobar `/api/v1/health`;
6. comprobar import/CLI `--help` del bridge sin requerir hardware;
7. comprobar que las dos SPA contienen `index.html` y assets válidos;
8. detener backend sin listener huérfano.

No iniciar evdev real en CI.

## CI obligatoria

Agregar un gate independiente, conceptualmente:

`Empaquetado · release productiva`.

Se suma a los siete jobs existentes.

El job debe:

- partir de checkout limpio;
- preparar Python 3.14/uv;
- preparar Node 24/pnpm;
- instalar dependencias con lockfiles;
- construir el paquete productivo;
- validar checksum/manifest/allowlist;
- ejecutar smoke desde la release extraída;
- validar Nginx/systemd;
- subir el artefacto productivo y checksum como artifact de GitHub Actions;
- no usar secretos;
- no desplegar nada;
- no usar `continue-on-error`.

Después de WP-028 CI debe tener **8 jobs** normales.

## Seguridad y fallos

El mecanismo debe ser fail-closed:

- checksum inválido -> no preparar;
- manifest inválido -> no preparar;
- config inválida -> no activar;
- Nginx inválido -> no activar;
- systemd units inválidas -> no activar;
- estado activo -> no activar;
- health nuevo fallido -> rollback;
- health rollback fallido -> detener y escalar.

No ocultar errores mediante retries infinitos.

Las esperas de health deben ser acotadas y diagnosticables.

2. El paquete queda identificado por SHA completo.
3. Se produce SHA-256 sidecar.
4. Existe `release.json`.
5. El paquete no contiene secretos.
6. No contiene configuración institucional.
7. No contiene logs.
8. No contiene `node_modules`.
9. No contiene `.venv` construida en desarrollo.
10. Contiene ambas SPA ya generadas.
11. Contiene runtime Python suficiente para instalar backend y bridge.
12. Uvicorn queda disponible con instalación `--no-dev`.
13. No se agrega otro servidor ASGI.
14. Producción no necesita Node/pnpm.
15. La herramienta valida checksum y manifest.
16. Rechaza path traversal/extracción insegura.
17. Una release puede prepararse sin cambiar `current`.
18. La venv se crea en la ruta final de la release.
19. La release preparada queda operacionalmente inmutable.
20. Configuración y logs quedan fuera de releases.
21. Backend usa un solo worker.
22. Backend escucha sólo en 127.0.0.1:8000.
23. Bridge usa backend 127.0.0.1:8000.
24. Control bridge escucha sólo en 127.0.0.1:8765.
25. Backend y bridge no corren como root.
26. Sólo bridge recibe grupo `input`.
27. Persistencia de devices.json tiene directorio escribible apropiado.
28. Nginx sirve Moderación bajo `/moderacion/`.
29. Nginx sirve Recinto bajo `/recinto/`.
30. Nginx proxifica `/api/v1/` sin romper rutas.
31. SSE queda sin buffering indebido.
32. No se requiere CORS.
33. No se usa Node/Nitro productivo.
34. Nginx real valida la configuración en CI.
35. Las units pasan validación oficial de systemd.
36. El guard rechaza activar con `PREPARANDO`.
37. El guard rechaza activar con `SESION_ABIERTA`.
38. Primera instalación sin runtime activo puede continuar.
39. Backend activo pero inaccesible hace fallar cerrado.
40. Cambio de `current` usa reemplazo atómico de symlink.
41. Health backend se verifica antes de considerar exitosa la activación.
42. Nginx se recarga sólo tras validación.
43. Ambas SPA se verifican a través de Nginx.
44. `previous` queda disponible tras activación exitosa.
45. Rollback explícito funciona.
46. Fallo post-switch intenta rollback automático.
47. Rollback preserva configuración.
48. Rollback preserva logs.
49. Fallo de rollback se reporta sin seguir mutando.
50. No se borran releases automáticamente.
51. Se valida configuración con parsers propietarios sin inventar reglas.
52. Logs productivos resuelven a `/opt/sis-leg/logs`.
53. Los fixtures de desarrollo no se instalan automáticamente.
54. El package smoke arranca FastAPI desde la release extraída.
55. El package smoke verifica CLI del bridge sin hardware.
56. El package smoke limpia sus procesos.
57. Existe un octavo job CI independiente para empaquetado productivo.
58. Los siete jobs anteriores permanecen.
59. El job nuevo sube paquete + checksum como artifact.
60. El job no despliega remotamente.
61. No usa secretos.
62. Documentación explica primera instalación, actualización y rollback.
63. Documentación explica diagnóstico.
64. No se realizan cambios persistentes en VPS/agent-dev.
65. No se modifica ContextosAgenticos desde implementador/revisor.
66. No se agregan dependencias externas salvo la reclasificación autorizada de Uvicorn ya bloqueada en lockfile.
67. Gates existentes siguen verdes.
68. Código/comentarios propios respetan DEC-001.
69. Herramientas/documentación externa respetan DEC-003.
70. Flujo de agentes respeta DEC-007/DEC-017.

## Pruebas obligatorias

Además de tests nuevos de empaquetado/despliegue:

```bash
git diff --check
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
pnpm check:types
pnpm check:contrato
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
pnpm test:e2e:integrado
pnpm empaquetar:produccion
```

Agregar la validación específica del artefacto/release que se defina.

El candidato remoto debe tener los **8 jobs CI** verdes sobre el SHA exacto.

## Validación local en agent-dev

El implementador debe:

1. construir el paquete desde checkout limpio;
2. inspeccionar su manifest y allowlist;
3. verificar SHA-256;
4. extraerlo en un directorio temporal;
5. ejecutar el smoke runtime permitido sin systemd real;
6. ejecutar tests de la herramienta con raíz temporal;
7. confirmar que no modificó:
   - `/etc`;
   - servicios persistentes;
   - Docker;
   - Supervisor;
   - Tailscale;
   - Caddy;
   - firewall;
8. confirmar `git status --short` limpio salvo outputs ignorados.

No instalar Nginx persistentemente dentro de agent-dev.

## Revisión independiente

El revisor debe prestar especial atención a:

- integridad/seguridad de extracción tar;
- fail-closed del guard institucional;
- atomicidad de `current`;
- rollback y rollback fallido;
- ownership/permisos;
- escritura persistente de `devices.json`;
- un solo worker;
- loopback;
- Nginx SSE;
- no CORS;
- ausencia de config/logs en releases;
- ausencia de Node runtime;
- instalación `--no-dev` real;
- Uvicorn runtime;
- smoke desde artefacto extraído;
- octavo gate CI;
- que ningún test de despliegue mockeado sea presentado como E2E institucional.

## Herramientas externas

Conforme DEC-003, el implementador y revisor deben consultar documentación primaria vigente para:

- systemd unit files, usuarios, grupos y `systemd-analyze verify`;
- Nginx `proxy_pass`, `try_files`, SSE/`proxy_buffering`;
- Uvicorn CLI/runtime;
- uv `sync --frozen --no-dev --all-packages`;
- Python `tarfile`/extracción segura si se utiliza;
- GitHub Actions artifacts si se modifica CI.

Si un MCP no está disponible, registrar fallback.

## Decisiones que requieren escalamiento

Detener la parte afectada y escalar DT-038 si se propone:

- servidor ASGI distinto de Uvicorn;
- Gunicorn;
- más de un worker;
- Docker/Compose;
- servidor Node productivo;
- nuevo origen/API/CORS;
- modificar rutas HTTP;
- cambiar estructura conceptual de config/logs;
- instalar automáticamente paquetes del SO;
- deploy automático por SSH/CI;
- TLS;
- backup externo;
- persistencia/recovery de estado institucional;
- modificación del backend sólo para facilitar despliegue;
- una dependencia externa nueva no autorizada;
- ejecutar cambios reales en producción durante este WP.

## Documentación de intervención externa

Como WP-028 no debe modificar el VPS ni la máquina productiva durante implementación/revisión, no corresponde registrar una intervención administrativa como si hubiese ocurrido.

Si durante validación se descubre que el entorno `agent-dev` necesita un cambio persistente real, detener esa parte y solicitar intervención separada.
