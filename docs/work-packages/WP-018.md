# WP-018 - Cliente TypeScript derivado de OpenAPI con REST, SSE y reconexión

## Estado documental

`APROBADO`

## Objetivo

Implementar `packages/api-client/` como cliente TypeScript compartido y testeado para consumir la API canónica de SIS-Leg, derivando sus tipos desde OpenAPI, encapsulando REST/SSE, normalizando errores y resolviendo de forma única la recuperación de snapshot, reconexión y control de `revision` para Moderación y Recinto.

## Resultado esperado

Al completar este WP debe existir un paquete `@sis-leg/api-client` utilizable por los frontends posteriores que:

- derive y versione tipos TypeScript desde el OpenAPI generado por FastAPI;
- detecte drift backend -> OpenAPI -> TypeScript en validaciones automáticas;
- exponga una superficie `ClienteModeracion` con snapshots, SSE y comandos del operador;
- exponga una superficie `ClienteRecinto` estrictamente de solo lectura;
- use `fetch` y `EventSource` nativos mediante fronteras inyectables/testeables;
- mantenga un único protocolo de sincronización `snapshot -> SSE` y recuperación `error SSE -> snapshot -> SSE nuevo`;
- trate correctamente el reinicio de `revision` después de un restart del backend;
- no duplique reglas de negocio, DTOs manuales ni lógica visual de los frontends.

## Dependencias

- DEC-013 `APROBADA`: contrato de proyecciones, mensajes SSE completos y secreto temporal.

## Alcance

### 1. Generación y artefactos de contrato

- Incorporar `openapi-typescript@7.13.0` como la única nueva dependencia directa externa aprobada para este WP, en calidad de `devDependency` del tooling de `packages/api-client/`.
- Definir un comando determinista que genere un snapshot OpenAPI desde la aplicación FastAPI vigente sin depender de red ni de un servidor externo.
- Versionar ese snapshot dentro de `packages/api-client/`.
- Generar y versionar los tipos TypeScript derivados desde ese snapshot mediante `openapi-typescript`.
- Definir comandos claros de regeneración local.
- Agregar gates que detecten drift entre backend/OpenAPI y OpenAPI/tipos TypeScript.
- La ubicación exacta de los artefactos dentro de `packages/api-client/` puede elegirse durante la implementación, pero debe ser estable, documentada y consumida por los scripts/versionado.

### 2. Cliente REST base

- Crear una frontera común de configuración con base URL y primitivas de transporte inyectables.
- Utilizar `fetch` nativo en runtime.
- Encapsular serialización de JSON, ausencia de body para comandos que no lo usan, respuestas `204 No Content` y multipart/form-data para Orden del Día.
- No reconstruir validaciones reglamentarias ni capacidades del backend.

### 3. Errores uniformes

- Definir una representación discriminada para:
  - respuesta HTTP no exitosa;
  - fallo de transporte/red;
  - fallo de protocolo/parsing;
  - cancelación/disposición cuando corresponda.
- Preservar `codigo` y `mensaje` exactamente cuando el backend responda ese contrato.
- Conservar status y cuerpo/detalle útil para respuestas de validación que no tengan `codigo` estable.
- No inventar códigos de dominio para reemplazar información ausente.

### 4. Superficie de Moderación

Exponer una interfaz/fábrica pública equivalente a `ClienteModeracion` que incluya:

- obtener snapshot de Moderación;
- iniciar/gestionar sincronización SSE de Moderación;
- preparar sala;
- actualizar preparación;
- cancelar preparación;
- abrir sesión;
- actualizar sesión;
- cerrar sesión;
- cargar Orden del Día;
- descartar Orden del Día;
- abrir votación;
- finalizar votación;
- emitir desempate presidencial;
- otorgar palabra;
- quitar palabra.

Los nombres propios nuevos del paquete deben respetar DEC-001; la lista anterior es conceptual y no obliga a calcar nombres del backend si una nomenclatura TypeScript más clara en español mantiene el contrato.

El cliente de Moderación no debe exponer como comando del operador la ruta de entrada física utilizada por el bridge.

### 5. Superficie de Recinto

Exponer una interfaz/fábrica pública equivalente a `ClienteRecinto` que contenga únicamente:

- obtener snapshot público;
- iniciar/gestionar sincronización SSE pública;
- detener/disponer esa sincronización.

Debe ser imposible invocar desde esa superficie métodos mutantes de preparación, sesión, votación, palabra u Orden del Día sin escapar deliberadamente al API interno del paquete.

### 6. SSE y parsing

- Utilizar `EventSource` nativo mediante una fábrica/frontera inyectable.
- Consumir el evento funcional `estado` y su `data` JSON completo.
- No implementar deltas ni historial/replay.
- Tratar errores de JSON/protocolo como fallo de sincronización que fuerza recuperación segura.
- Mantener el parseo SSE común entre Moderación y Recinto sin mezclar sus DTOs.

### 7. Sincronización inicial

El flujo normal debe ser:

1. obtener snapshot REST;
2. publicarlo/entregarlo como baseline vigente;
3. abrir SSE;
4. aceptar el primer payload completo igual o posterior para esa baseline;
5. continuar con revisiones completas posteriores.

Una mutación ocurrida entre snapshot y apertura de SSE no debe perderse porque el primer evento del stream reemplaza/actualiza la baseline cuando corresponde.

### 8. Control de `revision`

- Dentro de una conexión/época vigente, no retroceder a una revisión menor por duplicación/reordenamiento.
- Revisiones iguales deben poder tratarse de forma idempotente.
- Saltos de revisiones son válidos porque cada payload es completo.
- El paquete no debe exigir recibir todos los números intermedios.

### 9. Restart del backend

Una recuperación iniciada por snapshot REST crea deliberadamente una nueva baseline incluso si su `revision` es numéricamente menor que la observada antes de la caída.

Debe existir prueba explícita del caso:

```text
estado previo: revision alta
backend reinicia
snapshot de recuperación: revision 0 + SIN_PREPARAR
```

El cliente debe adoptar el snapshot nuevo y descartar el estado viejo.

No se incorpora epoch persistente ni recovery del backend en este WP.

### 10. Reconexión controlada

Ante error/pérdida del SSE:

1. cerrar el `EventSource` vigente para impedir que la reconexión automática nativa continúe por su cuenta;
2. esperar según estrategia de backoff acotada y cancelable;
3. recuperar snapshot REST;
4. adoptar ese snapshot como nueva baseline;
5. crear un `EventSource` nuevo;
6. repetir mientras el consumidor siga activo.

La estrategia exacta de backoff puede definirse localmente, debe tener límites razonables y ser inyectable/controlable para tests.

No implementar polling periódico.

### 11. Ciclo de vida/cancelación

- Exponer una operación clara de `cerrar`, `dispose`, `abortar` o equivalente en español coherente con DEC-001.
- Cancelar esperas de reconexión pendientes.
- Cerrar `EventSource` activo.
- Evitar callbacks/actualizaciones posteriores a la disposición.
- No acumular timers, listeners ni conexiones al reconectar repetidamente.

### 12. Integración con tooling del monorepo

- Incorporar el paquete a los gates TypeScript/format/testing aplicables del monorepo sin agregar dependencias externas no aprobadas.
- Mantener `pnpm-lock.yaml` actualizado únicamente por la incorporación aprobada de `openapi-typescript@7.13.0` y sus dependencias transitivas legítimas.
- Actualizar CI para ejecutar los checks de drift del contrato y los tests del paquete cuando corresponda.
- Cualquier necesidad de otra dependencia directa debe escalarse por DT-038.

### 13. Documentación del paquete

Documentar como mínimo:

- cómo regenerar OpenAPI y tipos;
- cómo ejecutar los checks de drift;
- cómo construir cada cliente;
- flujo de sincronización/reconexión;
- modelo de errores;
- diferencia entre Moderación y Recinto;
- política de `revision` y restart.

## Criterios de aceptación

1. Existe `@sis-leg/api-client` funcional y exporta superficies públicas separadas para Moderación y Recinto.
2. El snapshot OpenAPI versionado puede regenerarse determinísticamente desde el backend actual sin red externa.
3. Los tipos TypeScript se generan desde ese snapshot con `openapi-typescript@7.13.0` y no existen DTOs raíz duplicados manualmente como fuente alternativa.
4. Un check automático falla si cambia el OpenAPI real del backend sin actualizar el snapshot versionado.
5. Otro check automático falla si el snapshot cambia sin regenerar los tipos TypeScript.
6. `ClienteModeracion` cubre snapshots/SSE y todos los comandos actuales destinados a Moderación enumerados en este WP.
7. `ClienteRecinto` no expone métodos mutantes.
8. REST procesa correctamente JSON, `204 No Content`, errores estructurados y multipart de Orden del Día.
9. Los errores conservan status y, cuando existan, `codigo` y `mensaje` del backend.
10. La sincronización inicial ejecuta snapshot antes de SSE.
11. El primer SSE completo puede avanzar el estado si hubo una mutación entre snapshot y conexión.
12. El cliente descarta revisiones anteriores dentro de una baseline vigente y acepta saltos hacia revisiones posteriores.
13. Una recuperación por snapshot acepta una revisión numéricamente menor después de un restart y reemplaza el estado previo.
14. Ante fallo SSE, el cliente cierra la conexión fallada, obtiene snapshot y solo entonces abre un stream nuevo.
15. La reconexión puede repetirse sin acumular recursos y puede cancelarse de forma determinista.
16. No existe polling periódico ni dependencia de historial SSE.
17. No se agregó ninguna dependencia runtime externa nueva.
18. La única nueva dependencia directa externa del WP es `openapi-typescript@7.13.0` como `devDependency` aprobada.
19. Código propio nuevo usa nomenclatura en español conforme DEC-001 salvo contratos/identificadores generados o impuestos externamente.
20. Comentarios/documentación explican suficientemente generación, errores, revisión y reconexión.
21. Los gates y tests aplicables quedan integrados a CI y verdes.
22. El documento conserva el formato parseable exigido por `FORMATO_WP_LANZADORES.md`.

## Pruebas obligatorias

### Generación/contrato

- exportación OpenAPI determinista;
- check de snapshot actualizado;
- generación de tipos;
- check de tipos actualizados;
- prueba/gate que demuestre drift detectable en ambas fronteras.

### REST

- GET snapshot Moderación exitoso;
- GET snapshot Recinto exitoso;
- comando sin body y `204`;
- comando JSON con body;
- multipart de Orden del Día;
- error HTTP `{ codigo, mensaje }` preservado;
- error de validación no estructurado preservando status/detalle;
- fallo de red;
- cuerpo JSON inválido cuando se esperaba JSON;
- cancelación cuando corresponda.

### SSE/sincronización

- snapshot inicial ocurre antes de crear SSE;
- primer evento SSE se procesa como estado completo;
- revisión igual/idempotente;
- revisión anterior se descarta dentro de la baseline;
- salto de revisiones se acepta;
- mutación conceptual snapshot -> primer SSE no se pierde;
- evento SSE inválido fuerza recuperación segura;
- error SSE cierra el `EventSource` fallado;
- recuperación obtiene snapshot antes de crear el nuevo SSE;
- múltiples ciclos de reconexión sin acumulación de listeners/timers;
- disposición durante conexión activa;
- disposición durante backoff;
- disposición durante recuperación REST;
- no existen actualizaciones posteriores a disposición.

### Restart de backend

- baseline previa con revisión alta;
- desconexión;
- snapshot nuevo con revisión menor/cero;
- aceptación del snapshot nuevo;
- SSE posterior continúa desde la nueva baseline.

### Separación de superficies

- tests de tipos y/o compilación que demuestren que la superficie pública del Recinto carece de comandos mutantes;
- Moderación sí expone los comandos aprobados.

Las pruebas de reconexión/backoff deben usar relojes falsos, callbacks controlados o mecanismos equivalentes; no sleeps reales prolongados.

## Invariantes y restricciones

- FastAPI/Pydantic/OpenAPI siguen siendo la fuente técnica canónica del HTTP.
- `EstadoOperativo` continúa autoritativo; el cliente no crea reglas ni estado institucional.
- El secreto público sigue garantizado por el backend; el paquete no transforma `EstadoModeracion` en estado público.
- No cambiar rutas o schemas backend para simplificar el cliente sin una necesidad real y escalamiento correspondiente.
- No generar manualmente una segunda taxonomía de DTOs que pueda divergir de OpenAPI.
- `revision` no es persistente ni global entre restarts.
- No asumir continuidad después de una desconexión sin snapshot recovery.
- No dejar que `EventSource` reconecte automáticamente saltando ese recovery.
- No agregar otra dependencia directa por conveniencia.
- No incorporar credenciales, tokens ni secretos.
- Aplican DEC-001, DEC-003, DEC-007, DEC-013, DEC-014 y DT-038.
- El formato máquina de `Estado documental` y `Dependencias` debe mantenerse compatible con los lanzadores.

## Herramientas MCP y documentación técnica externa

- Aplicar DEC-003.
- Para `openapi-typescript`, consultar Context7 cuando esté disponible y contrastar con documentación oficial vigente si es necesario.
- Para `EventSource`, `fetch`, `AbortSignal` y timers, preferir documentación oficial MDN/WHATWG o equivalente autoritativa cuando Context7 no cubra el contrato.
- Para FastAPI/OpenAPI, preferir documentación oficial de FastAPI/Pydantic.

- GitHub MCP/integración equivalente se usa únicamente dentro de la autoridad permitida.
