# WP-075 - Captura exclusiva de los numpads de banca en Device Bridge

## Estado documental

`APROBADO`

## Objetivo

Evitar que las pulsaciones de los teclados numéricos físicos asignados a las bancas lleguen al escritorio gráfico y al navegador del equipo de Moderación, sin dejar de ser capturadas por Device Bridge ni enviadas al backend.

La instalación objetivo continúa usando una única PC para Moderación, Device Bridge y los hubs USB de los dispositivos de banca.

## Resultado esperado

Mientras Device Bridge está operativo:

- cada dispositivo físico que forma parte del **mapping efectivo** `fingerprint -> devXX` queda tomado en forma exclusiva por el proceso mediante la capacidad `EVIOCGRAB` expuesta por `python-evdev`;
- las pulsaciones de esos numpads llegan solamente a Device Bridge y no se escriben en campos de texto, terminales u otras aplicaciones del escritorio;
- teclado y mouse del moderador, y cualquier otro dispositivo no mapeado, siguen funcionando normalmente en el sistema operativo;
- una desconexión, reconexión o remapeo actualiza de forma segura qué dispositivos deben estar capturados en exclusiva;
- al detenerse o perderse un dispositivo, la exclusividad se libera junto con su descriptor.

## Dependencias

- WP-019 `INTEGRADO`: Device Bridge Linux basado en `evdev`.
- WP-020 `INTEGRADO`: remapeo físico -> lógico y mapping efectivo dinámico.

## Alcance

- Extender la abstracción `AdaptadorEntradaFisica` para poder adquirir y liberar de forma explícita la captura exclusiva de un dispositivo.
- En `AdaptadorEvdevLinux`, utilizar `InputDevice.grab()` / `ungrab()` de forma idempotente desde la perspectiva del bridge y mantener trazabilidad local del estado de exclusividad.
- Aplicar exclusividad **únicamente** a dispositivos cuyo fingerprint pertenezca al mapping efectivo vigente.
- No capturar en exclusiva dispositivos descubiertos pero no mapeados.
- Reconciliar la exclusividad cuando cambia el mapping efectivo por remapeo:
  - el nuevo fingerprint efectivo debe adquirir exclusividad;
  - el fingerprint reemplazado debe liberarla si deja de estar mapeado;
  - un cambio no debe dejar dos dispositivos apropiándose silenciosamente del mismo `devXX`.
- Reaplicar exclusividad después de desconectar/reconectar físicamente un dispositivo mapeado.
- Liberar explícitamente la exclusividad en el cierre normal antes de cerrar el descriptor; el cierre del descriptor sigue siendo la última garantía de liberación del recurso.
- Si la adquisición exclusiva de un dispositivo **mapeado** falla, no degradar silenciosamente a "captura compartida": el bridge debe registrar un diagnóstico claro y ese dispositivo no debe despachar pulsaciones funcionales al backend hasta que la exclusividad se consiga.
- Mantener el comportamiento actual de dispositivos no mapeados y del flujo de candidato de remapeo, salvo lo estrictamente necesario para reconciliar exclusividad después de una confirmación.
- Agregar al adaptador falso capacidades equivalentes para probar la política sin hardware real.
- Documentar en Device Bridge y manual de soporte que los numpads mapeados quedan dedicados a SISLeg mientras el servicio está activo.
- Agregar pruebas automatizadas que garanticen que el teclado del operador/no mapeado nunca recibe `grab()`.

## Fuera de alcance

- Interceptar teclas desde JavaScript en Moderación.
- Bloquear globalmente teclas numéricas o `Numpad*` en el navegador.
- Configurar X11, Wayland, libinput o reglas udev para deshabilitar teclados en el escritorio.
- Cambiar el mapping físico `fingerprint -> devXX`.
- Cambiar teclas, acciones de voto/palabra, reglas de negocio ni normalización existente.
- Rediseñar la UI.
- Capturar en exclusiva dispositivos no mapeados sólo porque tengan capacidad `EV_KEY`.
- Resolver en este WP la selección de un dispositivo completamente nuevo durante el primer keydown de un remapeo; ese evento no debe justificar secuestrar teclados desconocidos del operador.
- Exigir una segunda PC para Device Bridge.

## Criterios de aceptación

- Un dispositivo mapeado que se descubre correctamente adquiere captura exclusiva antes de poder despachar pulsaciones funcionales.
- Una pulsación de un numpad mapeado sigue llegando al flujo normal `evdev -> Device Bridge -> POST /api/v1/entradas/tecla`.
- Ese mismo dispositivo no queda disponible para otras aplicaciones mientras la exclusividad está activa, conforme al contrato de `EVIOCGRAB`.
- Un dispositivo no mapeado nunca recibe captura exclusiva por el mero hecho de ser un teclado.
- El teclado normal del moderador permanece operativo aunque Device Bridge esté ejecutándose.
- Un fallo de `grab()` sobre un dispositivo mapeado produce diagnóstico explícito y evita el despacho funcional de sus pulsaciones hasta recuperar exclusividad.
- Una reconexión física de un numpad mapeado vuelve a adquirir exclusividad.
- Un remapeo TEMPORAL o PERSISTENTE reconcilia quién queda capturado según el mapping efectivo resultante.
- El dispositivo que deja de estar mapeado libera exclusividad.
- El cierre normal libera exclusividad y descriptores sin excepciones espurias por doble `ungrab()`.
- El cierre/desconexión es idempotente desde el punto de vista del servicio.
- Ninguna prueba requiere privilegios ni hardware real en CI; el comportamiento de política se cubre con fakes/mocks.
- Se documenta una verificación humana sobre Linux real: con Moderación enfocada en un campo editable, pulsar las teclas funcionales desde los numpads mapeados no inserta caracteres, mientras el teclado del moderador sí escribe normalmente.
- La solución no depende de cambios en HTTP, navegador ni frontend.

## Pruebas obligatorias

Como mínimo:

- unitarias del adaptador real con manejador evdev simulado:
  - `grab()` una vez;
  - `ungrab()` una vez;
  - manejo de error al adquirir;
  - cierre sin doble liberación;
- pruebas del adaptador falso para estado exclusivo;
- pruebas de servicio:
  - mapeado -> exclusividad requerida antes de dispatch;
  - no mapeado -> nunca grabado;
  - fallo de exclusividad -> cero POST funcional;
  - reconexión -> reacquire;
  - cambio de mapping efectivo -> liberar/adquirir correctamente;
  - detener -> liberar todo;
- regresión completa de `tests/device_bridge/`;
- `uv run ruff check .`;
- `uv run ruff format --check .`;
- `uv run pyright`;
- `uv run pytest`;
- `git diff --check`.

No requiere Playwright para la implementación. La verificación final con navegador + hardware físico corresponde a HUMAN_GATE sobre Linux real.

## Invariantes y restricciones

- FastAPI continúa siendo la única autoridad de reglas de negocio.
- El bridge no interpreta voto, quórum, palabra ni validez funcional.
- Sólo los fingerprints del mapping efectivo pueden quedar capturados en exclusiva.
- La exclusividad es fail-safe: no se permite continuar silenciosamente en modo compartido para un dispositivo mapeado.
- Ninguna operación de captura exclusiva puede secuestrar el teclado del operador por heurística de nombre, vendor/product o mera capacidad `EV_KEY`.
- No agregar dependencias directas nuevas: `python-evdev` ya forma parte del proyecto.
- Sin rebase ni force-push.
- El implementador/revisor no hace merge ni cleanup.
- El cambio debe soportar hotplug y el remapeo vigente.

## Herramientas MCP y documentación técnica externa

Aplicar DEC-003. Verificar el contrato de `InputDevice.grab()` y `ungrab()` en la documentación oficial de `python-evdev`. No inferir semántica de exclusividad desde ejemplos de terceros.
