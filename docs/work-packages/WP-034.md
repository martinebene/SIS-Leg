# WP-034 - Simulador visual web de dispositivos lógicos para prueba humana y diagnóstico

## Estado documental

`APROBADO`

## Objetivo

Crear una tercera aplicación web independiente de SIS-Leg, orientada a prueba humana y diagnóstico, que represente visualmente al menos los 12 dispositivos lógicos `dev01..dev12` y permita emitir mediante botones las seis pulsaciones funcionales de uso habitual:

- voto afirmativo -> tecla `1`;
- abstención -> tecla `2`;
- voto negativo -> tecla `3`;
- pedir/retirar/finalizar palabra -> tecla `7`;
- test -> tecla `8`;
- presentarse/ausentarse -> tecla `9`.

La aplicación debe utilizar exclusivamente los contratos HTTP reales del sistema, sin hardware físico y sin duplicar reglas institucionales. Su finalidad es permitir que pocas personas puedan operar simultáneamente múltiples dispositivos lógicos durante pruebas funcionales completas y conservar una herramienta visual reutilizable para diagnóstico futuro.

## Resultado esperado

Al integrar este WP debe existir una nueva SPA Nuxt bajo una ruta propia, conceptualmente:

```text
/simulador/
```

que:

- muestre simultáneamente `dev01..dev12` en una pantalla Full HD sin scroll vertical ni horizontal;
- presente seis botones compactos y claramente identificados por dispositivo;
- emita cada pulsación real a `POST /api/v1/entradas/tecla`;
- muestre estado de conexión y diagnóstico útil derivado del backend real;
- utilice snapshot REST + SSE para mantenerse sincronizada;
- mantenga cada dispositivo deliberadamente mínimo: identificador `devXX` y sus seis botones, sin cargar identidad, banca, presencia, voto, palabra, test ni diagnósticos individuales;
- concentre toda la información contextual en un panel general y en un log global visible de pulsaciones/respuestas;
- permita a dos o tres operadores manejar varios dispositivos cada uno durante una prueba humana;
- no sustituya ni elimine el simulador CLI existente;
- no pase por el `device-bridge`, porque simula dispositivos lógicos y no hardware físico;
- no modifique reglas de negocio, contratos institucionales ni auditoría.

En producción, `/simulador/` debe quedar disponible exclusivamente desde `localhost`/loopback. Nginx debe rechazar accesos remotos a esa ruta aunque `/moderacion/`, `/recinto/` y `/api/v1/` continúen con su política normal.

## Alcance

### 1. Nueva SPA independiente

Crear una aplicación Nuxt independiente bajo:

```text
apps/simulador/
```

Debe conservar la separación arquitectónica de Moderación y Recinto.

No convertir `apps/moderacion` en una aplicación multipágina ni incrustar el simulador como panel interno de Moderación.

La SPA puede reutilizar:

- `@sis-leg/api-client`;
- utilidades o componentes genuinamente compartibles ya existentes;
- estilos/tokens comunes cuando hacerlo no acople responsabilidades.

No debe copiar masivamente componentes de Moderación.

### 2. Ruta, mismo origen y acceso productivo

La ruta será:

```text
/simulador/
```

En desarrollo debe funcionar bajo el mismo origen que:

```text
/moderacion/
/recinto/
/api/v1/
```

La aplicación consume `/api/v1` por mismo origen por defecto.

En producción la SPA debe quedar incluida en el artefacto, pero Nginx permitirá acceder a `/simulador/` únicamente desde loopback (`127.0.0.1` y `::1` o equivalente correcto). Un cliente remoto de la LAN no debe poder abrir esa ruta. Esta restricción no debe impedir que la propia SPA, abierta localmente en la máquina productiva, consuma `/api/v1/` por mismo origen.

### 3. Dispositivos visibles

La interfaz debe representar como mínimo:

```text
dev01 .. dev12
```

Los 12 deben estar visibles simultáneamente en pantalla completa a 1920x1080 sin necesitar scroll.

La composición de referencia debe priorizar una grilla compacta y legible. El número exacto de columnas/filas puede resolverse localmente si cumple el criterio observable.

En resoluciones alternativas debe responder de forma controlada conforme DT-020; no se exige conservar simultaneidad sin scroll en toda resolución arbitraria.

### 4. Tarjeta mínima por dispositivo

Cada tarjeta debe contener únicamente:

- identificador lógico `devXX`;
- los seis botones funcionales definidos en la sección siguiente.

No mostrar dentro de cada tarjeta:

- concejal ni banca;
- presencia;
- estado de test;
- estado de palabra;
- si votó o qué votó;
- resultado HTTP individual persistente;
- latencia;
- mensajes de diagnóstico.

Puede existir feedback visual efímero del click/request en curso si ayuda a evitar dobles pulsaciones accidentales, pero no debe convertir la tarjeta en un panel de estado.

Toda información de contexto y diagnóstico se concentra en el panel general y en el log global.

### 5. Seis botones funcionales

Cada dispositivo debe tener exactamente seis acciones principales visibles:

| Etiqueta humana | Tecla enviada |
|---|---|
| Afirmativo | `1` |
| Abstención | `2` |
| Negativo | `3` |
| Palabra | `7` |
| Test | `8` |
| Pres. / Aus. | `9` |

El botón de presencia debe usar una etiqueta neutra y compacta, por ejemplo `Pres. / Aus.`, sin revelar dentro de la tarjeta si ese dispositivo está actualmente presente o ausente. La acción siempre envía tecla `9` y FastAPI decide el resultado.

La acción `Palabra` puede mantener una etiqueta única compacta aunque la tecla 7 tenga semánticas distintas según el estado actual.

### 6. Regla crítica: no duplicar negocio

Los botones no deben habilitarse/deshabilitarse replicando reglas institucionales del backend.

Ejemplos:

- Afirmativo puede enviarse durante `PREPARANDO` y el backend debe responder el rechazo correspondiente.
- Palabra puede enviarse en un estado donde no corresponda y el backend decide.
- Test o presencia siguen la misma regla.

La SPA puede impedir temporalmente el doble click involuntario del mismo control mientras su request exacta está en vuelo, pero no debe imponer una matriz propia de estados permitidos.

El propósito diagnóstico exige observar también rechazos funcionales reales.

### 7. Emisión de pulsaciones

Cada botón debe emitir exclusivamente:

```http
POST /api/v1/entradas/tecla
Content-Type: application/json
```

con:

```json
{
  "dispositivo": "dev05",
  "tecla": "1"
}
```

No importar servicios internos del backend ni invocar lógica Python directamente.

No pasar por el device-bridge.

No usar fingerprints físicos.

No crear un endpoint alternativo especial para el simulador salvo defecto contractual real escalado al ORCHESTRATOR.

### 8. Cliente API

El camino preferido es extender `@sis-leg/api-client` con una frontera explícita para entrada lógica/simulador si el endpoint todavía no está expuesto por el cliente TypeScript.

Esa incorporación debe:

- derivar tipos desde OpenAPI cuando corresponda;
- conservar el body exacto del endpoint;
- no mezclar la entrada lógica con `ClienteModeracion` si eso viola la separación ya documentada;
- evitar duplicar wrappers `fetch` ad hoc en la SPA si el paquete compartido puede expresar el contrato limpiamente.

### 9. Panel general de estado

La SPA debe obtener la proyección real de Moderación mediante:

1. snapshot REST;
2. SSE;
3. recuperación de snapshot ante reconexión.

Debe existir un único panel general compacto, separado de las 12 tarjetas, que muestre como mínimo:

- conexión al backend: conectado / reconectando / desconectado;
- `estado_global`;
- revisión monotónica actual;
- presentes y quórum cuando existan;
- número/estado de sesión o preparación cuando esté disponible;
- estado resumido de la votación activa/reciente cuando exista;
- última latencia HTTP observada o un resumen equivalente;
- último error técnico de transporte/protocolo si existe;
- indicación explícita de que las pulsaciones del simulador se envían directamente a FastAPI y no atraviesan el device-bridge.

Puede incorporar otros datos generales ya presentes en `EstadoModeracion` si son útiles para diagnóstico y caben sin desplazar la grilla ni introducir scroll en Full HD.

No agregar estado por dispositivo al panel general ni pedir cambios de backend sólo para enriquecer esta pantalla.

### 10. Log global visible y autoscrolleable

Debe existir un log visible en la propia pantalla, compacto y con autoscroll hacia la entrada más reciente.

Cada pulsación iniciada desde la SPA debe agregar una entrada con información suficiente para diagnóstico:

- hora local;
- dispositivo `devXX`;
- acción humana y tecla enviada;
- status HTTP cuando exista;
- `aceptada` cuando exista;
- `motivo` cuando exista;
- latencia aproximada;
- error técnico cuando no hubo respuesta válida.

El log representa la respuesta real de FastAPI. El `device-bridge` no participa en este camino porque esta SPA simula dispositivos lógicos, no hardware físico.

El historial debe:

- conservar sólo una cantidad acotada de entradas en memoria;
- autoscrollear normalmente al último evento;
- no persistirse en disco;
- no convertirse en auditoría institucional;
- no generar polling ni tráfico adicional sólo para completar el diagnóstico.

Puede incluir una acción local para limpiar el log si no agrega complejidad significativa.

### 11. Concurrencia de operadores humanos

La UI no debe serializar globalmente todas las tarjetas.

Debe ser posible pulsar dispositivos distintos de forma muy cercana o concurrente para ejercitar la serialización real del backend.

No implementar cola durable, retries automáticos ni replay de pulsaciones.

Cada click humano genera como máximo un intento HTTP.

### 12. Diseño visual

La pantalla debe ser deliberadamente utilitaria y compacta, no una consola técnica.

Requisitos:

- 12 dispositivos simultáneos en Full HD;
- botones pequeños pero claramente pulsables con mouse/touch;
- diferencia visual clara entre Afirmativo, Abstención y Negativo;
- tarjetas deliberadamente mínimas, sin datos individuales de estado;
- panel general y log visibles sin ocupar el espacio necesario para las 12 tarjetas;
- ausencia de modales para la interacción normal;
- no requerir scroll para las 12 tarjetas en 1920x1080;
- no ocultar dispositivos detrás de pestañas, carruseles o paginación;
- mantener una cabecera de diagnóstico compacta;
- mostrar de forma inequívoca que se trata de un **SIMULADOR** que genera entradas reales en el backend al que está conectado;
- log global autoscrolleable visible sin requerir cambiar de pantalla.

La implementación debe evitar asumir colores como única codificación del sentido de voto.

### 13. Uso humano previsto

La herramienta debe soportar explícitamente una modalidad de prueba donde dos o tres personas controlen varios dispositivos cada una.

No se requiere autenticación individual ni asociación operador -> dispositivo en este WP.

No se requiere grabar quién hizo click.

### 14. Integración con desarrollo

Actualizar el harness de desarrollo para que el comando canónico correspondiente permita disponer simultáneamente de:

```text
/moderacion/
/recinto/
/simulador/
/api/v1/
```

sin cambiar el principio de mismo origen.

El simulador CLI existente debe seguir funcionando exactamente como herramienta de terminal y escenarios automatizados.

### 15. Build y empaquetado

La nueva SPA debe participar de:

- pnpm workspace;
- lint;
- format;
- typecheck;
- tests unitarios;
- build estático;
- verificaciones CI aplicables.

El build raíz debe producir también la SPA del simulador.

El empaquetado productivo debe incluir sus archivos estáticos de manera reproducible, sin introducir Node como runtime.

Nginx debe servir `/simulador/` únicamente a clientes loopback en producción y rechazar accesos remotos a esa ruta.

### 16. Pruebas automatizadas

Agregar pruebas deterministas que cubran al menos:

- render de `dev01..dev12`;
- las seis acciones por tarjeta con mapping correcto a `1/2/3/7/8/9`;
- body exacto `{dispositivo, tecla}`;
- aceptación funcional;
- rechazo funcional;
- error de transporte;
- ausencia de retry;
- dos dispositivos enviando de forma concurrente;
- etiqueta neutra `Pres. / Aus.` que siempre envía tecla `9`;
- ausencia de datos individuales en cada tarjeta salvo `devXX` y botones;
- estado de conexión/reconexión en panel general;
- resumen general de quórum/votación cuando existe;
- log global limitado y autoscrolleable;
- ausencia de reglas locales que bloqueen una pulsación por estado institucional;
- viewport Full HD sin scroll para las 12 tarjetas;
- al menos una resolución alternativa conforme DT-020.

### 17. E2E integrado

Extender o agregar un recorrido Playwright integrado que utilice la nueva SPA contra FastAPI real y demuestre como mínimo:

1. iniciar desde snapshot real;
2. usar `dev01` para tecla 9 y observar presencia;
3. usar tecla 8 y observar test;
4. con sesión/votación preparada por el harness, emitir 1/2/3 desde distintos dispositivos;
5. emitir 7 y observar efecto de palabra;
6. comprobar que un rechazo real del backend se muestra como rechazo y no se oculta;
7. emitir pulsaciones cercanas desde dos dispositivos y conservar orden/estado coherente;
8. no dejar listeners/procesos huérfanos.

No reemplazar los E2E existentes; agregarlos o ampliarlos sin reducir cobertura.

## Criterios de aceptación

1. Existe una tercera SPA independiente `apps/simulador`.
2. `/simulador/` funciona en el stack integrado de desarrollo bajo mismo origen.
3. Se ven `dev01..dev12` simultáneamente en 1920x1080 sin scroll.
4. Cada dispositivo muestra seis acciones humanas: Afirmativo, Abstención, Negativo, Palabra, Test y Pres./Aus.
5. Las acciones envían exactamente `1`, `2`, `3`, `7`, `8` y `9` respectivamente.
6. Cada click produce como máximo un intento HTTP.
7. No hay retries ni replay.
8. FastAPI sigue siendo autoridad exclusiva para aceptar/rechazar.
9. La UI permite enviar acciones aunque sean funcionalmente inválidas en el estado actual, para observar el rechazo real.
10. El simulador no usa el device-bridge ni fingerprints.
11. La sincronización usa snapshot + SSE y muestra su estado técnico en un panel general.
12. Se muestran presentes/quórum y estado global en el panel general cuando existen.
13. Se muestra un resumen general útil de votación cuando existe sin crear nuevo estado autoritativo.
14. Cada tarjeta contiene sólo `devXX` y los seis botones, sin información individual adicional.
15. Existe un log global breve, autoscrolleable y sólo en memoria.
16. Pulsaciones de dispositivos distintos pueden solaparse/concurrir.
17. El simulador CLI continúa operativo y sin regresiones.
18. El build y CI incluyen la tercera SPA.
19. El artefacto sigue siendo reproducible.
20. No se introduce Node como runtime productivo.
21. No se modifica ninguna regla institucional.
22. No se ejecutan pruebas con hardware real en este WP.
23. En producción `/simulador/` sólo es accesible desde loopback y un cliente remoto recibe rechazo.

## Invariantes y restricciones

- El simulador genera entradas lógicas reales contra el backend seleccionado.
- FastAPI decide toda semántica institucional.
- No hay segunda autoridad de reglas en frontend.
- No hay hardware físico en este WP.
- No hay persistencia durable ni replay.
- No hay retries automáticos.
- No se agregan endpoints de test para facilitar la SPA.
- No se debilitan contratos ni pruebas existentes.
- La nueva aplicación debe permanecer separada de Moderación y Recinto.
- La futura prueba humana puede producir WPs posteriores de ajuste visual antes de la campaña final de hardware real.
- Aplica DT-038 ante cualquier necesidad de alterar contrato, seguridad, persistencia, infraestructura o reglas fuera de este alcance.
