# WP-080 - Garantizar continuidad de sincronización REST/SSE tras reinicio del backend

## Estado documental

`APROBADO`

## Objetivo

Evitar que Moderación, Recinto o Apoyo Técnico permanezcan conectados mostrando un snapshot obsoleto cuando el backend reinicia entre la carga REST inicial y la recepción SSE, reiniciando su contador de revisiones.

## Resultado esperado

Cada estado publicado identifica inequívocamente la instancia/época del backend. El sincronizador ordena snapshots dentro de una misma instancia por revisión, pero adopta inmediatamente una instancia nueva aunque su revisión sea numéricamente menor.

## Dependencias

- WP-079 `INTEGRADO`: gate de identidad/CI reproducible restaurado para abrir nuevos PR funcionales.
- WP-074 `INTEGRADO`: topología vigente de streams, incluido el stream técnico consolidado.

## Fuentes canónicas obligatorias

- `packages/api-client/src/sincronizador.ts`.
- APIs/proyecciones de estado backend y contratos generados.
- Composables de sincronización de Moderación, Recinto y Técnico.
- Tests de SSE/carga inicial existentes.
- Triage Astra ASTRA-001.
- DEC-001, DEC-003, DEC-007, DEC-017.

## Alcance

- Introducir un identificador opaco y estable durante la vida del proceso backend para la instancia/época que emite snapshots.
- Transportarlo en REST y SSE en los estados necesarios.
- Hacer que el sincronizador compare `instancia + revisión`: dentro de la misma instancia no retrocede; al cambiar de instancia adopta la nueva baseline aunque la revisión sea menor.
- Preservar reconexión, deduplicación y comportamiento normal existente.
- Actualizar tipos/cliente generado y pruebas.

## Fuera de alcance

- Implementar heartbeat/watchdog para blackholes de red (HIP-02).
- Persistir la revisión entre reinicios sólo para evitar el problema.
- Recuperar estado operativo previo a un reinicio.
- Cambiar polling/SSE por otra tecnología.

## Componentes previsiblemente afectados

- Backend: proyecciones/serialización/publicación de estados.
- `packages/api-client`.
- Composables de los tres frontends.
- Tests backend, frontend e integración SSE.

## Criterios de aceptación

1. Escenario reproducible: REST adopta revisión alta de instancia A; backend cambia a instancia B; SSE B entrega revisión baja; la UI adopta B.
2. Dentro de una misma instancia, un evento con revisión menor que la vigente continúa ignorándose.
3. Reinicio no requiere `onerror` para que el estado nuevo sea aceptado.
4. Moderación, Recinto y Técnico comparten la misma semántica.
5. No se introduce polling adicional.
6. Carga inicial y reconexiones normales no producen regresiones.

## Pruebas obligatorias

- Unitarias del sincronizador con cambio de instancia.
- Backend/contrato para el nuevo campo.
- Integración SSE reproduciendo reinicio/época nueva.
- E2E cuando sea razonable para al menos una superficie y regresión de las otras.
- `pnpm check:contrato`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
- Checks Python aplicables.
- `git diff --check`.

## Invariantes y restricciones

- El identificador de instancia es técnico/opaco, no una identidad institucional.
- No exponer secretos ni depender del reloj civil.
- La revisión conserva significado monotónico sólo dentro de una instancia.
- No rebase/force-push.

## Herramientas MCP y documentación técnica externa

Usar documentación oficial de EventSource/SSE sólo si aparece una duda técnica; no sustituye el contrato interno definido aquí.

## Consulta a producción si existe ambigüedad funcional/UX/visual

No copiar mecanismos históricos si contradicen la arquitectura SSE vigente.

## Decisiones que requieren escalamiento

Cualquier cambio que implique persistir estado entre reinicios, añadir autenticación o sustituir SSE requiere escalamiento.

## Documentación a actualizar

- Contratos/integraciones de estado y sincronización.
- Documentación técnica del mecanismo de revisión cuando corresponda.

## Impacto en el manual de usuario y soporte

`Requiere actualización del manual.` Añadir una nota de soporte que aclare que, tras reinicio del backend, las pantallas deben rebaselinarse automáticamente y qué señal de conexión esperar.
