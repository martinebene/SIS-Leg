# WP-001 - Inicialización reproducible del monorepo y toolchains

## Estado documental

`APROBADO`

## Objetivo

Crear la estructura ejecutable mínima y reproducible del monorepo SIS-Leg, con toolchains, lockfiles, scaffolds, controles de calidad base, un lanzador local de Work Packages y documentación del entorno MCP estándar para agentes, **sin implementar reglas de negocio**.

## Resultado esperado

Desde un clon limpio, un desarrollador o agente puede instalar dependencias con los gestores aprobados, ejecutar los checks raíz documentados y construir los dos frontends mínimos sin decisiones implícitas de stack.

Quedan creadas las ubicaciones canónicas de backend, Moderación, Recinto, device-bridge, paquetes compartidos y herramientas, listas para WPs posteriores.

Además queda disponible `scripts/iniciar_wp.py`, capaz de validar que un WP futuro ya está autorizado en la documentación, preparar automáticamente su rama y `git worktree` aislados y abrir la CLI del agente asignado dentro de ese worktree.

El README documenta también las herramientas MCP estándar definidas en DEC-003, cómo verificar su disponibilidad y cómo configurarlas en Codex, Claude Code y OpenCode sin almacenar credenciales en Git.

## Criterios de aceptación

1. Un clon limpio puede resolver dependencias Python exclusivamente mediante `uv` y el `uv.lock` versionado.
2. Un clon limpio puede resolver dependencias JS/TS exclusivamente mediante `pnpm` y `pnpm-lock.yaml` versionado.
3. La versión objetivo de Python queda fijada en 3.14 y la de Node en 24 LTS mediante mecanismos versionados apropiados.
4. Los dos Nuxt mínimos compilan como SPA estáticas y no arrancan un servidor Node como requisito del artefacto productivo.
5. TypeScript estricto y `nuxt typecheck` están habilitados.
6. Ruff, Ruff format check, Pyright, ESLint, Prettier y los builds aplicables pueden ejecutarse mediante comandos documentados.
7. La estructura del monorepo coincide con DT-001 y no introduce una rama `develop`, Docker ni base de datos.
8. CI ejecuta checks deterministas sobre el scaffold disponible y queda preparada para ampliarse sin cambiar la estrategia aprobada.
9. No existe lógica de sesión, votación, presencia, palabra ni auditoría institucional en este WP.
10. No hay secretos, datos institucionales reales ni artefactos de entorno versionados.
11. `scripts/iniciar_wp.py` rechaza iniciar un WP no aprobado, no marcado `EN_CURSO`, con agente distinto al asignado o con dependencias no integradas.
12. Con un WP futuro correctamente autorizado y un `main` limpio/actualizado, el lanzador crea una rama `wp/NNN-descripcion-corta`, un worktree hermano dedicado y ejecuta la CLI solicitada con ese worktree como directorio de trabajo.
13. Si la rama/worktree ya existe y corresponde inequívocamente al mismo WP, el lanzador puede reutilizarlo sin crear duplicados; si existe conflicto, falla sin borrar ni reparar destructivamente.
14. El lanzador soporta inicialmente `codex`, `claude` y `opencode`, y falla de forma explícita si la CLI solicitada no está instalada.
15. Ejecutar el lanzador no cambia `PLAN.md`, no hace commits directos a `main`, no abre/fusiona PRs y no realiza despliegues.
16. El flujo del lanzador y sus precondiciones quedan explicados en README con nivel suficiente para que el operador pueda iniciar un WP posterior mediante un único comando local después de la autorización documental.
17. README identifica Context7, Nuxt MCP, Playwright MCP y GitHub MCP/integración equivalente como herramientas estándar de agentes y explica su responsabilidad sin convertirlas en dependencias de runtime del producto.
18. README explica cómo verificar/configurar esas herramientas en los arneses principales sin versionar secretos ni archivos personales de configuración.
19. Queda documentado que la ausencia de un MCP necesario debe notificarse y que solo puede usarse un fallback claramente equivalente y seguro conforme a DEC-003.
20. Ningún check o test depende de una credencial MCP privada para poder ejecutar CI normal.

## Pruebas obligatorias

- Bootstrap desde entorno limpio o CI usando lockfiles congelados.
- Ruff check y format check.
- Pyright sobre los paquetes Python existentes.
- ESLint y Prettier check.
- `nuxt typecheck` en ambos frontends.
- Build de ambos frontends.
- Tests automatizados del lanzador usando repositorios Git temporales o mecanismos equivalentes seguros para cubrir al menos:
  - rechazo por rama distinta de `main`;
  - rechazo por working tree sucio;
  - rechazo por WP no aprobado/no autorizado;
  - rechazo por agente incorrecto;
  - rechazo por dependencia no integrada;
  - creación correcta de rama/worktree;
  - reentrada segura;
  - conflicto de worktree;
  - CLI ausente sin modificación destructiva.
- Comprobación documental de que los ejemplos de configuración MCP no contienen secretos reales y de que el flujo de ausencia/fallback está explicado.
- Tests de infraestructura mínimos únicamente cuando sean necesarios para demostrar que los runners/configuraciones funcionan; no inventar tests de negocio.

## Invariantes y restricciones

- No implementar anticipadamente WPs posteriores.
- No agregar librerías UI distintas de Tailwind/componentes propios.
- No usar npm/yarn como gestor canónico.
- No usar pip/requirements como fuente canónica.
- No introducir Docker/Compose.
- No agregar dependencias directas nuevas no previstas sin escalamiento DT-038.
- Los archivos específicos de herramientas agénticas no deben duplicar `AGENTS.md`.
- El lanzador es una herramienta mecánica local: no tiene autoridad sobre PLAN, aprobación, integración ni despliegue.
- El lanzador no puede usar force-push, rebase destructivo ni limpieza automática de worktrees/ramas con trabajo.
- Aplican las reglas de nomenclatura en español, comentarios pedagógicos y explicación de PR de DEC-001.
- Aplican las reglas de disponibilidad, aviso, fallback y secretos de MCP de DEC-003.
