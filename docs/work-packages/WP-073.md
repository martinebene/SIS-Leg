# WP-073 - Separar configuración operativa local de plantillas versionadas

## Estado documental

`APROBADO`

## Objetivo

Evitar que las pruebas humanas, el remapeo de hardware o la operación del entorno de desarrollo ensucien repetidamente el checkout coordinador de `main`, separando de forma explícita los archivos de configuración **operativos/locales** de las plantillas de referencia **versionadas**.

## Problema observado

Durante pruebas humanas se modifican archivos que hoy están trackeados por Git, especialmente bajo `config/`. Eso hace que `scripts/iniciar_wp_orca.py` falle correctamente al exigir un checkout coordinador limpio, aunque el cambio sea sólo estado/configuración local de la instalación.

También se observaron temporales de editor como `config/.system.toml.swp`, que no son producto ni configuración y no deben aparecer como archivos sin seguimiento.

`skip-worktree` sirve como mitigación local, pero no es una solución canónica: no se versiona, puede perderse o cambiar entre clones/operaciones Git y oculta de manera poco explícita la diferencia entre plantilla y dato operacional.

## Dependencias

- WP-069 `INTEGRADO`: base actual de la campaña y gate previo de ejecución.

## Decisiones humanas cerradas

1. Los archivos operativos reales de desarrollo/hardware deben quedar **ignorados por Git**.
2. El repositorio debe conservar ejemplos versionados suficientes para crear un entorno nuevo.
3. Un clon nuevo debe poder materializar sus archivos locales mediante un mecanismo idempotente.
4. Ese mecanismo **nunca sobrescribe** una configuración local existente.
5. Los temporales habituales de editor deben ignorarse canónicamente.
6. La migración de clones existentes debe preservar los archivos locales antes de que Git deje de trackear sus nombres.
7. Producción continúa provisionando configuración fuera de las releases; este WP no cambia DT-031 ni el runbook productivo.
8. No se utilizará `skip-worktree` como mecanismo permanente del producto.

## Archivos runtime/locales que deben dejar de versionarse

- `config/system.toml`
- `config/concejales.csv`
- `config/apoyo-tecnico/mensajes.csv`
- `services/device-bridge/config/devices.json`

Deben figurar explícitamente en `.gitignore`.

## Plantillas versionadas

Crear y mantener:

- `config/system.example.toml`
- `config/concejales.example.csv`
- `config/apoyo-tecnico/mensajes.example.csv`
- `services/device-bridge/config/devices.example.json`

Como punto de partida, las plantillas deben preservar el contenido de referencia que hoy está versionado, salvo ajustes estrictamente necesarios para explicar que son ejemplos.

## Temporales de editor a ignorar

Como mínimo:

- `*.swp`
- `*.swo`
- `*.swx`
- `*~`

No agregar patrones excesivamente amplios que puedan ocultar archivos legítimos del proyecto.

## Bootstrap local

Implementar un comando versionado, simple y multiplataforma, por ejemplo `scripts/preparar_config_local.py`, con estas reglas:

1. para cada runtime local, si el archivo **no existe**, copiar la plantilla correspondiente;
2. si ya existe, dejarlo byte a byte intacto;
3. crear directorios faltantes cuando corresponda;
4. informar claramente qué creó y qué preservó;
5. ejecución repetida idempotente;
6. no usar credenciales ni datos externos;
7. código de salida no cero ante un fallo real de E/S;
8. no depender de Git index flags como `skip-worktree`.

El nombre final del script puede variar si existe una convención mejor en el repositorio, pero el contrato anterior es obligatorio.

## Integración con desarrollo y CI

El implementador debe inspeccionar todos los consumidores reales antes de cambiar rutas o supuestos.

Debe garantizar que:

- `pnpm dev:stack` funciona desde un clon donde sólo existen las plantillas versionadas;
- `pnpm dev:stack:hot` funciona bajo la misma condición;
- la suite E2E integrada puede preparar su configuración local sin depender de archivos runtime trackeados;
- tests unitarios que ya usan `tmp_path`/fixtures continúan aislados y no se acoplan innecesariamente al runtime local;
- el device bridge conserva como ruta runtime predeterminada `services/device-bridge/config/devices.json`, pero existe una forma documentada de materializarla desde su ejemplo;
- el empaquetado productivo sigue excluyendo configuración institucional y no incorpora accidentalmente los archivos locales ignorados;
- la validación y despliegue productivos siguen operando sobre configuración provisionada en `/opt/sis-leg/config/`.

Se prefiere mantener las rutas runtime vigentes y cambiar sólo cómo se materializan/versionan. Cualquier cambio de contrato productivo de rutas queda fuera de alcance.

## Migración segura de clones existentes

Este WP debe documentar un procedimiento de una sola vez que **preserve antes de actualizar** los cuatro archivos runtime locales.

La documentación debe contemplar explícitamente que:

- algunos clones pueden tener `skip-worktree` en uno o más archivos;
- antes de adoptar el commit que deja de trackearlos, el operador debe copiar/resguardar sus archivos locales fuera del árbol o mediante un script disponible en la revisión;
- después de actualizar, se restauran en las rutas runtime ya ignoradas;
- se retiran flags `skip-worktree` heredados cuando corresponda;
- ninguna migración puede asumir que el contenido local coincide con el ejemplo versionado.

El implementador debe proponer en la PR el procedimiento exacto para este checkout coordinador. El ORCHESTRATOR/HUMAN_GATE ejecutará la migración en el momento de integración; el IMPLEMENTER no debe borrar ni reemplazar la configuración operacional del checkout coordinador.

## Alcance

- `.gitignore`.
- mover/copiar contenido de referencia a archivos `.example`.
- dejar de trackear los cuatro nombres runtime.
- bootstrap local idempotente.
- adaptar tooling de desarrollo/CI estrictamente necesario.
- pruebas de bootstrap y de comportamiento desde clon/config local ausente.
- documentación de `config/`, device bridge, README/runbook de desarrollo y manual si corresponde para soporte.
- actualizar cualquier referencia canónica que hoy afirme que los archivos runtime locales están versionados.

## Fuera de alcance

- cambiar el esquema o los valores funcionales de `system.toml`;
- modificar el contrato CSV del padrón;
- modificar el contrato de mensajes técnicos;
- cambiar fingerprints o reglas del device bridge;
- cambiar rutas productivas bajo `/opt/sis-leg/config/`;
- migrar a base de datos;
- introducir secretos, `.env` u otro sistema de configuración;
- hacer que el lanzador de WP ignore indiscriminadamente cambios arbitrarios del checkout;
- debilitar la exigencia de checkout limpio para archivos realmente versionables;
- limpiar o alterar los archivos locales reales del usuario como efecto lateral.

## Criterios de aceptación

1. En un clon limpio, Git no trackea los cuatro archivos runtime y sí trackea las cuatro plantillas.
2. `.gitignore` ignora explícitamente runtime y temporales de editor definidos.
3. El bootstrap crea los cuatro runtime faltantes desde plantillas.
4. Una segunda ejecución no modifica ningún runtime existente.
5. Si sólo cambian los runtime ignorados o aparecen swaps de editor, `git status --short` permanece limpio.
6. Un cambio real en una plantilla `.example` sí aparece en Git y sigue siendo revisable.
7. `scripts/iniciar_wp_orca.py` conserva su política general de checkout limpio; no se introduce una allowlist especial para esconder cambios trackeados.
8. `pnpm dev:stack` y `pnpm dev:stack:hot` pueden iniciar desde la situación documentada de clon nuevo.
9. La E2E integrada funciona sin depender de runtime trackeado.
10. El device bridge conserva su ruta runtime y puede ser preparado desde su ejemplo.
11. Empaquetado/release no contiene configuración institucional local.
12. Producción y rollback conservan el contrato vigente de configuración fuera de releases.
13. Existe documentación explícita de migración segura para clones con y sin `skip-worktree`.
14. La ayuda/manual se evalúa y se actualiza si el cambio afecta al soporte técnico; si no requiere contenido de usuario, la PR lo justifica.
15. `config/apoyo-tecnico/mensajes.csv` local nunca es sobreescrito por bootstrap, tests o migración.

## Pruebas obligatorias

- unitarias del bootstrap:
  - crea cuando falta;
  - preserva cuando existe;
  - idempotencia;
  - directorios faltantes;
  - error de E/S;
- prueba Git en un repositorio temporal o equivalente que demuestre runtime ignorado y plantilla trackeable;
- tests existentes de configuración backend, padrón, mensajes y bridge;
- `pnpm dev:stack`/smoke equivalente desde runtime inicialmente ausente;
- `pnpm dev:stack:hot` al menos mediante tests de su lógica de preparación o smoke controlado;
- `pnpm test:e2e:integrado`;
- `pnpm empaquetar:produccion` y validación de que no se empaquetan runtime locales;
- gates generales de calidad;
- CI completa de la PR exacta.

## Invariantes y restricciones

- No rebase.
- No force-push.
- Squash merge.
- Revisión independiente obligatoria.
- Preservar configuración operacional local.
- No usar `git clean`, `git reset --hard` ni restauraciones destructivas sobre los runtime.
- No modificar `config/apoyo-tecnico/mensajes.csv` operacional del checkout coordinador.
- WP-029 permanece BLOQUEADO.
- Con el perfil actual del contenedor, si se ejecutan pruebas con navegador rige `max_concurrency = 1`.
