# WP-025 - Shell público, bancas, presencia, quórum y uso de palabra

## Estado documental

`APROBADO`

## Objetivo

Construir la primera versión funcional de la **Pantalla del Recinto** sobre el scaffold Nuxt existente, conectada exclusivamente al estado público autoritativo de FastAPI mediante `ClienteRecinto`.

El WP debe dejar operativa la experiencia pública básica fuera del tratamiento visual específico de votaciones:

- shell general y estado de conexión;
- contexto de preparación/sesión;
- disposición visual de bancas;
- identidad pública e imagen de cada concejal;
- presencia/ausencia;
- test físico temporal;
- quórum;
- orador actual y cola de pedidos de palabra;
- reconstrucción completa después de recarga o reconexión;
- comportamiento responsive para Full HD y otra resolución representativa.

La Pantalla del Recinto permanece estrictamente **de solo lectura**.

## Resultado esperado

Al integrar este WP:

- `apps/recinto/` deja de ser un scaffold estático y consume `EstadoRecinto` mediante `@sis-leg/api-client`;
- snapshot REST + SSE constituyen la única fuente de estado;
- la aplicación distingue `SIN_PREPARAR`, `PREPARANDO` y `SESION_ABIERTA`;
- la sesión pública muestra número, Presidencia y Secretaría Legislativa cuando corresponda;
- presencia y quórum cambian con baja latencia sin cálculos institucionales duplicados;
- las bancas se construyen desde la disposición configurada y el padrón público, nunca desde una geometría fija para doce bancas;
- cada banca utiliza `ruta_imagen` proyectada, sin asociación hardcodeada banca→archivo;
- ausencia, presencia, test físico y uso de palabra se distinguen visualmente;
- orador y cola pública provienen exclusivamente de `EstadoRecinto.palabra`;
- una pérdida de SSE conserva la última vista confirmada pero deja claro que puede estar desactualizada;
- una reconexión vuelve a adoptar el snapshot público vigente sin depender de historia local;
- no existe ningún comando mutante ni acceso a `ClienteModeracion`;
- no se agregan dependencias externas nuevas.

## Alcance

### 1. Shell público de solo lectura

Construir una aplicación de pantalla completa orientada a visualización pública.

Debe incluir como mínimo:

- identificación institucional visible;
- estado técnico de conexión;
- contexto de estado global;
- contexto de sesión cuando exista;
- área principal de bancas;
- área pública de uso de palabra;
- área de quórum/presentes integrada al diseño.

No debe contener botones, formularios ni affordances que sugieran acciones institucionales.

No importar ni instanciar `ClienteModeracion`.

### 2. Sincronización autoritativa REST + SSE

Crear una frontera reactiva para Recinto sobre:

- `ClienteRecinto.obtenerEstado()`;
- `ClienteRecinto.suscribirEstado()`.

Debe conservar las garantías ya vigentes del sincronizador compartido:

- snapshot inicial;
- stream SSE;
- adopción de estados completos;
- reconexión mediante nueva baseline;
- cancelación determinista al desmontar;
- sin polling periódico;
- sin WebSocket;
- sin segunda fuente de verdad.

Estados visuales mínimos de conexión:

- inicial/conectando;
- conectado;
- reconectando con último snapshot conservado;
- desconectado sin snapshot válido.

Durante `RECONECTANDO`, la última vista confirmada puede mantenerse visible, pero debe mostrarse una indicación pública discreta de conexión degradada/desactualización.

No borrar el último estado confirmado únicamente por perder el stream.

### 3. SIN_PREPARAR

En `SIN_PREPARAR`:

- no mostrar datos residuales de una preparación/sesión anterior;
- mostrar un estado neutro institucional;
- no mostrar bancas viejas, quórum viejo, orador viejo ni cola vieja;
- conservar únicamente elementos de shell no funcionales, como marca institucional y estado de conexión.

El frontend debe obedecer la nueva baseline incluso si la revisión numérica reinicia después de un restart del backend.

### 4. PREPARANDO

En `PREPARANDO`, la pantalla puede mostrar que la sala está en preparación sin presentarla como sesión formalmente abierta.

Debe poder mostrar:

- bancas cargadas;
- presencia/acreditación actual;
- test físico temporal;
- quórum actual;
- número/autoridades solo si ya están informados, diferenciando visualmente que aún se trata de preparación.

No debe inventar un número de sesión ni completar autoridades ausentes.

### 5. SESION_ABIERTA y cabecera institucional

Cuando `estado_global == SESION_ABIERTA` y `estado.sesion` existe, mostrar al menos:

- número de sesión;
- Presidencia;
- Secretaría Legislativa;
- presentes actuales;
- quórum requerido/alcanzado.

No recalcular quórum desde `concejales.filter(...)` como fuente institucional: usar `EstadoRecinto.quorum`.

Un conteo derivado de concejales puede usarse solo como verificación visual interna/test, nunca como dato autoritativo alternativo.

### 6. Disposición de bancas

La disposición visual debe provenir de la configuración congelada de la preparación activa.

Regla histórica/canónica a preservar:

- banca 1 comienza abajo a la izquierda;
- cada fila numera de izquierda a derecha;
- al completar una fila, la numeración continúa en la fila inmediatamente superior.

La UI debe soportar cambios razonables en:

- cantidad de filas;
- cantidad de bancas por fila;
- cantidad total de concejales.

No hardcodear 12 bancas, dos filas, coordenadas fijas ni un layout que dependa de la configuración actual de producción.

La relación entre número de banca y posición se deriva de `filas_bancas` y del campo `banca` de cada `ConcejalPublico`.

### 7. Tarjeta pública de banca

Cada banca debe mostrar de forma legible:

- imagen desde `ruta_imagen`;
- nombre;
- apellido;
- bloque cuando no esté vacío;
- número de banca cuando aporte claridad.

No usar DNI ni identificador de dispositivo: esos campos no pertenecen al DTO público.

La ruta de imagen se consume tal como la proyecta el backend/padrón. No crear un mapa local `banca -> archivo`.

Una imagen faltante/rota debe degradar de forma controlada sin romper toda la grilla.

### 8. Presencia y ausencia

Los estados presente/ausente deben ser inequívocos sin depender exclusivamente de una variación sutil de color.

La ausencia puede atenuar imagen/fondo y/o mostrar una marca textual, siempre manteniendo identificable la banca.

No existe control de presencia en esta aplicación.

Un cambio de presencia debe reflejarse cuando llega el nuevo `EstadoRecinto`.

### 9. Test físico temporal

Si `ConcejalPublico.test_activo == true`, la banca debe mostrar un estado visual temporal claramente distinguible de:

- presente normal;
- ausente;
- uso de palabra.

La UI no crea ni prolonga el test.

`test_expira_en` puede utilizarse para presentación local si aporta valor, pero no debe producir una segunda transición institucional. La expiración autoritativa continúa en backend/proyección.

### 10. Quórum público

Mostrar desde `EstadoQuorum`:

- cantidad_presentes;
- requerido;
- alcanzado.

El diseño debe permitir reconocer rápidamente si hay o no quórum.

No calcular mayoría, denominadores ni reglas de votación en este WP.

### 11. Uso de palabra público

Mostrar desde `EstadoPalabraPublico`:

- orador actual, si existe;
- cola completa en orden FIFO;
- nombre/apellido/banca de cada persona.

La banca del orador puede resaltarse con una señal visual derivada exclusivamente de `palabra.orador.banca`.

La cola debe conservar exactamente el orden recibido.

No habilitar:

- otorgar palabra;
- quitar palabra;
- editar cola;
- reordenar;
- eliminar pedidos.

Si no existe palabra activa, la UI puede dejar la zona vacía o mostrar un estado neutro breve.

### 12. Coexistencia de palabra con otros estados

La palabra puede seguir mostrándose durante una votación.

Este WP no debe ocultarla, congelarla ni alterar su orden porque exista `estado.votacion`.

El tratamiento visual específico de votación queda fuera de alcance de este WP.

### 13. Responsive y hardware

Resolución primaria de referencia:

- 1920×1080 Full HD.

Agregar al menos otra resolución representativa, preferentemente:

- 1366×768.

La composición debe:

- mantener legibles nombres, imágenes, quórum y palabra;
- evitar solapamientos;
- evitar scroll general de página en la resolución de referencia;
- permitir scroll interno únicamente donde una cola o contenido variable lo requiera;
- adaptarse de forma controlada a relaciones de aspecto no exactamente 16:9;
- evitar píxeles/coordenadas absolutas que obliguen a reescribir la aplicación ante otro monitor.

### 14. Seguridad del frontend público

La aplicación solo consume `EstadoRecinto`.

No debe:

- leer `EstadoModeracion`;
- importar `ClienteModeracion`;
- llamar endpoints mutantes;
- contener DNI/dispositivos por rutas alternativas;
- inspeccionar auditoría cruda;
- reconstruir votos ocultos;
- mantener datos no públicos ocultos con CSS.

Aunque el tratamiento visual de votación se implementará posteriormente, este WP no puede introducir una vía que degrade CA-050.

### 15. Accesibilidad visual mínima

Sin convertir este WP en un proyecto de accesibilidad transversal, asegurar:

- contraste suficiente en texto crítico;
- nombres legibles a distancia;
- estados presente/ausente/test/orador no dependientes únicamente del color;
- textos largos que no desborden el layout;
- indicadores de conexión visibles pero no dominantes.

## Decisión aprobada para este WP

### DP-025-01 - Disposición pública de bancas en EstadoRecinto

Durante la planificación se verificó directamente el contrato integrado:

- `EstadoRecinto` expone estado global, preparación/sesión, concejales públicos, quórum, votación y palabra;
- `ConcejalPublico` expone número de banca e identidad pública;
- la configuración congelada ya contiene `filas_bancas`;
- `config/system.toml` representa la disposición mediante `[room] rows = [...] `;
- el modelo `ConfiguracionSistema.filas_bancas` define cada elemento como **cantidad de bancas de una fila**;
- el validador acepta una lista no vacía de enteros positivos y no exige igualdad entre filas;
- la proyección pública actual todavía no expone esa disposición.

El HUMAN_GATE aprobó explícitamente la alternativa A: extender `EstadoRecinto` con un campo público mínimo:

`filas_bancas: tuple[int, ...] | None`

Semántica exacta:

- `null` en `SIN_PREPARAR`;
- copia exacta, ordenada e inmutable de `contexto.configuracion.filas_bancas` en `PREPARANDO` y `SESION_ABIERTA`;
- cada posición representa **una fila física**;
- cada valor representa **la cantidad de bancas de esa fila**;
- las filas pueden contener cantidades distintas de bancas;
- el primer elemento corresponde a la **fila inferior** del recinto;
- los elementos siguientes corresponden sucesivamente a filas superiores;
- dentro de cada fila, las bancas se numeran de izquierda a derecha;
- la numeración total continúa en la fila superior cuando se completa la inferior.

Ejemplos válidos de configuración:

- `rows = [6, 6]`: dos filas de seis bancas;
- `rows = [5, 7]`: fila inferior de cinco y fila superior de siete;
- `rows = [3, 4, 5]`: tres filas con cantidades diferentes, como la configuración de desarrollo actual.

No es una matriz rectangular `filas × columnas` ni se deduce una cantidad global de columnas. Cada fila tiene su propia capacidad.

La capacidad total del recinto sigue siendo:

`sum(filas_bancas)`

y debe continuar coincidiendo con la cantidad de concejales del padrón conforme al contrato de configuración vigente.

La consulta acotada al sistema original en producción confirmó la misma semántica funcional: la disposición histórica contiene filas independientes con su propia cantidad de columnas, la fila 1 es la inferior y la numeración continúa hacia arriba. Esa referencia no reemplaza el contrato canónico de SIS-Leg ni autoriza copiar su formato JSON o su lógica técnica.

El cambio de DP-025-01 queda limitado a:

- DTO/proyección pública;
- OpenAPI;
- tipos TypeScript derivados;
- tests de contrato/proyección;
- consumo en `apps/recinto`.

No cambia:

- el formato actual de `config/system.toml`;
- `ConfiguracionSistema.filas_bancas`;
- el validador de `room.rows`;
- el padrón;
- la numeración institucional de bancas;
- el resto de la configuración pública o privada.

No se crea una consulta pública separada y no se considera aceptable inferir filas por números de banca ni hardcodear la disposición vigente.

## Invariantes y restricciones

- `EstadoRecinto` es una allowlist pública propia.
- La pantalla pública nunca muta estado.
- REST snapshot + SSE es el único mecanismo normal de sincronización.

- DEC-001, DEC-003, DEC-007, DEC-013, DEC-014 y DEC-017 siguen vigentes.
